# Повторный проход E2E по исходному коду: дополнительные находки

Дата: 2026-09-05. Это исследование, не отчёт о новом живом прогоне.
Исходная база: dd-eval `c1f0b93`, dd-flow-cli `e11a611`, текущие инструкции dd-memorybank.
Дополняет `specs/024-three-e2e-systemic-repair-implementation-plan.md` и
`2026-09-05-three-e2e-root-cause-audit.md`. Исходный код не исправлялся.

## Границы достоверности

Проверены критические пути запуска, привязки, делегирования, паузы,
продолжения, завершения и восстановления в Codex, AGY, ZCode; Grok и
OpenCode проверены как потребители тех же контрактов. Это не утверждение,
что прочитана каждая строка всех пяти нативных упряжек. Для Codex дополнительно
проверен локальный нативный `codex-rs/core/src/hook_runtime.rs`.
Ни одна новая находка ниже не объявляется доказанной причиной прошедшего
инцидента без соответствующего события в его транскрипте. Различаем дефект
ветки кода, воспроизводимый сценарий и историческое проявление.

## Модель прохода, общая для пяти упряжек

1. Подготовка: отдельные project и DD_FLOW_HOME, выбранная пара движка/пакета,
   профиль, ресурсы. Создать daemon и корневую Session, сохранить её native id.
2. SPECIFY: отдельный stage start → хук → привязка Session/Work → стартовый
   пакет. Семантику intake и вопросы обрабатывает модель. HITL означает pause,
   а не завершение стадии. Ответ проходит semantic Judge, сохраняется и resume
   возвращает управление той же стадии.
3. PROTOCOLIZE: принятый результат SPECIFY → распределение требований,
   протоколы и маршрут рабочего дерева. project_root остаётся технической
   идентичностью; workspace_root может смениться. Нельзя смешивать их с RUN home.
4. PLAN: контекст реализации, проверки, новые проверочные средства и граф Work.
   CLI проверяет структуру и зависимости, но не решает семантическую достаточность.
5. PLAN-REVIEW: готовые независимые группы запускаются волнами с учётом depends_on.
   Ревьюеры должны иметь пустой контекст; координатор классифицирует находки
   и корректирует план. review_off не запускает модельное ревью.
6. CODE: work start выдаёт контекст; работник реализует задачу; work finish
   запускает назначенные проверки. Завершение Work не доказывает завершение
   нативного хода. Координатор выполняет общую верификацию и общий gate.
7. CODE-REVIEW: независимое ревью → решение координатора → исправления →
   проверка исправлений и актуальные доказательства. Зависимые Work не должны
   стартовать до принятия результатов предшественников.
8. MERGE: захват очереди/блокировки, merge apply без коммита, проверки
   интегрированного дерева, затем коммит. При неуспехе нужен согласованный
   маршрут восстановления, а не угадывание по линейному номеру стадии.
9. Завершение: отдельно зафиксировать состояние флоу, Work, родителя и детей
   упряжки; собрать статистику и доказательства; остановить принадлежащие
   запуску процессы. Не подменять исходный failure успешной уборкой.

## По каждой упряжке

### Codex

Создание thread и turn идёт через `lib/dd-codex.mjs`, жизненный цикл процесса —
`lib/dd-codex-daemon.mjs`. Во всех стадиях lifecycle-команда проходит
`handleCodexHook`. Нативный PreToolUse содержит transcript текущей Session и
agent_id текущего дочернего thread. Именно на переходе от корня к Work ребёнка
обнаружено смешение transcript binding (N03). В PLAN/ревью/CODE запускающий
пакет недостаточно явно различает новую Session и пустой контекст (N02).
В MERGE действует общее противоречие N01; при рестарте — N06/N07.
Известные D01/D03/D04 не переименовываются в новые дефекты.

### AGY

`bin/dd-agy.mjs` передаёт хуки демону и переводит tool events в CLI;
`handleAgyEvent` переиспользует механическую обработку OpenCode.
SPECIFY/HITL доходит до общего раннера. После делегирования появляется
дополнительная проблема: Stop и transcript ребёнка меняют общий receipt
родителя (N04). Статус ребёнка в observeStep также выводится из состояния
родительского tool step, а не собственного terminal-события ребёнка.
При CODE/ревью это делает дерево ненадёжным источником решения «можно дальше».
При восстановлении остаётся ранее найденная подмена Session D08; её исправление
не устраняет N04. MERGE и сбор результатов используют общие контракты.

### ZCode

Создание/продолжение используют отдельные native и adapter id. После первого
хода requireSettled проверяет корневую projection и running children. Однако
productive/session.inspect/session.cancel обновляют active_tree по детям и
локальному activeProductive. Это разные определения одного состояния (D06,
дополнительные затронутые пути). При max_turn_requests возможно «адаптер
вернул результат» без завершения корня; повторный wait от координатора не
устраняет причину. Проверить normal, inspect, cancel, recovery, stop одним
набором сценариев. Во всех последующих стадиях повторяется тот же lifecycle,
поэтому чинить только CODE нельзя. Счётчики и осиротевшие процессы остаются
отдельными уже описанными D09/D10, не новыми находками.

### Grok

Общий runner → daemon → ACP session info/list_running/usage. В начале всё
связано с одной корневой Session. После ошибки транспортного запроса локальный
active снимается; refreshTree читает info корня, но не использует его status
при вычислении завершённости (N05). Список детей пуст не означает, что корень
закончил работу. Это тот же класс, что ZCode, с другим местом потери состояния.
Касается ожидания после любой стадии, нового prompt и daemon.stop.

### OpenCode

HTTP session create/prompt/inspect, plugin events → общий CLI hook handler.
describe обходит дочернее дерево и читает статусы; отсутствие id в statuses
трактуется как idle. Само по себе это НЕ объявлено дефектом: такое может быть
контрактом sparse status API и требует проверки нативной реализации.
Но параллельные inspect и завершение prompt вызывают persist без очереди,
пишут один и тот же временный файл (N09). Точка риска повторяется после любой
стадии и при уборке; последовательный smoke её не ловит.

## Дополнительные находки и системные исправления

### N01. Две противоположные инструкции MERGE — подтверждено

Источники: dd-memorybank `.memory-bank/dd-flow/vnext/merge.md:33`,
dd-flow-cli `src/services/vnext-merge.ts:219`.
Канон требует чинить integration workspace в том же Work и повторять finish;
CLI требует merge repair, возврат в CODE, независимое CODE-REVIEW и новый MRG.
Это дефект согласованности документации/промптов, не доказательство того, что
оба текста обязательно попали в конкретную Session. Агент, читающий канон,
получает несовместимую с runtime инструкцию.

Исправление: закрепить один принятый маршрут source repair и исправить канон,
пакет, операционные примеры. Отдельно описать разрешённое восстановление среды
без изменения продукта и повтор проверки из B5 плана 024. Не разрешать этим
обход обязательного review исправленного продукта.
Тест: упавший gate → точная команда/ожидаемый Work/новый MRG; отдельный случай
восстановления среды. Согласованность смысловых инструкций проверяет reviewer,
а не поиск запрещённых слов в тестах.

### N02. Fresh Session не гарантирует пустой контекст — подтверждён пробел контракта

Источники: dd-eval `lib/runner.mjs:1735`; dd-flow-cli
`src/services/work-registry.ts:249`, vnext-plan-review.ts:110,
vnext-code-review.ts:69. Work помечен fresh_agent_required, но CLI проверяет
новый id и отсутствие предыдущих Work в этом RUN. nativeChildFanoutPrompt
передаёт id/команду, а не режим контекста. Новая дочерняя Session с унаследованной
историей удовлетворяет проверке id, но не цели независимого ревью.

Исправление: явно передавать требование пустого контекста в запускающем
поручении и профильном способе вызова нативного инструмента. Использовать
существующий launch policy, не добавлять вторую сущность «ревью-сессии».
Если упряжка подтверждает режим — сохранить наблюдаемое подтверждение;
если не подтверждает — не выдавать проверку уникального id за доказательство
изоляции. Проверка полномочий CLI и оценка контекста Judge остаются разными.
Тесты: рендер поручения с режимом/моделью, совместимость для каждой упряжки;
живой smoke проверяет реальный режим. Не утверждаем, что все прежние ревью
были загрязнены: это требует исследования их launch events.

### N03. Codex: transcript ребёнка записывается в binding корня — подтверждено по коду

Источники: CLI hooks.ts:400, hooks.ts:1508; Codex
`codex-rs/core/src/hook_runtime.rs:183` (PreToolUse), :1030 (agent_id).
Эффективная identity выбрана по agent_id, но upsertSessionBindingFromPayload
вызывается с rootProviderSessionId и payload текущего ребёнка. transcript_path
в payload имеет приоритет и обновляет codex_session_bindings корня.

Исправление: вычислить эффективную native identity один раз; transcript и cwd
записывать её владельцу. Корневой session_id сохранить как отдельный факт
родства, не как владельца child transcript. Проверить все читатели
codex_session_bindings, импорт transcript/usage и проекцию Session.
Тест: чередование хуков root → child A → child B → root; ни один transcript
не мигрирует к соседу. Проверять таблицу и event receipt, не только успешный start.

### N04. AGY: общее lastStop/transcriptPath смешивает разные Session

Источники: dd-eval lib/dd-agy-daemon.mjs:156, :169, :173.
observeHook вычисляет conversationId, но Stop записывает в this.lastStop,
transcript в this.transcriptPath без проверки принадлежности. receipt корня
читает эти общие поля. Отдельно DONE родительского tool step объявляет детей
completed. Это подтверждённые правила кода; порядок таких событий в конкретном
прогоне требует отдельного сопоставления журнала.

Исправление: map наблюдений по conversation_id; root receipt читает root;
дети получают собственные состояния. Если provider не даёт terminal ребёнка,
показывать unknown, а не выводить success из завершения инструмента запуска.
Stop должен относиться к текущему execution, не прошлому ходу.
Тесты: перестановки root/child Stop, запоздалый Stop предыдущего хода,
parent tool DONE при ещё работающем ребёнке, child transcript после root.

### N05. Grok повторяет класс «нет запроса/детей ⇒ корень завершён»

Источники: dd-eval lib/dd-grok-daemon.mjs:216–234;
lib/dd-grok.mjs:78. refreshTree получает info, но проверяет this.active и
list_running детей, не info.status корня. После обрыва/исключения productive
сбрасывает active, и следующий status/stop может признать дерево свободным.

Исправление: единая нормализация наблюдений корня и детей с различением
terminal, running и unknown. Использовать её в prompt, inspect, stop, cancel,
recovery. Это расширение B1/B2 на Grok, а не новый механизм оркестрации.
Тест: запрос адаптера завершился ошибкой, native root running, детей нет;
нельзя новый prompt или clean shutdown. Отсутствующий status не считать success.

### N06. Recovery обходит дополнительные контракты обычного пути

Источники: dd-eval lib/runner.mjs:1676, :2255, :2317.
promptExistingSession вызывает callDriver напрямую: пропускает
assertObservedProfile и boundedPromptArgs из providerTurn. Successor всегда
продолжается в прежней Session, без normal ветки new_session/merge_server.
Кроме того, новый slice и launcher записываются без context_prepared event;
preparedContextFor затем не может вернуть их hashes в результат восстановления.

Исправление: B2 должен объединять не только выбор стадии, но и исполнение
provider turn, session policy и регистрацию границы. Не копировать эти ветки
снова в recovery. Тесты: profile mismatch после recovery, new_session,
merge_server, тот же набор context hashes в normal и recovered результатах.
Это углубление известного D01, не отдельный повторный подсчёт дефекта.

### N07. Повтор HITL читает изменяемый файл, но пишет старый checksum

Источники: runner.mjs:473–478 и :2281–2284. В reference и recovery проверяется
существование answer_file, но не соответствие bytes сохранённому answer_sha256.
В журнал resume_retried попадает старый hash; resume читает текущий файл.

Исправление: один helper загрузки принятого ответа с проверкой bytes/hash до
отправки. При несовпадении — инфраструктурная ошибка с сохранением evidence,
не повтор semantic Judge и не молчаливое обновление hash. Это не семантический
гард, а проверка целостности уже принятого ответа.
Тесты: изменение/удаление файла между match и resume для обеих веток;
неизменённый ответ передаётся без нового раунда.

### N08. Стартовые ответы следующих стадий перезаписывают один файл

Источник: runner.mjs:1372. Для context-файлов
stage-context/<stage>.json response path всегда stage-context/stage-start-response.json.
Текущая стадия получает правильный ответ, но ссылка в launcher предыдущей
стадии позднее показывает уже другой ответ. Это доказанный дефект сохранности
живого стартового артефакта; возможные копии текста в provider transcript
не объявляются утраченными.

Исправление: response path в каталоге конкретной стадии/попытки; тот же path
сохранить в boundary event и evidence. Повтор текущего start остаётся
идемпотентным. Не нужны отдельная БД или новая система версионирования.
Тест: PLAN→PLAN-REVIEW→CODE и repair attempt не меняют принятые предыдущие файлы.

### N09. OpenCode: конкурентные сохранения используют один temp-файл

Источники: lib/dd-opencode-daemon.mjs:18, :65, :77, :111.
persist не сериализован; два socket запроса могут одновременно write/rename
`daemon.json.<pid>.tmp`. Возможны ENOENT второго rename и несогласованный снимок.
Соседние Codex/Grok/ZCode используют promise-очередь; AGY ещё и снимает snapshot.

Исправление: применить существующий паттерн очереди записи и structuredClone
до постановки в очередь. Уникальный temp без очереди устраняет коллизию имён,
но не гарантирует порядок состояний. Не вводить общий persistence framework.
Тест: параллельные inspect, окончание prompt и cancel; искусственно задержать
write/rename; проверить JSON, порядок и отсутствие ложной ошибки API.

## Что не следует ошибочно исправлять

- Перехват ошибок heartbeat сам по себе не означает потерю защиты:
  managed-daemon.mjs хранит lease.error, daemon-operations.mjs:28 вызывает
  assertDaemonOwnership перед продуктивной операцией. Повторный guard не нужен.
- OpenCode sparse statuses требует проверки API, а не запрета отсутствующих id
  по аналогии с другим provider.
- Отсутствие tool output не доказывает зависание. Изменения должны сохранить
  согласованные правила наблюдения за живой упряжкой.
- Нельзя исправлять продукт тестового кейса вместо общих контрактов флоу.

## Приоритет и порядок дополнения плана 024

1. N01: согласовать принятое поведение MERGE во всех источниках инструкций.
2. N03/N04/N05: identity и scoped observations; тесты с перемешанными событиями.
3. N06: общий механизм продолжения и исполнения turn, включая профиль и события.
4. N02: явный режим контекста нативных детей, без смешения с Session id.
5. N07/N08: целостность принятого ответа и сохранность стартовых артефактов.
6. N09: очередь сохранения состояния OpenCode.
7. Объединить с D01–D12, провести контрактные/интеграционные тесты; затем
   разрешённые отдельно smoke/E2E. Не считать этот мысленный проход живой проверкой.
