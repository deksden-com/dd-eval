## 1. Раннер дублирует линейную последовательность вместо переходов флоу

**Подтверждено журналом и кодом.** Последний ответ Luna сообщает о падении
`CHK-P1-API-UNIT`, успешном `merge repair`, создании WRK-024 и намеренной
остановке перед следующей стадией. CLI вернул `next.stage: code`.

`dd-flow-cli/src/services/vnext-merge.ts:repairVnextMerge` создаёт цикл
CODE → CODE-REVIEW → replacement MERGE. `runs.ts:prepareVnextMergeSourceRepairAttempt`
архивирует предыдущие стадии, открывает CODE, убирает текущую MERGE из stage_runs.
Но `dd-eval/lib/runner.mjs` около 2100 требует done у прежней стадии,
а `nextStage()` просто выбирает соседний элемент массива. Поэтому законное
состояние восстановления превращается в `incomplete_subject_turn`.

**Тот же класс:** основной путь, reference builder, recovery и merge-server
имеют самостоятельные решения о переходах; recovery около 2318 также использует
`nextStage`, а server-ветки требуют немедленно завершённый MERGE.

**Исправление:** один общий обработчик продолжения для этих путей. Он читает
авторитетное состояние и разрешённое следующее действие dd-flow, учитывает
попытку/цикл и границу запрошенного эвала. Не исполнять произвольную команду из
агентного текста. Не вводить вторую Flow DSL. Повтор одинакового состояния без
прогресса диагностировать, но законный новый repair-цикл не считать повтором.

## 2. Проверка с БД попала в unit-набор без подготовки среды

**Подтверждено.** В MERGE 11 из 12 receipts passed, включая browser.
RCP-001: `pnpm --filter @dd-tasks/api test:unit` упал:
`database "dd_tasks_foundation_test_4c34d2c6ba0f" does not exist`.
Следующий RCP-002 `pnpm test:api-contract` прошёл.

В feature workspace `vitest.unit.config.ts` включает все `tests/**/*.test.ts`,
исключая только `*.integration.test.ts`. `api-task-contract.test.ts` подключает
SQL и использует константы из global-setup, но импорт модуля не запускает его
подготовку БД. Поэтому отдельный contract entrypoint работает, а unit entrypoint
не воспроизводит необходимую среду. Это не доказательство поломки PostgreSQL
или коллизии параллельных эвалов. Подготовленная раньше БД способна маскировать дефект.

**Системное исправление флоу:** PLAN должен назначать проверку вместе с её
реальным entrypoint и условиями подготовки; CODE проверяет затронутые публичные
тестовые команды в чистой предусмотренной среде; REVIEW ищет скрытую зависимость
от порядка предыдущих проверок. Семантическую классификацию делает агент.
CLI выполняет объявленную подготовку и команды, а не угадывает тип теста по имени.
Продуктовый код этого исторического эвала в рамках аудита не менять.

## 3. Repair Work может завершиться без проверки своего исправления

**Подтверждено.** После WRK-018 были WRK-019…022: последовательные исправления
форматирования одного browser-файла. Retained stderr RCP-038/048/058/068 показывает
ошибки форматирования; после исправления появлялись/оставались следующие.

`selectRepairChecks` сохраняет `run_at: code/readiness`.
`work-registry.ts:settle` выполняет только `run_at === work`.
При этом prompt WRK-019 говорит: «CLI executes work-scoped checks» и
«do not rerun declared checks manually», а его единственная проверка —
`POLICY/code/quality at code`. Исполнитель объявляет успех, родитель снова
запускает полный gate. В CODE-REVIEW сохранено 60 aggregate receipts,
из них шесть failed; суммарная длительность этих команд — около 13,46 минуты.
Это время команд, не полная длительность стадии.

**Исправление:** отличить владельца исходного итогового gate от обязательной
проверки repair. При завершении repair повторить причинную проверку либо
заранее объявленную подходящую фокусную проверку. Исходное назначение итогового
gate не менять и итоговую интеграционную проверку не отменять. Если локально
запуск невозможен, решение должен явно принять координатор, а не молчаливый фильтр.
Для механического форматирования использовать штатный formatter, а не серию
ручных правок отступов. Не создавать новый Work на каждую неуспешную самопроверку.

Существующий тест `test/vnext-code.test.ts` специально закрепляет сохранение
aggregate run_at. Его нужно дополнить проверкой ответственности за repair,
а не просто перевернуть ожидаемый флаг.

## 4. Архивирование стадий ломает ссылки на доказательства

**Подтверждено проверкой файлов.** После MERGE repair RCP-001 существует под
`07-merge/try-001/works/WRK-023-merge/checks/RCP-001/`.
Его `receipt_path`, `stdout_path`, `stderr_path`, `completion_path` указывают на
старую папку без `try-001`; все четыре указанных файла отсутствуют.

`archiveExistingStageAttempt` делает rename файлов, но не обновляет адреса.
`checkReceipts` читает прежние пути из SQLite. `addVnextCodeRepair` переносит
`receipt_path` в required_read новой задачи. Значит даже исправление раннера
из пункта 1 приведёт следующего исполнителя к повреждённой ссылке на причину.

**Тот же класс:** обычный restart стадии использует ту же функцию; сообщения,
HTML, work_sessions и `run://` ссылки тоже могут описывать старую попытку.
Отдельно проверить `retryWork`, архивирующий лишь несколько файлов Work и
сбрасывающий его статус: это не доказанный инцидент данного прогона, но тот же
участок ответственности за попытки, связи с Session и доказательства.

**Исправление:** сохранить существующую концепцию текущей папки и архива, но
централизовать перенос попытки и разрешение исторических ссылок. Квитанция/ID
не должны терять адресуемость после перемещения. Использовать имеющиеся ID
receipt и attempt, не вводить дополнительные версии ради версий. Проверять
читабельность всех зависимых доказательств после архива и после рестарта процесса.

## 5. Ошибка нативного дочернего исполнителя не отражается в Work

**Подтверждено.** В daemon.json ZCode два CODE-субагента:
`agent_289492ae-3109-428f-aef3-546eddab54f8` и
`agent_10fcde3f-4f6a-48a9-b3e8-028d1905876f` — failed с текстом
`Subagent was inactive for 600000ms`. Но WRK-009 продолжает считаться running;
есть и созданные незавершённые Work. Родителю повторно выдавались инструкции ожидания.

`flowForwarder` передаёт прежде всего tool_call с dd-flow, а не любой terminal
исход дочерней сессии. `driveFanout` опирается на works.running. Нет общей сверки
«задача ↔ назначенный исполнитель ↔ подтверждённый исход его запуска».

**Исправление:** перед ожиданием/новой волной сверять известные Work с нативным
деревом. Явный failed/cancelled дочернего запуска регистрировать и сообщать
координатору; отсутствие наблюдения не считать failure. Успешное завершение
Turn тоже не подменяет `work finish`. Если Turn завершён без завершения Work —
нужна явная продолжимая ситуация, а не бесконечное ожидание. Применить ко всем
адаптерам, включая сбой до первого `work start`.

Почему сам native ZCode оборвал именно эти запросы по неактивности, полностью
не установлено: сохранён terminal reason, но он не доказывает зависание модели.
Не выдавать родительские опросы или повторный статус tool за активность ребёнка.

## 6. ZCode принимает неуспешное окончание ACP-запроса как обычный результат

**Подтверждено receipt.** Запрос 15:08:57 вернул
`turn.stopReason: max_turn_requests`, состояние root running, детей running нет.
Он записан как completed. Следующий prompt в 15:28 получил tree_not_settled.

`promptSessionWithBridge` возвращает turn, не разбирая stopReason;
`productive` считает active_tree по дочерним сессиям, не учитывая root.
`requireSettled` затем отдельно проверяет root. Это разные определения завершения.

В текущем `zcode-acp/src/handlers/session.ts:runEventTurn` есть отдельный
120-секундный таймер, после которого вызывается stopBackendTurn и сразу
возвращается max_turn_requests. Подтверждения остановки перед этим ответом нет.
Этот путь объясняет наблюдаемое сочетание, но причину конкретного истечения
native/bridge таймера следует уточнять по нижележащему журналу, а не угадывать.

**Исправление:** нормализовать stopReason и последующее settlement. Ответ RPC
не равен успешному Turn, остановка не равна подтверждению её завершения.
Согласовать stop/inspect/prompt/daemon stop, сохранять причину и root/children
в error details. При неизвестном исходе только наблюдение и reconcile, не новый prompt.

## 7. Таймауты и признаки активности расходятся между слоями

В dd-eval есть ObservationClock, различающий наблюдаемое бездействие и разрыв
наблюдения. Но у zcode-acp собственный Date.now-таймер; у native subagent свой
600000ms watchdog. В `isProductiveSessionNotification` почти любое обновление
кроме heartbeat обновляет активность, даже повторное состояние. AGY также
markActivity на каждом provider event; это не всегда прогресс конкретной работы.

**Исправление:** единый смысл сигналов, но не обязательная общая библиотека для
разных проектов: real progress, provider liveness, observation gap, terminal.
Не продлевать таймер исполнения ребёнка родительским polling. Не останавливать
агента только из-за задержки вывода или разрыва часов. Настройки внешнего
раннера не должны обещать поведение, которое опровергает внутренний watchdog.

## 8. AGY recovery отменяет другую сессию

**Подтверждено.** В events.jsonl:

- 13:58:38 — `agy_provider_failed`, original session
  `e106ee52-6f3d-4b13-816f-3baf5f44abdb`;
- 14:00:45 — cancel_requested именно этой сессии;
- 14:00:59 — cancellation receipt для
  `e9a788f9-a44c-4c57-905f-8e7c9d43911c`, новая сессия с нулевой работой.

`withExecutionDaemon` при недоступном primary стартует recovery daemon.
AGY daemon при старте создаёт новую provider-сессию. В dispatch session.cancel
и session.inspect не проверяется запрошенный Session ID; prompt проверяет.
session.resume тоже может вернуть уже запущенную сессию через ранний return start().

**Исправление:** общий guard идентичности для каждого session-targeted вызова.
Recovery обязан реально восстановить оригинал либо сообщить невозможность;
создать новый daemon недостаточно. Runner дополнительно проверяет native ID
и harness в подтверждении. Отмена терминального прогона не должна создавать сессию.

## 9. Cleanup меняет причину результата и оставляет сиротский демон

AGY сначала completed_with_failures, затем cancelled. `storedExecutionResults`
при отсутствии успешного launch result выбирает наличие cancellation event;
исходный failed launch не сохраняется как приоритетный результат этого пути.
`runnerCancel` не отсекает уже терминальные execution.

Для ZCode daemon stop отказал из-за root running. На момент аудита записанный
PID 40856 существует, parent PID 1; daemon.json всё ещё active_tree=true.
Это подтверждает оставшийся процесс, но не доказывает полезную активность модели.
В рамках расследования процесс не останавливался.

**Исправление:** исход выполнения и очистка ресурсов независимы. Сохранить
первую доказанную причину failure, а последующий stop записывать как cleanup.
Не считать неотвечающий socket разрешением подменить владельца. Завершение
наблюдения должно оставлять владельца дальнейшего наблюдения/уборки через
имеющийся managed-process реестр; подтверждённую активную работу не убивать
лишь ради зелёного cleanup. Протестировать остановку после failure, при
живом root, при мёртвом socket и при уже завершённом provider.

## 10. Счётчики инструментов передаются в разных единицах

**Подтверждено кодом и receipts.** ZCode отправляет `toolSummarySince(toolCursor)`
за один prompt, а CLI `readHarnessToolCallsWindow` вычитает эти значения как
накопительные снимки физической Session. В сохранённых receipts встречаются
244 вызова за один prompt, затем 12, затем 1; это не монотонный счётчик.
`Math.max(0, delta)` скрывает несовместимость вместо корректного учёта.

AGY считает terminal step updates без dedup по ID шага; повторный DONE способен
удвоить tools. Это найденный по коду риск, а не доказанная величина завышения
этого прогона. Grok уже имеет механизм накопления per-session tool counters —
его следует использовать как существующий образец, а не плодить иной контракт.

**Исправление:** явная одинаковая семантика накопительных counters по native
Session, уникальные tool IDs, сохранение baseline при восстановлении. Отдельно
неизвестное usage, root и дочерние сессии. Не заменять провалы импорта нулём.
Точное количество потерянных tools сейчас не объявляется установленным.

## 11. Одинаковые проверки повторяются на одном интегрированном состоянии

MERGE RCP-008 и RCP-011 — `pnpm quality`; RCP-009 и RCP-012 — `pnpm docs:check`.
Дерево совпадает. Второй quality занял около 149 секунд.
`deduplicate` включает run_at в ключ: CODE и MERGE считаются разными группами
даже внутри одного вызова итогового MERGE.

**Исправление:** объединять одинаковое исполнение внутри конкретного
интеграционного gate при совпадении команды, cwd, среды, ресурсов, артефактов и
проверяемого состояния; receipt покрывает несколько обязательств. Не объединять
лишь по строке команды и не переиспользовать feature-branch receipt на другом
интегрированном дереве. Это оптимизация, не причина неуспеха данного MERGE.

## 12. Неполные прогоны теряют штатный разбор и полноту доказательств

`captureExecutionCandidate` вызывается после успешного терминального stage.
Если candidate.json отсутствует, evalJudge возвращает
`not_run_incomplete_execution`. Большая часть выполненных стадий остаётся без
штатной итоговой оценки. Boundary event содержит stage/run_id, но сам по себе
не является снимком исходников и артефактов на этой границе.

**Исправление:** итоговый evidence bundle создавать при любом исходе с явным
описанием реально достигнутой границы, причин остановки, receipt/log/session IDs
и доступного usage. Judge оценивает выполненную часть и отказы; не получает
выдуманный успешный terminal candidate. Использовать существующую методику и
форму отчёта, не вводить дополнительную классификацию эвалов. Если заявляем
сохранение состояния стадии, сохранять настоящий snapshot, а не только событие.

## Содержательная работа и границы доказанности

PLAN-REVIEW ZCode нашёл реальные проблемы: разделение БД reset/seed и API,
неучтённые изменения seed, несогласованность сортировки после обновления,
ложное обещание доказательства миграции на пустой БД, несовместимость archived
priority-only API с обычным UI PATCH. Нельзя считать review пустой формальностью.
Часть замечаний трактует planned_write_areas как запрет, хотя worker prompt
объявляет их мягкими координационными подсказками: это надо проверять отдельно
при оценке обоснованности замечаний, а не усиливать ограничения записи.

У Luna review привёл к исправлению реальной гонки lifecycle/priority; одновременно
test-entrypoint defect из пункта 2 дошёл до MERGE. Общий урок для промптов:
проверять причинную связь «обязательство → изменённый путь → исполняемая проверка
→ подготовленная среда → результат», а не добавлять матрицу ради матрицы.
Не делать семантические выводы CLI по ключевым словам в коде/логе.

Не установлены полностью: первопричина native ZCode inactivity,
первопричина AGY stream interruption (провайдер/транспорт/хост), истинная доля
ненаблюдаемого времени и точное полное usage всех дочерних сессий. Перерыв
наблюдения не объявляется доказанным сном компьютера или зависанием модели.

## Последовательность исправлений и регрессии

1. **Идентичность и результат:** исправить AGY target guard, recovery attach,
   сохранение failed при cleanup. Тесты: ошибочный native ID, terminal cancel,
   daemon recreation, late result, повтор inspect без новых сессий.
2. **Единый переход/settlement:** обработчик разрешённого next action для
   normal/recovery/reference/server, нормализация native stop reasons,
   reconciliation дочерних исполнителей и Work. Тесты: MERGE→CODE repair,
   child failed before/after work start, normal end без work finish,
   max_turn_requests + running root, отсутствие duplicate prompt.
3. **Доказательства попыток:** общий перенос и разрешение путей; тест чтения
   receipt/logs нового repair после архива и после процесса-restart.
   Проверить сбои между abortIntegration, failWork, archive и созданием repair:
   текущая последовательность многосоставная, её восстановление должно быть
   явным, без повторных необратимых операций.
4. **Замкнутый repair:** причинная самопроверка repair, затем итоговый gate;
   регрессия с повторным formatter failure должна оставлять текущий repair
   открытым, не производить цепочку новых Work. На MERGE различать агентным
   решением дефект исходников и поломку среды; не принуждать любое падение к
   изменению продукта. Повтор после восстановления среды должен быть доступен
   без фиктивного изменения Git fingerprint.
5. **Промпты и критерии:** явная ответственность PLAN/CODE/REVIEW за окружение
   проверки и тестовые entrypoints; одинаковая семантика soft boundaries;
   точные инструкции на все исходы, не только success.
6. **Наблюдаемость:** counters, terminal failure bundle, независимый cleanup,
   различение фактической активности и наблюдения. Затем оптимизация одинаковых
   MERGE-проверок.
7. **Проверки перед платным E2E:** целевые модульные тесты и сквозные тесты с
   управляемыми фиктивными адаптерами на сбои между компонентами; короткие live
   smoke на повторный prompt/дочерний failure/recovery конкретной упряжки.
   Новый E2E — отдельный запуск после реализации, без правки результатов этих RUN.
