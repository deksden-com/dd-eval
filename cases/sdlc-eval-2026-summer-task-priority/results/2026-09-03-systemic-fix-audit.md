# Повторная проверка системности исправлений — 2026-09-03

## Вывод

Пакет **не готов к объявлению полностью исправленным**. Он устраняет часть
первопричин, но некоторые изменения защищают только обычный путь исполнения.
Остались расхождения на границах принятия результата, восстановления после

Это аудит текущего кода, а не новая оценка качества моделей. Старые E2E не
переписывались. Платные сессии, продуктовые базы и исторические доказательства
при проверке не менялись. Наличие канонических пакетов **не является** условием
запуска E2E: препятствия ниже относятся к реализации раннера/движка.

Проверены рабочие копии:

- `dd-flow-cli`: HEAD `aab3af0`, версия `0.9.0-beta.5`, включая незакоммиченные
  изменения semantic CODE repair;
- `dd-eval`: HEAD `e0b8d85`, включая изменения ACP error details, ожидания

- `dd-memorybank`: текущие соответствующие изменения CODE prompt и схемы.

## Что действительно улучшено

1. Проверка ссылок и назначенных аспектов PLAN/CODE reviewer перенесена перед
   сохранением `works.result`. Синтаксически неправильный результат можно
   исправить, пока Work ещё выполняется. Проверены общие валидаторы в
   `work-registry.ts`, а не только текст промптов.
2. Восстановление repair-деклараций опирается на исходный CODE-граф, а не только
   на непосредственного предшественника. Это исправляет потерю допустимых
   проверок при последовательных исправлениях разных ошибок.
3. Квитанция проверки резервируется до запуска процесса. Появился атомарно
   записываемый `completion.json`; при его отсутствии успех не угадывается.
4. Внутренние ключи Session отделены от native ID. Новые проекции RUN/Work/usage
   используют общую функцию публичной идентичности. Однако перенос не завершён.
5. ACP сохраняет сведения провайдера, включая `error.data.message`. Этот
   конкретный дополнительный формат теперь проверен отдельным тестом.
6. `daemon stop` ждёт исчезновения сокета после предварительного ответа. Новый
   тест различает получение подтверждения и фактическое закрытие сокета.
7. Обычное чтение проектного worktree под `DD_FLOW_HOME/projects` больше не
   считается нарушением только из-за общего префикса пути.

## Оставшиеся дефекты и первопричины

### 1. Поздняя проверка reviewer-результата осталась — только другого вида

**Подтверждено кодом.** `work-registry.ts:321–378` проверяет идентификаторы,
аспекты и ссылки; `code-review-result.schema.json` допускает `blocked` и не
запрещает сочетание `pass` с непустыми findings. Затем
`vnext-code-review.ts:212` отклоняет такие результаты уже при завершении стадии.
Эти проверки зависят только от самого reviewer-результата, а не от решения
оркестратора. Называть их проверками агрегирования неправильно.

Следствие: reviewer Work может стать completed, а CODE-REVIEW — не завершаться
из-за заведомо неприемлемого принятого результата. Повтор finish этого Work
отклоняется по состоянию. Это тот же класс ошибки, что ранее был со ссылками.

**Исправление:** все локальные условия принятия перенести в один валидатор
до фиксации Work. На агрегировании оставить отношения между несколькими
результатами/решениями. Для blocked явно выбрать существующий путь pause/block,
не завершать работу, которую затем потребуется дополнять. Не переносить это
правило вслепую на PLAN: там blocked reviewer-вывод используется иначе.

### 2. Автоматический CODE repair смешивает исправление с блокировкой

**Подтверждено кодом и частично воспроизведено.** В
`vnext-code.ts:192–204` любое `verdict !== passed` создаёт repair Work.
В `code-verification@2` есть отдельный `blocked`. Отсутствие внешнего доступа,
необходимость решения пользователя и реализуемый дефект тем самым получают
одинаковый выход.

Дополнительно `selectRepairChecks` переводит весь набор semantic checks,
включая общепроектные проверки, в `run_at: work`. Проверка воспроизводит
`code → work`. Решение PLAN о размещении проверки теряется; при нескольких
ремонтах тяжёлый общий gate будет выполняться внутри Work и снова в финале.
Проверки merge/release в этот конкретный semantic путь не попадают:
`finalCodeCheckDeclarations` фильтрует их — это проверено по вызывающему коду.

Промпт обещает «immutable verification file», но читается обычный файл по
переданному пути, который следующий finish предполагает обновить. В payload
копируются unresolved/summary, но полный исходный документ не замораживается.
Также полный список checks может оказаться пустым для внешних доказательств,
тогда регистрация repair отвергается общим требованием непустого массива.

**Исправление:** явное разветвление `passed / needs_repair / blocked`;
противоречивый passed+unresolved отклонять до побочных эффектов. Использовать
существующую pause/block-модель и возвращать точные команды продолжения.
Сохранять размещение проверок; узкую причинную проверку выбирает агент из
доступных деклараций, общий gate остаётся у стадии. Контекст repair копировать
в его существующие артефакты, не обещать неизменность изменяемого файла.
Создание repair по одному принятому входу должно быть защищено от конкуренции.

### 3. Окно между резервированием проверки и подтверждением PID не защищено

**Воспроизведено.** Два конкурентных `runCodeChecks` с одинаковым входом дали:

```text
первый вызов:  RUN-AUDIT/RCP-001 → aborted
второй вызов:  RUN-AUDIT/RCP-002 → passed
check_in_progress: ни у одного вызова
```

Это не доказательство двух полных запусков shell-команды: первый процесс может
быть остановлен до выполнения полезной части. Доказан более ранний дефект:
второй caller ошибочно объявляет живую стартующую попытку оборванной.

Причина: `reconcileUnfinishedChecks` требует одновременно активного состояния
и живого PID. У записи starting PID ещё нет. Резервирование номера в
`BEGIN IMMEDIATE` не защищает от этого; новый caller портит первый запуск.
Общий путь используется Work finish, CODE и CODE-REVIEW; локальный lock CODE
не заменяет защиту нижнего уровня.

**Исправление:** активное владение starting с действующим сроком не считать
смертью процесса. Резервировать именно выполнение по его ключу, а не только
следующий номер receipt. Повтор возвращает locator/progress уже имеющейся
попытки. После потери владельца — безопасное восстановление, а не второй spawn.

### 4. Процессные сроки владения не подключены ко всему жизненному циклу

**Подтверждено кодом.** `code-checks.ts` регистрирует и подтверждает процесс,
но не вызывает `heartbeatManagedProcess`. Скользящее окно вывода shell
обновляется, срок владения процессом в БД — нет. Через 15 минут живой
производительный check становится кандидатом уборщика.

У ZCode срок 5 минут продлевается из `DaemonRuntime.persist`; получение
`daemon.status` и обычные уведомления ACP сами по себе persist не вызывают.
Длинная productive operation не получает гарантированного продления lease
по активности. При отсутствии уборщика это остаётся невидимым дефектом.

**Исправление:** инфраструктурное продление владения на всём интервале
исполнения, независимо от пользовательского progress. Привязать его к живому
контроллеру/операции; не давать брошенному daemon бесконечно продлевать себя.
Потеря lease — явный исход, а не проглоченная ошибка. Проверить длинный ход,
молчаливую команду, смерть контроллера и конкурирующую уборку.

### 5. Уборщик не завершает дерево и не восстанавливает собственную уборку

**Воспроизведено на временных процессах и БД.**

- `reconcileExpiredManagedProcesses` отправляет сигнал одному положительному
  PID. После остановки тестового родителя дочерний процесс остался жив.
  В конце аудита он принудительно убран в собственной тестовой process group.
- После claim состояние становится orphaned, но следующий claim выбирает
  только starting/running/stopping. Если уборщик упал или получил kill_failed,
  запись больше не будет подхвачена следующим уборщиком.
- `finishManagedProcess` не освобождает связанные `managed_resources`.
  При утрате исходного caller исчезает и возможность вызвать его
  `allocation.release()`. Тест после terminal процесса находит оставшийся порт.

`processIsAlive` при отсутствующем pid_started_at допускает PID-only проверку;
уборщик в таком случае не имеет достаточного доказательства против PID reuse.
Это дополнительный риск из кода, не воспроизведённый на чужих процессах.

**Исправление:** хранить и проверять принадлежащую операции process group/tree;
останавливать её и подтверждать остановку до terminal/release. Для уборки
также нужен срок владения и повторный claim. Освобождать ресурсы по тому же
владельцу после подтверждённой остановки; без проверки идентичности PID —
диагностировать, не убивать произвольный процесс.

### 6. completion marker ещё не делает проверку полностью независимой от CLI

**Подтверждено кодом; реальное убийство check-клиента в этом аудите не выполнено.**
Shell detached, но stdout/stderr по-прежнему идут через pipe родительского
Node CLI и только им пишутся в файлы. Потеря клиента означает потерю канала
логирования; возможны EPIPE/SIGPIPE. Тест восстановления сейчас создаёт готовый
completion.json вручную — он проверяет чтение маркера, а не выживание команды.

Маркер хранит только exit_code. При восстановлении finished_at берётся из
текущего времени, а не из времени реального завершения проверки. Кроме того,
trap EXIT объявлен в той же shell, что и пользовательская команда: команда
может заменить trap или использовать exec и лишить систему маркера.

**Исправление:** маленькая независимая оболочка исполнения, существующий
receipt/completion как хранение, прямые файловые дескрипторы для логов.
Сохранять фактическое время и код выхода. Проверять падение caller настоящим
тестовым процессом, а не только подготовленным JSON. Новый постоянный сервис
для этого не нужен.

### 7. Проверка обхода CLI остаётся неточным анализом строк

**Воспроизведено.** `runtimeIntegrityViolation`:

- пропускает явную запись Python в engine;
- пропускает `sqlite3 <runtime>/db.sqlite UPDATE ...`;
- пропускает private bin invocation, если в той же строке упомянут public CLI;
- отклоняет копирование engine-файла наружу для чтения.

`collectCommands` собирает только строковые поля command. Изменения через
файловые инструменты и полнота дочерних журналов этим не обеспечены.

**Исправление:** не объявлять нарушение по имени утилиты. Использовать
структурированные операции/пути, различать агентские drafts и принятые
служебные данные. Для неизменяемого engine использовать уже имеющиеся
контрольные суммы. Неизвестную семантику скрипта отмечать как ограничение
доказательства для Judge, а не автоматически обвинять модель или объявлять
полную проверку успешной. Это аудит, не попытка построить security sandbox.

### 8. Одинаковая финализация отчёта не означает одинаковое принятие результата

**Подтверждено кодом.** В `runner.mjs` аудит вызывается на обычном пути перед
`captureCandidate` (~2141). Восстановление (~2241) и server MERGE (~2038)
сразу вызывают capture без него. Ошибочный запуск также не получает такого
аудита. Общая `finalizeRunProjection` вызывается уже после этой развилки.

**Исправление:** один общий путь принятия candidate: собрать все журналы,
провести аудит, сохранить доступную статистику, зафиксировать snapshot,
сформировать итог. Вызывать его из normal/recovery/server; восстановление не
должно позволять принять результат по более слабому набору правил.

### 9. Публичная идентичность сессий перенесена не во все API

**Воспроизведено полным Vitest suite.**
`test/run-cli.test.ts:5660` ожидает native `session-file-payload`, получает
внутренний `SES-e10e8e74a0e5e98ea8638447`.

Это не повод переписать expected под SES. `sessions.ts:187–255` возвращает
сырой DB record из register/status/stop; новые проекции в других местах
используют publicSessionIdentity. `merge-worker.ts` тоже возвращает такой
record. Помимо несовпадающих названий, клиенты получают два разных смысла
поля session_id. Публичные lookup-команды также надо сверить с парой harness/ID.

**Исправление:** общая сериализация на внешней границе и явное разрешение
публичной пары в storage key. Внутренние SQL-связи не переименовывать обратно.
Проверить все команды и их потребителей одним контрактным набором, включая
совпадающие native ID разных упряжек. Не исправлять тест ослаблением проверки.

### 10. Схемы, ручные валидаторы и генерируемые payload расходятся

**Подтверждено кодом.** CLI code-work-batch допускает `check.ports`, копия
в memorybank — нет. Генератор repair пишет `review_check_refs`, но обе
repair-схемы с additionalProperties:false этого поля не описывают. С другой
стороны, `addWorkBatch` опирается на облегчённый validateItem, поэтому успешная
регистрация не доказывает соответствие объявленной JSON Schema.

**Исправление:** проверять реальные генерируемые payload по схеме выбранной
пары; синхронизировать копии автоматически/проверкой равенства. Не вводить
ещё одну схему на каждый исправленный кейс. В тесте должен участвовать
генератор → сериализация → фактическая Schema, а не только ручной объект.

### 11. Неуспех по-прежнему обедняет статистику и объяснение Judge

**Подтверждено кодом.** Обычная ветка catch возвращает code/error/time, тогда
как сбор statistics стоит после успешной проверки стадии. Final Judge
запускается только если все результаты candidate_ready. В Markdown при
отсутствии judge пишется `not requested`, даже когда он был запрошен, но
заблокирован неполным исполнением. Это противоречит §11 спецификации 019.

**Исправление:** в общем финализаторе собирать доступные метрики и доказательства
для terminal success/failure/cancel. Отдельно сообщать, почему оценка не
запущена. Неполный прогон можно оценить по доступным стадиям без объявления
его успешным. Не заменять это второй классификацией эвалов.

### 12. Область гарантированной очистки начинается после запуска daemon

**Подтверждено кодом.** В `runner.mjs:2042` последовательно выполняются
daemon start, doctor, проверка профиля, session create, проверка её профиля
и запись события. `try/finally` с daemon stop начинается только после них.
Ошибка любого из этих предварительных шагов оставляет запущенный daemon.
Сохранение первичной ошибки в более позднем finally этого окна не закрывает.

В `DaemonRuntime.shutdown` закрытие bridge предшествует обновлению состояния
и закрытию server/socket. Если bridge.close бросает исключение после flush,
последующие шаги не гарантированы. Это тот же класс дефекта: очистка охватывает
не весь приобретённый ресурс, а только успешную часть жизненного цикла.

**Исправление:** scope владения начинается с первой попытки приобретения
ресурса; idempotent cleanup в finally охватывает preflight/create/prompt.
Шаги shutdown выполняются независимо с сохранением первичной и вторичных
ошибок; terminal clean допустим только после подтверждения остановки.
Проверить fault injection после каждого шага, не только после prompt.

## Дополнительные связанные ограничения

- `unchangedFinalGateFailures` всё ещё связывает возможность повтора только
  с fingerprint файлов. Исправленная среда/доступность внешней зависимости
  без Git-изменения не даёт штатного повторного запуска. Не нужен бесконтрольный
  retry: нужен явно зарегистрированный мотивированный новый check attempt.
- `AcpBridge.providerErrors` живёт дольше одного запроса. Воспроизведение:
  первая ошибка 402 → следующая Invalid prompt тоже provider_quota_exhausted.
  Сведения об ошибке должны принадлежать запросу/ходу, а не всей сессии.
- Событие `_x.ai/session_notification` учитывается при получении ошибки,
  но не при продлении sessionActivity. Один нативный поток интерпретируется
  разными подсистемами по-разному. Нужна общая нормализация известных событий,
  с сохранением сырого журнала. Не считать служебный heartbeat доказательством
  активности модели.
- `AcpBridge.close` после SIGTERM не ждёт подтверждённого завершения и не
  обеспечивает остановку всего дерева. Ожидание сокета daemon исправляет
  гонку клиента, но не подменяет управление дочерними процессами.

## Что не подтверждено и не включено в список дефектов

Прямой вызов `selectRepairChecks` способен перенести external в work, но
штатный `addVnextCodeReviewRepair` заранее отфильтровывает external. Поэтому
это **не** объявлено воспроизведённой ошибкой запуска `manual://` в shell.
Аналогично не заявляется, что каждая daemon lease обязательно протухает:
частые productive/persist вызовы могут маскировать отсутствие продления.

исполняемыми файлами (это не зелёные тесты и не пропуски):

```sh
# из dd-eval; без провайдеров, команды анализируются только как текст
node tools/audit-runtime-fix-boundaries.mjs

# из dd-flow-cli; временная БД, короткая команда и собственная process group
pnpm build
node tools/audit-runtime-fix-boundaries.mjs
```

Оба audit-вызова сейчас возвращают exit 1 и JSON с expected/actual. Их задача —
дать проверяемые критерии следующему исправлению. Они не заменяют полный suite.
Временные процессы/каталоги этих воспроизведений очищаются самим тестом;
исторические E2E и их runtime не затрагиваются.

## Минимальный следующий пакет

1. Свести локальное принятие результата и исходы blocked/repair к одному
   контракту; исправить публичные Session API и проверку схем генератора.
2. Доделать одну подсистему исполнения проверок: резервирование операции,
   starting lease, независимые логи/completion, действительное время, retry.
3. Замкнуть владение ресурсами: cleanup уже с начала запуска daemon,
   heartbeat, подтверждённая остановка дерева, повторная уборка orphaned,
   освобождение портов, независимые шаги shutdown при ошибках.
4. Общий приём candidate и сбор метрик во всех ветках; корректный аудит
   публичной границы и причина отсутствия Judge.
5. Нормализовать события ACP и привязать ошибки к конкретному запросу.
6. Добиться прохождения воспроизведений и полного suite, затем выпускать
   согласованную пару, выполнить AGY adapter smoke и провести один E2E через
   AGY. Luna, Grok и ZCode остаются отдельным будущим сравнительным набором.
   Канонические пакеты
   остаются независимой работой, а не блокирующим предварительным этапом.

Новых планировщиков, DSL и постоянных сервисов этот пакет не требует.
По ponytail исправлять следует общие точки жизненного цикла, а не добавлять
ещё по условию в каждый из normal/recovery/server-путей.
