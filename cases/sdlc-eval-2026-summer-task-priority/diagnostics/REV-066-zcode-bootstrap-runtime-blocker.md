# REV-066 · ZCode bootstrap runtime blocker

## Observed run

- Pair: `cp-042-zcode-sequential-code-beta-121`.
- Harness: `zcode-acp`; provider `builtin:zai-coding-plan`; model `GLM-5.3-Flash`, reasoning `high`.
- Root provider Session: `sess_ed70c98c-11ed-4361-9a07-da949f68c26f`.
- Adapter Session: `f6286d9b-2ae1-4df4-b57f-6292ecc84242`.
- Canonical runtime: `REV-066/harnesses/zcode-acp/canonical/workspace/runtime`.

The ordinary user request correctly led the subject to the SPECIFY bootstrap.
It then guessed `DD_FLOW_HOME="$HOME/.dd-flow"` because no exact eval runtime was
present in its initial context. The ZCode lifecycle hook was forwarded into the
isolated eval runtime, while the actual `dd-flow stage start` command targeted
the home runtime. The command therefore failed closed with
`trusted_session_binding_required`.

The subject could not infer the isolated runtime from that error and began
searching for hooks under `~/.zcode`. This is an expected consequence of a
missing deterministic input, not a model-reasoning failure.

## Root cause

`dd-zcode daemon start --dd-flow-home` configures lifecycle forwarding, but the
fresh subject message contains neither that home nor an exact bootstrap command.
The process environment alone is insufficient: a subject may explicitly set
`DD_FLOW_HOME`, and the existing generic project documentation legitimately
mentions the normal `~/.dd-flow` location.

## Required correction

Before an agent receives the ordinary user message, the ZCode harness must add
one small execution envelope containing the evaluated project root, the
isolated `DD_FLOW_HOME`, and the exact standalone SPECIFY bootstrap command.
It must state that these runtime coordinates are authoritative for this turn,
that the command is the first lifecycle action, and that the agent must not
search for or configure hooks. The user request itself remains unchanged.

The envelope is harness-owned operational context, not an evaluation hint. It
is required for any isolated `DD_FLOW_HOME` execution and must be generated by
`dd-eval`/`dd-zcode`, not hand-authored per case.

## Additional shutdown defect

After `session cancel`, the root provider Session still reported `running` with
no active tool and `dd-zcode daemon stop --cancel-tree` returned
`tree_not_settled` after its fixed five-second wait. The invalid run must be
terminated by its exact daemon PID. This is a second harness defect: terminal
root cancellation needs a bounded completion acknowledgement, rather than
leaving an irrecoverable productive operation in the daemon.
