## 3. Исправления, уже намеченные и дополненные аудитом

### M1. Grok: физический источник модели, не догадка о наследовании

**Причина.** `Runtime.recordDescendant` в `dd-grok-daemon.mjs` сохраняет child/parent/attempt/status, но выбрасывает `update.model`. Общий ACP `observeModelUpdate` в `dd-zcode.mjs` обрабатывает лишь `config_option_update`. `dd-grok.mjs` затем спрашивает `x.ai/session/info`, которое для не-резидентного child может вернуть `{}` (см. `grok-build/crates/codegen/xai-grok-shell/src/agent/handlers/session.rs`). Все 15 `subagent_spawned` в owned journals CP-173 содержат child ID, parent ID, attempt ID и `model: grok-4.7`. `initialize.modelState` описывает соединение до `session/new`, а не фактически выбранную модель нового root.

**Изменение и порядок обработки.** В Grok-specific обработчике native spawn сохранять model как **configured model конкретного child/attempt**, не как доказательство модели каждого ответа. Обрабатывать полную identity `{harness, child_session_id, parent_session_id, attempt_id, parent_prompt_id}`. Сначала проверить parent/attempt и retired-attempt правила, затем обновлять registry/profile и записывать `observeModel` с `source: {channel: "x.ai/subagent_spawned", event_sha256: hash(normalized_spawn)}`. Hash включает identity, model и native event identity/timestamp, если они есть; локальное время получения не делает replay новым фактом. Одинаковые payload повторного attempt не схлопываются с предыдущим attempt.

`recordDescendant`, `track`, `observeSubagentEvent` сейчас синхронные; не добавлять туда забытый Promise. Использовать существующую последовательную notification queue ACP bridge: валидированный переход возвращает fact, async notification handler ожидает его запись, `flush()` ожидает очередь. `track` и другие callers не начинают тайно I/O. На поддерживаемом retained-daemon resume восстановить known configured profiles из owned model journal для удержанных Sessions; это не разрешение обходить crash/recovery guards. Если durable запись не состоялась, observation failure остаётся в diagnostics/completeness; primary native failure не заменяется ошибкой наблюдателя. Не делать дополнительный native RPC/долгое сканирование в синхронном hook path.

`initialize.modelState` остаётся connection diagnostic вне Session attribution. `session/info` является новым model fact только когда ответ сам содержит model; `{}` не стирает spawn fact, но не является подтверждением текущего response model. Не копировать requested/root model на child. Root без собственного source остаётся unknown. Grok Build не меняется.

**Контракт общего reducer.** Исправить обе копии — `dd-flow/src/harness-runtime/lib/model-observations.mjs` и `dd-eval/lib/model-observations.mjs` — и одинаковые contract vectors. Не создавать ради этого общий npm-пакет. Различать scope configured Session/attempt, response Turn и connection; сохранять capability/unknown там, где native API не даёт response attribution. Unavailable с последующим подтверждением **того же scope** закрывается; недоступный поздний inspect не уничтожает прежний configured fact, но пропавший новый Turn/attempt остаётся gap. Неизвестный scope в legacy records нельзя считать автоматически закрытым. Законная последовательная смена модели — `model_changed`, а не conflict; конфликт — несовместимые утверждения об одном scope/identity без порядка, позволяющего объяснить смену. Разные channels/evidence classes не дают ложных переходов. Expected Session inventory должен выявлять полностью отсутствующий model stream; поздняя parent/requested metadata не теряется из-за выбора первого события. Токены по моделям не распределять по configured profile: сохраняется `session_totals_unattributed_to_model`, пока нет native per-response proof.

dd-eval `resolveEvidenceJournals` должен считать полноту по покрытию Sessions/facts, а не по наличию model-sidecar у **каждого** tool journal. Недоступный необязательный transcript не ухудшает уже полное owned coverage; реально недостающий scope, parse/observation error ухудшает. Старые frozen candidate/Judge packets не пересчитывать.

**Проверки.** Spawn CP-173 с 15 children; нет model; `{}` inspect; known→unavailable в том же scope; unknown новый attempt/Turn; позднее подтверждение; законная смена модели и конфликт одного scope; parent conflict; retired attempt без побочного обновления profile; одинаковый event повторно и новый attempt с тем же model; orderly resume и corrupt/partial journal; native failure + observer failure сохраняют primary error. Connection 4.6 + root info 4.7 не создаёт Session transition. В обеих репах одинаковый input даёт одинаковый summary; полностью отсутствующий child и missing sidecar необязательного tool source дают разные результаты. Старые events без scope читаются консервативно, не превращаются в invented response evidence.

### T1. Codex/Luna: owned app-server events как основной tool receipt

**Причина.** `codexToolObservation` понимает rollout `response_item`, но managed `adapter.events.jsonl` содержит `payload.method=item/started|item/completed` с `params.threadId` и `item.id/type/status/exitCode`. Codex home намеренно линкует `sessions` во внешний home (`hooks.ts:codexHomeSharedEntries`), а `run-observations.ts` и dd-eval realpath guards закономерно отвергают его как RUN-owned evidence. В CP-175 семь root journals доступны, а 15 child thread events есть внутри них.

**Decoder.** Расширить существующий `replayToolJournal` app-server формой, сохранить rollout decoder и один reducer. Физическая identity — `params.threadId`, Turn — `params.turnId`, call — `item.id`, source family/epoch — native, а не имя файла. Вся пара start/terminal и повтор события дедуплицируются в одном scope. Collab call принадлежит sender, а не receiver; чужой thread отфильтровывается по RUN inventory до суммирования. Для ACP sibling path проверить использование `params.sessionId`, чтобы child event в root journal не приписать root. При отсутствии доказанной native identity не подставлять root из пути файла. Валидационные gaps тоже должны иметь scope: чужая Session не портит текущий RUN, ошибка чтения выбранного общего журнала — портит.

**Terminal semantics по исходникам Codex.** `codex-rs/app-server-protocol/src/protocol/v2/item.rs`: command/fileChange имеют `inProgress/completed/failed/declined`; collab — также `interrupted` вместо declined; MCP/dynamic — `inProgress/completed/failed`. Declined/interrupted — settled non-success с сохранённым native reason, не pending и не successful execution. Native failed/ненулевой exit/structured error побеждают optimistic completed; противоречие фиксируется gap. `exitCode:null` само по себе не равно нулю. Успешный collab spawn/wait не доказывает успех child Work. Не классифицировать произвольное слово/JSON-поле `error` внутри tool content как protocol failure.

Нужна явная таблица известных item types: command, fileChange, collab, MCP, dynamic, webSearch/imageView/imageGeneration/sleep — tool forms с доступной для каждого типа полнотой outcome; user/agent message, reasoning, plan, subAgentActivity, review markers, compaction/hook prompt — не самостоятельные tool calls. `functionCallOutput` — evidence результата, не ещё один вызов. Не считать произвольный неизвестный item успешным tool и не молча объявлять coverage complete: unknown type/status сохраняет scoped unsupported gap. Источники локального Codex отражают текущий протокол, поэтому shape tests привязать также к версии реально квалифицированного binary; не требовать от старого binary новых полей.

**Покрытие и source selection.** Сначала replay всех owned managed journals, затем вычислить покрытые физические Sessions/Turns, только после этого выбрать допустимый transcript fallback. Предпочитать managed app-server для покрытого scope. Не складывать его с rollout без доказанного mapping call IDs: если mapping отсутствует, использовать один источник для целой Session, второй оставить diagnostics; для неполного основного источника явно показать partial, не выдавать union разных IDs за полный счёт. Source selection детерминирован при повторном status и inherited journals. Optional отвергнутый fallback не становится gap при полном основном source. Token usage из legacy rollout сохранить отдельно.

Ноль инструментов доказан только для **наблюдённого** завершённого Turn с start/end, корректным parse, поддерживаемыми item types и успешно flushed capture без зарегистрированной потери. Все Turns Session проверяются, а не только первая пара. Turn cancellation/error не превращает unresolved tool в success; terminal без start даёт известный исход при неполном lifecycle. Незавершённый JSON tail активного журнала допускается как pending, повреждённая середина/неполный terminal journal — gap. Отсутствие durable capture proof означает partial, даже при наличии start/end. Не заявлять математическую без потерь доставку native протокола, если он её не гарантирует.

**Counters и consumers.** Разделить journal locator availability, Session observation coverage, call outcome completeness. `measured/complete` в `run-observations.ts`, `usage.ts` и dd-eval не должны скрывать pending/unknown outcomes. Present-but-partial authoritative inventory не заменять legacy счётчиком, даже при `observed_sessions=0`; отсутствие inventory у старого engine — отдельный compatibility path. Не ослаблять lexical/realpath guards, включая symlink substitution между discovery и чтением. Проверять результат чтения именно выбранного owned source.

**Проверки.** Минимальный table-driven native corpus всех перечисленных status/type ветвей; duplicate start/completed, completed-before-start, reused item ID в другом thread/Turn, sender/receiver mismatch, nested child в root journal, один/несколько no-tool Turns, truncated/invalid/unknown event, interrupted Turn, внешний symlink и foreign Session. Integration через `runObservations` и dd-eval inventory с fallback до/после replay, без double count, без чтения внешнего home и без скрытия partial. В CP-175 подтверждены lifecycle events 22 threads; из 2060 started / 2059 completed незакрытым оказался **reasoning**, не tool. Эти числа не заменяют replay outcome-проверку. Target нового Luna — покрытие фактического inventory, не hardcoded 22/22; other harness regressions проверяют отсутствие изменения их счётчиков.

### A1. ZCode и все harnesses: у acceptance должен быть исполнимый владелец

**Причина.** CP-177 PLAN `DEC-003` прямо переносит verification matrix на «merge/readiness owner», но такого Work в CODE batch нет. `document_updates` назначает P3 лишь обновление SCN-002 до `planned`; текст сценария говорит вернуть `accepted_local` после fresh readiness evidence. `validatePlanSemantics` проверяет ID owner/AC/check refs, но не запрещает принятие плана с deferred closure без stage/Work. MERGE `mergePrompt` разрешает только разрешение фактических конфликтов, не произвольную правку docs. Поэтому все проверки могли пройти, а durable acceptance осталась незакрытой.

**PLAN ownership.** В общем PLAN-REVIEW проверять смысл каждого отложенного document action: owner, causal checks, момент допустимого изменения. Не парсить `DEC-*` regex и не вводить новый scheduler. Структурные `document_updates.owner`, dependencies и refs сохраняются. Для этого case PLAN назначает CODE owner содержательной приёмки, matrix и scenario; до aggregate evidence этот owner пишет правдивый pending статус, а окончательное закрытие явно входит в семантическую верификацию CODE и при необходимости её repair Work. «Потом сделает MERGE/readiness owner» без исполнимого пути — material finding. Не путать начальный bootstrap `workspace-readiness.json` с проверками новой функции.

**Решение циклической зависимости — один дополнительный исход существующего finish.** В `vnext-code.ts` и CODE verification schema добавить opt-in verdict `needs_checks`: координатор просит выполнить уже объявленные aggregate checks, **не утверждая**, что acceptance-документы завершены. Используется только при доказанной зависимости semantic closure от aggregate evidence; обычный `passed/needs_repair/blocked` путь не получает обязательного лишнего раунда. Новый writer использует `code-verification@3`; reader сохраняет v2 для pinned старых RUN. Обновить type, schema routing, prompt example, template и tests вместе.

Последовательность без нового Stage:

1. Все implementation Work завершены; pending closure обозначен в verification, verdict `needs_checks`. Work, ждущего своего будущего aggregate gate, нет.
2. Штатный `stage finish` валидирует запрос, выполняет существующий `runCodeChecks(scope=aggregate)`. Failure идёт в текущий aggregate repair route. Success возвращает `verification_required`, точные receipts/input fingerprints и **выданную runtime successor finish command**, исполнимую после обновления verification file; Stage остаётся CODE, terminal stage-report/MERGE request не создаются. Это следующий вызов той же операции, а не replay consumed invocation ID. Повтор на неизменном workspace использует штатную receipt reuse policy, не создаёт новый Work.
3. Координатор сопоставляет evidence с AC. Если нужны продуктовые/doc changes — существующий `needs_repair` и **один** fresh child repair Work, не запись в product из coordinator. `prepareVnextCodeRepair` сейчас делает `document_updates: []`: для этого пути переносить конкретные unresolved document obligations и их baselines/check refs из исходного owner, а не все документы проекта. Если изменений не нужно — `passed` с содержательным обоснованием текущих документов.
4. Repair обновляет SCN-002, matrix и curated evidence на основании реально пройденных проверок, с явными proof limits. Finish повторно валидирует semantic result и актуальность checks; stale receipts пересчитываются существующим механизмом. Только после успеха — CODE-REVIEW/MERGE. Повторный запрос с тем же verification/repair identity не порождает duplicate Work; старый ответ после cancel/generation change не принимается.

**Без самоссылочного evidence.** Passport фиксирует выполненные проверки, base commit/workspace и их фактические inputs; не требует hash/commit файла, в который сам записывается. Последний полный tree подтверждается последующими immutable gate receipts и frozen EVAL checkpoint. Passport может ссылаться на предыдущий проход для продуктового контура, но не называть его проверкой изменённого полного tree. Изменение только документа не обязано снова менять ссылки на «самый последний receipt»: final packet содержит цепочку доказательств. `inputs` в check profile остаются причинными; при `inputs=["."]` изменение docs закономерно вызывает повтор, а не глобальное исключение docs из hashing. Нельзя ослаблять mutation guard или запускать aggregate-команду внутри Work вопреки `validateCheckPlacement`.

**Lifecycle/SSOT guard.** Новый nonterminal outcome должен быть явным continuation в общей lifecycle-инструкции `src/harness-runtime/lib/delegation-instructions.mjs`, CLI help и CODE prompt, а не особым указанием для Grok. `src/cli/run-cli.ts` сохраняет successful invocation даже при незавершённом Stage; successor создаётся/связывается штатным invocation machinery. После `verification_required` координатор читает evidence и пишет только stage verification file; fresh child нужен лишь после material `needs_repair`. Проверить hook settlement/controller capture: успешное выполнение команды не означает terminal Stage. Checks/provider/file I/O не перемещать внутрь SQLite transaction; сохранять prepare→short settlement/publication и generation fencing. Это обязательная регрессия против ранее устранённых lock/повторного вызова дефектов 053.

**Границы.** Общие инструкции и finish исходы одинаковы для четырёх harnesses; adapter добавляет лишь transport/delegation детали. MERGE не редактирует docs произвольно; product/doc defect направляется в существующий source CODE repair route. Case receipt E1 ловит оставшийся пропуск, но не подменяет semantic review и не чинит workspace. Паспорт с произвольным фиксированным именем не обязателен: допустим эквивалент с criterion→check→result→proof limit и разрешимыми refs.

**Проверки.** Неисполнимый deferred owner; `needs_checks` при incomplete graph; успешный evidence-only finish без terminal effects; failed gate; повтор запроса и lost response; needs_repair с сохранённым doc owner/baseline; cancel во время checks; stale receipt после docs/code/check-profile изменения; inputs `.` и scoped inputs; отсутствие рекурсии «receipt hash меняет паспорт, паспорт меняет hash». Два прохода с одной doc-only repair должны завершиться, не создавать новую repair только из-за нового receipt ID. Независимый проект без post-check closure идёт прежним коротким путём. Fake harness controller matrix проверяет одинаковый `verification_required → repair → finish` для Grok/Luna/ZCode/AGY до дорогих E2E.

### H1. AGY и любая упряжка: квалификация canonical HITL-ответа

**Причина.** Frozen fixture CP-177/178 не выражала два самостоятельных продуктовых решения. `fixturesValidate` проверяет пакет/blueprint, но не семантическое покрытие ранее встретившихся HITL. `interactionJudgePrompt` требует явного/логически вытекающего ответа, поэтому отказ был правильным.

**Изменение и wiring.** Сохранить CP-179 canonical ответ. Добавить к case definition маленький corpus известных материальных вопросов и **явную отдельную definition qualification** перед scored run, использующую существующие `interactionJudgePrompt`/validator и lifecycle Judge. Это не расширение AGY adapter и не скрытый LLM-вызов из preflight. Qualification создаёт только свои Judge Sessions, имеет bounded timeout/cleanup и различает auth/quota/transport error, invalid Judge output и настоящий fixture gap. Preflight остаётся `provider_sessions_created: 0`; для нового checkpoint этого case он проверяет уже созданный qualification receipt. Scored `evalRun` проверяет тот же receipt и hashes независимо от того, был ли вызван preflight: E2E path без entry pack не должен обходить gate. Для других кейсов и старых frozen manifests corpus не становится новой безусловной обязанностью.

Corpus хранит вопрос, stage, ожидаемую классификацию и допустимый набор response IDs, не хрупкий дословный rationale или порядок массива. Receipt связывает fixture/definition/corpus, Judge prompt/validator version, Judge profile (sol/high), результаты отдельных вопросов и qualification operation. Изменение любого смыслового входа инвалидирует reuse. Qualification не зависит от subject harness ID, повторять одинаковый оплачиваемый Judge для каждого из четырёх запусков не нужно. Mock regression детерминирован; live qualification — отдельная проверка доступности и поведения, не доказательство математической стабильности LLM.

**Проверки.** Два исторических вопроса отдельно и вместе; текстовый индикатор/закрытая задача не получают разных решений в четырёх профилях. Старый fixture не проходит корпус, CP-179 проходит. Отрицательный вопрос должен быть действительно in-scope material и не покрытый ответом; out_of_scope/ambiguous — отдельные корректные классификации, не ошибка matcher. Не менять ответы/expected result только чтобы пройти Judge. Для case, включившего corpus qualification, пустой corpus, неизвестный response ID, неверный hash, stale prompt/profile и malformed Judge result блокируют admission с точной причиной. Нет утечки qualification Sessions в scored usage/Work inventory; cleanup failure сохраняется отдельно. Новый неизвестный вопрос всё ещё fail-closed и требует решения пользователя. Старые EVAL не меняются.

### E1. Общая case-level проверка итогового результата

**Дополнение аудита.** У Grok, Luna и ZCode разный финальный статус SCN-002 (`runnable_local`, `accepted_local`, `planned`), при этом у Grok/Luna Judge outcome 4. `assessment.json` уже требует full deterministic local acceptance matrix, criterion-level evidence/proof limits и protocol evidence passport standards. Нужен не новый универсальный бюрократический барьер в dd-flow, а одинаковая **case-specific** мера успешности.

**Минимальная мера.** Case-local acceptance checker извлекает объективные факты из **frozen execution checkpoint**, не из текущего изменяемого workspace: статус SCN-002, PRT-007 matrix coverage, curated evidence refs, criterion/check results, scope/checkout identity, явные gaps. Конкретный canonical SCN-002 требует возврата к `accepted_local` после fresh readiness; `planned/runnable_local` не заменяют его. Checker не пытается regex-оценкой доказать семантическую достаточность произвольного Markdown. Missing/неразрешимые refs, failed/stale checks и незакрытый status — детерминированные gaps; смысл и достаточность эквивалентного curated evidence оцениваются Final Judge по тем же AC. Не требовать точного имени passport, дополнительных цветов/индикаторов или production evidence, которых нет в контракте.

Использовать существующие artifact/checkpoint plumbing и **один** acceptance receipt на immutable checkpoint. В нём version checker/definition, checkpoint manifest digest, факты/gaps и status `passed|failed|not_applicable|unavailable`; путь/время status-вызова не входят в идентичность фактов. `not_applicable` — другой case/focused scope или Stage ещё не достигнута; missing обязательный документ в достигнутом финале — failed, не not_applicable. I/O/corrupt checkpoint — unavailable с evidence error, не продуктовый fail по догадке. Все пути relative к разрешённому checkpoint/owned artifacts; проверять traversal/symlink и содержимое receipt по manifest digest, не следовать произвольной внешней ссылке из prose.

**Жизненный цикл и совместимость.** В `finalizeRunProjection` построить/сохранить receipt перед freeze, после выбора устойчивого execution checkpoint; включить его digest в новую projection `candidateExecution` и packet `executionEvidence`. `candidateMatches` сравнивает сохранённый digest, а не перечитывает live tree. При concurrent finalize использовать существующие event/result hash guard и candidate lock; одинаковый checkpoint даёт один смысловой receipt. Если manifest включает этот же receipt, возникнет цикл hash: acceptance — sidecar, привязанный к уже frozen execution manifest, затем включённый в run candidate, не обратно в execution manifest.

Новые поля candidate/report optional и только для нового feature-enabled definition checkpoint; старый projection не дополнять null/default при чтении, иначе сломается старый immutable hash. Обновить `schemas/run-candidate.v2.schema.json`, `schemas/report.v2.schema.json` и evidence schema/producer вместе, включая уже существующие producer fields в затронутых структурах. Schema tests должны валидировать реальные generated objects, не искать строки в исходнике. Старые v2 без acceptance читаются без upgrade/re-score; несовместимые readers не используются для нового pinned checkpoint. `cleanupOnly`, repeated status, recovery/reconcile и authorized candidate revision переиспользуют receipt старого checkpoint либо создают receipt нового checkpoint в новой revision; не меняют старый candidate или Judge cache. Judge cache bound к candidate digest.

**Что означает успех.** Сохранить различие execution completion, case acceptance, Judge validity/quality и evidence completeness. Product acceptance failed не превращать в infrastructure failure и не запрещать Final Judge разбирать завершённый продукт. `completed` остаётся lifecycle-фактом; итоговый отчёт отдельно показывает failed acceptance и не называет такой запуск полным успехом. Machine receipt не меняет автоматически Judge score 4→0; расхождение с rationale остаётся видимым. `passed` checker означает только пройденные проверяемые условия, а не замену семантического вердикта Judge.

**Проверки.** Три исторических состояния сценария; иной case/focused run/failed SPECIFY; отсутствующий passport и содержательно эквивалентный evidence; stale/failed receipts; extra prose не даёт false pass; path escape/corruption; fixed checkpoint + изменённый live tree; параллельный/repeated finalize; cleanup-only после удаления live workspace; старая schema/candidate без новых полей; новая revision и старый Judge cache. Новый Final Judge packet содержит receipt вместе с исходным evidence, одинаково для всех harnesses.

## 4. Порядок реализации и gates

1. **Контракт до кода.** Перенести CP-179 canonical изменения в один выбранный новый definition checkpoint; проверить не только файл источника, но frozen packaging, case revision, assessment и остальные копии ответов. Не запускать E2E с новым runbook, но старым snapshot fixture. Зафиксировать таблицу native model scopes/tool types и acceptance evidence-only finish contract в regression vectors. Не менять исторические EVAL.
2. **Независимые исправления.** M1/T1 можно делать независимо от A1/H1. Но M1 завершён только после согласования dd-flow и dd-eval reducers; T1 — после проверки consumers, а не одного decoder. A1 — engine contract/schema/prompts/controller tests вместе. E1 зависит от согласованного A1 final checkpoint/evidence contract; H1 — от принятого CP-179 fixture и explicit qualification entrypoint.
3. **Локальные gates.** Проверки из таблицы ниже, затем dd-flow `pnpm typecheck`, `pnpm build`, `pnpm test:integration`, `pnpm test:runtime-sensitive`, `pnpm test:release`; dd-eval `npm test`. Targeted pass не выдавать за полный suite pass. Если suite завис/прерван, сохранить какой test/process и причину, результат считать незавершённым, не PASS. Тесты пишут только в собственные временные roots; не используют живые EVAL/home. Санитизированный corpus не включает secrets или полные tool output.
4. **Packaging/qualification.** Штатный release workflow dd-flow, опубликованный version/digest и совместимый dd-eval checkpoint. Проверить поведение из установленного пакета (включая скопированные `.mjs`, schemas и templates), не только source tests. Hooks в `~/.codex/` и `~/.codex-cpa/` обновлять штатным runbook; Codex через `cx`, home `~/.codex-cpa/`; текущие квалифицированные binaries AGY/Grok/ZCode, без охоты за старыми. Все Judge/Interaction Judge — `gpt-6-sol`, `high`; Luna subject — `gpt-6-luna`, `xhigh`. H1 live definition qualification выполняется один раз на этот exact checkpoint/profile; не проходит — scored runs не начинать.
5. **Четыре новые попытки.** Отдельные чистые homes, одинаковые case/engine checkpoints и официальные preflight receipts. Отдельно подтвердить native Session/profile/capacity/auth (preflight не считается продуктивным E2E). Проверить старые процессы/активные попытки до launch; не resume/restart и не создавать дубликат живого RUN. Не менять fixture/engine/hooks/runtime artifacts посреди scored попытки. Изменился binary или definition — новая qualification и новая попытка, а не подмена frozen inputs.
6. **Мониторинг и остановка.** Actual Stage из timeline/controller/artifacts, EVAL/Work/native Turn/lease/HITL/primary error сопоставляются по runbook. Runtime blocker — штатная адресная остановка только этого EVAL при ещё живом исполнении; terminal EVAL не останавливать повторно, процессы других homes не трогать. Без ручной правки DB/receipt или auto-resume; расследование read-only. При исчерпанной квоте/недоступном provider фиксировать внешний blocker, не ослаблять gates и не организовывать бесконечные retries. Heartbeat не включать заново без запроса пользователя.
7. **Финальная приёмка.** Для каждого из четырёх: baseline PASS; SPECIFY→PROTOCOLIZE→PLAN→PLAN-REVIEW→CODE→CODE-REVIEW→MERGE; clean settlement; valid Final Judge; закрытые принятые AC, SCN-002 и matrix/equivalent curated evidence; нет новых необъяснённых native evidence gaps. Отдельно показать execution outcome, acceptance, Judge result, observation coverage/capabilities и cleanup. Неподдерживаемое провайдером поле честно `unavailable/capability limitation`, а не придуманный факт; это не исправляется требованием 100% для несуществующей native API. **Утерянный доступный факт**, как Grok spawn model или Codex item event, — незакрытый дефект. Новый terminal failure/непройденный acceptance остаётся открытым, а не маскируется средним баллом остальных.

### Реестр рисков, а не обещание безусловного успеха

- Native API может не отдавать response-level model или lost-event sequence. Сохранять известный уровень доказательства; live run может подтвердить configured attribution, но не более сильное утверждение.
- Новый Codex binary может менять item shape. Qualification pin + explicit unsupported gap; обновить decoder по факту протокола, не считать unknown success и не падать всей продуктивной сессией из-за одной метрики.
- Semantic PLAN/Final Judge остаются модельными оценками. Механические checks закрывают объективные факты, corpus ловит известные вопросы; ни один из них не доказывает полноту всех будущих вопросов.
- A1 — единственное намеренное расширение lifecycle-контракта; оно допускается только вместе с controller/schema/replay tests. Не заменять его «последним Work, который ждёт final checks». Opt-in `needs_checks` не нужен для кейсов без такой зависимости.
- Provider quota/auth/capacity — внешняя предпосылка, не обещание плана. Верификация доступности непосредственно перед запуском обязательна; автоматический score reroll ради PASS запрещён.

## 5. Ponytail review: что сознательно не строим

- Используем существующие native journals, `observeModel`, `ToolObservations`, PLAN Work и Interaction Judge; не вводим новый event bus, БД, Stage, framework шаблонов или второй счётчик инструментов.
- Не делаем весь Grok home и глобальные Codex sessions «неизменными», не копируем их целиком в RUN и не ослабляем ownership/realpath guards. Берём конкретные native facts с явной Session identity.
- Не наследуем модель child от root и не выдаём requested model за observed. Не считаем absence of tool call доказательством отсутствия tool activity без native lifecycle receipt.
- Не «чинить» ZCode понижением требований Judge или разрешением MERGE править продукт. Назначаем CODE owner и используем opt-in evidence-only finish + уже существующий repair Work; не вводим отдельную очередь acceptance jobs.
- Не добавляем новые ответы в fixture без решения пользователя; новые вопросы остаются блокерами. Corpus qualification ограничен реально встреченными решениями.
- Не превращаем case-specific passport/status в глобальное правило для всех проектов. Проверяем содержимое и доказательство, а не красивое имя файла.

## 6. Итог проверки готовности R2

Исходная R1 **не была готова** к реализации без уточнений: смешивала journal/tool coverage; предлагала небезопасное снятие model incomplete; не учитывала второй reducer и потребителей; обещала невозможную очередность acceptance Work; не определяла E2E wiring qualification, schema compatibility и повторную finalization.

В R2 эти решения были определены: scopes и ограничения доказательств; supported terminal forms; source precedence и no-tool semantics; opt-in CODE evidence pass с существующим repair; отдельная qualification с нулевым provider preflight; immutable checkpoint-bound acceptance и legacy handling. R3 закрывает кодовую реализацию и перечисленные выше локальные проверки, но **не заявляет** PASS полного dd-flow suite, release или четырёх E2E до их фактического завершения. Нет нерешённой продуктовой развилки, требующей догадки об ответе пользователя. Тесты на rare failures, replay, compatibility и реальные provider capabilities остаются обязательными gates.

## 7. R4: выявленное live E2E продолжение

Grok `EVAL-20260928092401-1866ba37` прошёл baseline и вошёл в SPECIFY, но остановился на `interaction_fixture_gap`: трёхчастный вопрос Q-002 отдельно спрашивал, могут ли owner и member менять приоритет в активном проекте. Исходный канонический ответ говорил только о существующем интерфейсе редактирования, а корпус квалификации проверял закрытые/архивные задачи и индикаторы, но не активные роли. Interaction Judge корректно отказался домысливать права из косвенной фразы. Это дефект покрытия fixture/qualification, не отказ Grok или runtime.

Исправление: в единственном каноническом ответе явно закрепить существующие права owner/member активного проекта, отсутствие выбора при создании и видимость подписи в списке и карточке; сохранить уже принятые правила архивного проекта, API и отсутствие дополнительных индикаторов.
