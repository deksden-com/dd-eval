# 036 — Ревизия контролей: минимальный достаточный контур

Дата: 2026-09-16. Статус: изменения runtime реализованы; профильные регрессии проверены. Живой E2E и release gate не запускались.

Редакция 2: после дополнительного исследования приоритет изменён с оптимизации
контролей на удаление необоснованных контролей. Исходное исследование сохранено ниже;
фактическая реализация и границы проверки описаны в следующем разделе.

## Реализация (2026-09-16)

- R1: удалён общий `stageInputGuard`. PLAN-REVIEW принимает результат внутри
  существующей transaction; CODE/CODE-REVIEW проверяют generation и только свои
  terminal Work после await. Schema проверяет уже прочитанное значение.
- Freeze: content fingerprint не зависит от staging/commit удалений, добавлений
  и rename. Повтор после source commit до enqueue использует `source-freeze.json`
  при прежних workspace/branch/HEAD и чистом дереве; новые изменения отклоняются.
  Git freeze остаётся вне SQL transaction: она не может откатить commit.
- R2: детерминированный check переиспользуется между gates при совпадении остальных
  входов; binding возвращает текущий gate. Недетерминированные проверки, изменения
  кода, среды и профиля сохраняют собственные правила инвалидирования.
- R3: retry определяется классификацией ошибки и effect, а не наличием текста
  `retry_command`. Unknown/committed effect не разрешает повтор мутации.
- R4–R5: settlement inspect нужен для непогашенного дерева/недостающего evidence,
  но не для persistence-only pending. RPC и ожидание ограничены остатком deadline.
- R7: `eval preflight` проверяет baseline policy/pin, не исполняя её команды;
  возвращает `not_run`, а не PASS. Реальное admission execution сохранено.
  Baseline в другом workspace не считается автоматически переносимым.
- R11: корректно пересозданный CODE batch может иметь прежний checksum.
- R12: один baseline на группу review фиксируется при старте первого reviewer,
  проверяется при завершении последнего. Проверка standalone/старых read-only Work
  сохранена. Ошибка сообщает изменение входа, не обвиняет конкретного писателя.
- R13: принятое решение CODE-REVIEW хранится значением в существующем context;
  repair не зависит от дальнейшего наличия исходного файла. Явная подмена решения
  отклоняется; старый decision sidecar читается для совместимости.
- R14: обычная выдача engine summary не запускает health subprocess;
  doctor выполняет глубокую диагностику один раз. Install/selection protections сохранены.
- R6/R8/R9/R10: сохранены существующие границы capture/result, integrity импорта,
  provenance/comparability, observer/owner и машинного binding. Для этих пунктов
  дополнительного подтверждённого лишнего контроля, требующего удаления, не найдено;
  новая абстракция или второй supervisor не добавлены.

Проверки: 43 code-checks, 42 lifecycle-invocations, 12 stage-consistency и 3
run-controller-adapter regression cases прошли. Интеграционный PLAN correction
с неизменившимся batch прошёл. Engine list regression подтверждает отсутствие
entrypoint probe. В dd-eval policy-only baseline tests прошли. Fork EVAL и fork
snapshot tests отдельно прошли после таймаутов при параллельной тяжёлой нагрузке;
это не доказательство отсутствия timing-проблем под нагрузкой. Полный gate и
живой checkpoint E2E остаются отдельной квалификацией, не скрытой частью preflight.

## Цель и границы

dd-flow помогает исполнить flow и сохраняет достоверный результат его операций.
dd-eval задаёт эксперимент, отвечает только предусмотренными ответами и оценивает результат.
Адаптер отвечает за конкретного провайдера, его сессии и физическую остановку.
Не создавать ещё один supervisor, registry, journal или универсальный framework проверок.

Проверка нужна, если предотвращает конкретный неверный переход, повторный побочный
эффект, потерю данных, чужую остановку либо недостоверную оценку. Для каждой проверки
должны быть понятны: проверяемый факт, его владелец, когда он устаревает и действие при отказе.
Число assert само по себе не критерий качества. Проверка перед await и после await
может быть необходимой: между ними пользователь мог остановить RUN.

### Правило удаления, а не сохранения по умолчанию

Обычный переход Stage не требует checksum всего окружения. Достаточно права операции,
ожидаемого состояния, необходимых результатов и атомарного изменения принадлежащих
операции записей. Неизменность чужих файлов не является универсальным prerequisite.

Для сохранения контроля назвать конкретного независимого писателя/границу доверия,
неверное действие без проверки и почему существующий owner/transaction/receipt его
не предотвращает. Если такого сценария нет — удалить контроль, а не придумать ему
новый hash, revision, lease или абстракцию. Это критерий ревью, не новый runtime registry.

Hash оставляем для сравнения содержимого там, где от него зависит решение: reuse
тестов; импорт/restore артефактов; привязка результата к действительно проверенному
входу. Provenance также сохраняем, но metadata не превращаем автоматически в блокер.
Hash не является защитой от злонамеренного писателя, способного изменить и данные,
и их manifest, и не доказывает качество работы агента.

Исследованы основные пути admission → controller → lifecycle/Work → CODE → review
→ merge → capture/control/recovery → eval report. Просмотрены реализации и callsites
в dd-flow-cli/src/services и dd-eval/lib; адаптерная часть проверена прежде всего через
контракт и вызывающий код. Это не утверждение о построчном аудите всех адаптеров,
всех файлов репозиториев или измеренной стоимости каждого контроля. Ниже отделены
подтверждённые механизмы от кандидатов, требующих дополнительной проверки при реализации.

Ссылки на соседний checkout dd-flow-cli предполагают обычную раскладку репозиториев.

## Подтверждённый дефект: проверка отвергает штатный freeze source

Историческое свидетельство: fork-017, EVAL-20260916060330-cf20bb8e,
RUN-001-eval-subject, engine beta.74. Завершение code-review отклонено с
stage_inputs_changed, changed_inputs=files, effect=no_effect, disposition=fatal.
Workspace находится в ~/.dd-eval/qualification/cp-108-zcode/forks/
EVAL-20260916060330-late-allocation-fix-fork-017/executions/e2e/dd-flow-home/
projects/PRJ-001-project/checkouts/worktrees/RUN-RUN-001/project.

Цепочка в коде:

1. `vnext-code-review.ts:128` запоминает fingerprint workspace и артефактов review.
2. После проверок `:175` проверяет его снова.
3. `:176` вызывает prepareVnextMergeRequest; `vnext-merge.ts:70` выполняет
   commitPendingSource ДО возвращения замыкания DB enqueue.
4. `vnext-code-review.ts:179` сравнивает workspace со старым fingerprint.
5. `code-checks.ts:358` строит fingerprint по `git ls-files -co`. Удалённый tracked
   файл до коммита входит в список с digest `<missing>`, после коммита отсутствует.
   Следовательно, одинаковое фактическое дерево файлов может дать разные fingerprints.
6. В историческом workspace HEAD ff7d7636d8149c4f09e137a38c6ac4846fa18dab —
   `freeze accepted source`; этот коммит действительно удаляет `.env.example`.

Это согласованное объяснение ошибки по коду и сохранённому git-состоянию, а не новый
живой воспроизводящий прогон. HEAD сам по себе в fingerprint НЕ включён: утверждение
«любой commit меняет fingerprint» неверно. При добавлениях также проверить отсутствие
зависимости от состава/дубликатов git listing; список нормализовать как множество.

Решение: убрать общий stage guard вокруг штатного freeze, а не добавлять к нему
исключение «после commit». Принимаемые CODE checks должны относиться к принятому
source; это проверяется на соответствующей границе, не перечитыванием всех Work RUN.
Там, где content fingerprint остаётся нужен для checks, сделать его независимым от
staging/commit: отсутствующий файл не является содержимым дерева. Разделить read-only
подготовку merge и freeze. Переиспользовать существующий source-freeze.json и source
commit для восстановления; не добавлять ещё один журнал. Не называть ошибку всей
операции no_effect, если commit уже сделан.
SQLite transaction не откатывает git и filesystem.

## Реестр решений

### R1. Общий stageInputGuard — убрать; не заменять универсальным dependency guard

Источник: `runs.ts:849`; все три потребителя — vnext-code, vnext-plan-review,
vnext-code-review. Guard перечитывает ВСЕ works данного RUN, включая task/payload/result,
а не только зависимости принимаемого результата. Файлы представлены безымянным tuple;
ошибка показывает только общий hash `files` или `works`.

Целевое состояние — удалить helper и его три вызова. Вместо него:

- PLAN-REVIEW finish синхронный: читать решение один раз, принимать необходимые
  состояния reviewer Work в существующей write transaction; не сравнивать все Work
  RUN до/после вычисления результата. Не держать transaction при agent/RPC ожидании.
- CODE и CODE-REVIEW имеют await checks: после него повторно проверить cancellation/
  generation и необходимые terminal Work, а пригодность проверенного кода определять
  по check receipt. Не дублировать это ещё одним hash всего workspace.
- При реально поддерживаемом независимом редактировании принятого входа оставить
  адресную проверку этого входа на границе принятия. Не считать SQLite защитой файлов.
  Не удалять защиту stale evidence, пока не установлен её конкретный владелец.

Решение/verification читать и валидировать из одного принятого набора bytes; дальнейшее
изменение пользовательского пути не должно менять уже принятую операцию. Повторный
finish возвращает сохранённый результат, а не заново оценивает mutable входы.
Не вводить глобальный revision. Подтверждённый self-conflict найден в review;
аналогичный фактический сбой остальных двух путей не установлен.

### R2. Повторные quality gates — переиспользовать, не отменять

Источники: `vnext-code-review.ts:157–166`, `vnext-code.ts`, `vnext-merge.ts:179`,
`code-checks.ts:247–269,357,377,434`.

Review повторно запрашивает весь набор work/code/readiness даже без repairs.
runCodeChecks уже умеет reuse, но только при `reuse=deterministic` и пригодном receipt.
Dedup включает gate; execution hash также включает gate, абсолютный workspace и
всё переданное environment. Поэтому «тот же тест уже прошёл» не гарантирует reuse.
Это подтверждённый механизм повторов, не замер количества повторов конкретного E2E.

Минимум: для детерминированных проверок одинакового execution contract использовать
один успешный receipt, привязывая его к требованиям стадий. Review без изменения
проверяемых inputs не должен повторять эти команды. Изменение кода после repairs
инвалидирует зависимые receipts. Gate оставить как место требования, не как причину
повторить идентичную команду. Не переиспользовать внешние/времязависимые проверки
автоматически. Не удалять workspace/env из ключа вслепую: cwd и env могут менять результат.
Сначала ограниченный reuse в том же workspace; перенос между checkout — отдельная задача.
Сужение environment допустимо только при явном контракте релевантных переменных.

Merge проверяет ДРУГОЕ итоговое дерево после интеграции: его gate не объявлять лишним.
Readiness bootstrap нужен для рабочего окружения; его не смешивать с полным quality gate.
Failed receipt не превращать в бесконечный автоповтор: исправление или явный retry сохраняются.

### R3. Correctable/fatal зависит от списка кодов и retry_command — выпрямить

Источник: `lifecycle-invocations.ts`, isRetryableLifecycleRejection и outcome recording.
Классификация использует allowlist и наличие текстового retry_command. Изменение
подсказки оператору тем самым способно влиять на управление RUN.

Задавать смысл отказа у источника через существующие error details: rejected before
acceptance / committed / outcome unknown и явную recoverability. Текст подсказки не
является политикой. Сохранить совместимость старых errors в одном месте на время миграции.
Не делать любой no_effect автоматически retryable: неправильная identity и запрет
операции также могут не иметь эффекта. Не повторять неизвестно завершившуюся мутацию.

### R4. Completed operation и physical settlement — оставить различие, убрать лишние запросы

Источники: `run-controller-adapter.ts:95–144`, `native-session-control.ts`,
`runtime-scope-stop.ts`, `run-controller.ts:503–510`.

Уже есть полезные сокращения: recovery не повторяет session.create; нет запроса
operation journal при отсутствии daemon; settlement polling включается только при
pending/blocked. Controller status — локальная проекция, не provider inspect.
Не предлагать эти уже реализованные вещи как отсутствующие.

Остаётся кандидат: awaitSettlement сначала делает receipt-only retry, затем native
inspect при ЛЮБОЙ оставшейся pending/blocked причине. Вызов должен зависеть от того,
какого доказательства не хватает: DB persistence не исправляется проверкой провайдера.
Проверить значения settlement.reason у всех поддерживаемых адаптеров до удаления ветки.
При достаточном terminal receipt не опрашивать завершённый Turn заново.
При живых дочерних задачах inspect остаётся оправданным. ACK cancel НЕ доказывает stop.
Historical shutdown receipt можно использовать только при неизменной identity владельца
и отсутствии новых активных операций, как уже предусмотрено частью stop-кода.

### R5. Таймауты разных слоёв — разграничить, не складывать независимые watchdogs

Источники: `run-controller-adapter.ts` (120s settlement и 30s запросы),
`native-session-control.ts` (30s), `runtime-budget.ts`, recovery-observation-budget,
dd-eval `observation-clock.mjs`, managed-flow-client.

Deadline RPC, inactivity агента, общий лимит eval и recovery budget — разные ограничения.
Сохранить их назначения. У каждой productive операции один владелец времени исполнения;
observer timeout прекращает ожидание и показывает unknown/unavailable, не объявляет
удалённую работу погибшей. При вложенном ожидании передавать remaining budget, не
выдавать новый полный бюджет на каждом retry. Проверить границу 120s + последний RPC:
проверка deadline перед RPC сама по себе не ограничивает длительность RPC остатком.
Это конкретный кандидат на уточнение, а не доказанный источник последнего падения.

### R6. Capture на границах — нужен здесь, не должен переоценивать Stage

Источник: `run-controller-capture.ts`; controller вызывает capture перед successor.
Для наших checkpoint-resume экспериментов стабильный snapshot действительно нужен.
Сохранить fence писателей и проверку snapshot на импорт/восстановление; нельзя просто
копировать живое дерево и считать его пригодным для fork.

Разделять результат Stage и capture: сбой capture не отменяет уже принятый Stage.
При обязательном checkpoint остановить переход с capture_failed; восстановление
повторяет capture, не Stage. При отсутствии capture_root проверки capture уже не идут.
Новый optional-capture режим сейчас не нужен. Повторную полную проверку неизменного
snapshot можно сокращать только внутри одной операции с гарантией неизменности;
чтение с диска после рестарта/импорт — настоящая граница доверия.

### R7. Baseline admission — не делать повторную подготовку обязательным ритуалом

Источники: dd-eval `baseline-admission.mjs`, runner.mjs callsites.
Preflight и fresh execute могут оба исполнять baseline commands. Но fork уже проверяет
и переносит receipt/logs, а НЕ повторяет baseline. Проверка receipt не равна запуску тестов.

Использовать подготовленный admission для точного checkpoint/контракта/релевантного
окружения, если они не изменились. Один путь подготовки и запуска; не запускать полный
baseline только потому, что появился новый eval ID. Сохранить проверку, что admission
не изменил исходный baseline, и integrity на импортируемых данных.

### R8. Engine pin — provenance сохранить; сравнимость не связывать со всей обвязкой

Источник: dd-eval `engine-admission.mjs`: assertCheckpointEngine требует точного
engine version + artifact hash, затем читает артефакт. Это контроль конфигурации запуска,
не критерий сравнимости двух результатов. Нельзя просто удалить его и молча поменять
движок существующего RUN.

Для нового fork явный engine upgrade с provenance родителей и фактического engine.
Сравнимость определяется экспериментом/flow/memorybank/checkpoint, а отличия engine
и адаптера отражаются как metadata/ограничения интерпретации. Точная совместимость
восстановления старых артефактов проверяется отдельно. Полный hashing делать на admission
и при переносе артефакта; прежде чем убирать повторные вызовы, доказать неизменность
объекта между ними. В этом аудите не установлено, что hash идёт на каждом poll.

### R9. Eval не должен дублировать supervisor Subject

Источники: managed-flow-client, execution-state, runner, spec 035.
Managed client уже наблюдает dd-flow controller, поддерживает единый event cursor,
передаёт context/answer и проверяет fence перед dispatch. Это сохраняем.
Проверки порядка событий, controller identity и generation нужны против поздних ответов
и повторной доставки, а не для оценки качества продукта.

Убирать только реально дублирующиеся managed Subject ветки прямого контроля daemon/PID
после проверки callsites. Нельзя удалить driver-recovery целиком: focused/legacy/Judge
имеют собственных владельцев. При отсутствии подтверждения завершения cleanup сохранять
unknown, а не successful. Для Judge нужен стабильный candidate, не словесное «готово» агента.

### R10. Identity и invocation — оставить машине, не превращать в задачу модели

Источники: lifecycle-invocations, hooks, session-identity, controller-fanout.
RUN/Work/native Session/operation — разные идентификаторы и разные границы владения.
Их нельзя заменить одним session_id или доверять строке, которую придумала модель.
Проверки совпадения scope/session/generation сохраняются на входе мутации.

Упростить пользовательский контракт: модель вызывает бизнес-команду и передаёт
результат; транспортную identity подставляет binding/hook/adapter. Не добавлять новые
подтверждающие CLI-вызовы модели, когда identity уже достоверно известна runtime.
Для провайдера без child hooks нужен его поддерживаемый binding-путь, не фиктивный hook.
Это направление упрощения; отдельный новый дефект ZCode в этом аудите не воспроизведён.

### R11. Изменение hash не доказывает исправление — удалить такое требование

Дополнительное исследование: `vnext-plan-review.ts:193–198` сначала вызывает
prepareVnextPlanArtifacts, а затем при needsCorrection требует
prepared.batchChecksum !== initialBatchChecksum, иначе stale_code_work_batch.
Но изменение plan/aspect explanation не обязано менять производный CODE batch.
Равенство результата детерминированной генерации не доказывает, что генерации не было.

Удалить именно требование различия hash. Оставить валидацию финального PLAN и
генерацию batch из него, затем публикацию этого результата. Provenance checksum
можно оставить в report. Не заставлять модель искусственно менять задания ради hash.
Не ослаблять проверку актуальности входа, на котором действительно проходил review.
Регрессия: допустимое исправление PLAN с идентичным сгенерированным batch принимается;
невалидный PLAN отвергается. Это найденный по коду дефект условия, не живой репрод.

### R12. Fingerprint общего workspace не устанавливает виновника изменения

Дополнительное исследование: `work-registry.ts` start сохраняет workspaceFingerprint
для каждого read_only Work; settle сравнивает общий workspace и выдаёт
read_only_work_mutated_workspace. Результат доказывает только изменение дерева между
двумя моментами, но не запись именно этим Work. Особенно важно при нескольких workers
и координаторе в общем workspace. Сейчас каждое read-only Work также считает весь hash.

Стабильность входа review нужна; N независимых одинаковых проверок и обвинение конкретного
worker не нужны. Использовать один baseline принятого входа на review wave/stage и
проверку перед принятием её результатов. Repairs идут после завершения reviewers.
При реальном изменении входа — stale review input с понятными changed paths, а не
доказательство нарушения конкретным агентом. Сам read-only запрет сохраняется в
поддерживаемых permissions адаптера; не изобретать новую sandbox систему для этой задачи.
Перед переносом per-Work проверки просмотреть все read_only callers: standalone Work
без stage-owner сохраняет локальную проверку стабильности, но с корректной диагностикой.
Не удалять проверку поведения, пока её stage-level замена не покрывает этот путь.
Регрессии: параллельные reviewers используют один baseline; внешняя запись инвалидирует
вход, но не приписывается случайному worker; штатный repair после review разрешён.

### R13. Принятый repair decision — сохранять значение, не требовать вечности файла

`vnext-code-review.ts:139–145` хранит .decision-sha256 и требует неизменности файла
при завершении repair. Требуемый факт — repair и завершение относятся к одному
принятому решению, а не к вечному содержимому пути в filesystem.
Использовать сохранённое принятое решение/существующий repair payload в текущем цикле;
проверить достаточность payload перед удалением sidecar. Если данных не хватает,
сохранить решение в существующем stage artifact, без новой подсистемы receipts.
Новая попытка подменить решение должна отклоняться явно либо начинать предусмотренный
новый цикл, не молча приниматься. Старые runs с одним sidecar читать совместимым путём;
не переписывать их автоматически. Это упрощение хранения принятого входа, не отмена
связи findings → repair → accepted decision.

### R14. Проверки engine: не смешивать integrity и повторный health probe

`engines.ts:manifestDiagnostics` считает общий engine checksum, отдельно checksums
schema registry и запускает entrypoint --version (если checkEntrypoint не false).
Это несколько разных проверок в одном helper. Стоимость на каждом CLI-вызове пока
не установлена: нельзя утверждать, что каждая команда обязательно делает всё это.

Оставить глубокую проверку на installation/import/bind и явный doctor. Обычное чтение
уже выбранного binding не должно автоматически означать повторный запуск engine probe.
При полном content verification не пересчитывать те же bytes отдельным проходом ради
schema checksum; schema identity/валидность на admission сохраняется. Использовать
существующий режим checkEntrypoint, где caller не запрашивает healthcheck. До изменения
callers проверить требования к mutable external snapshot: имя каталога само по себе
не гарантирует immutable содержимое. Не строить фоновый watcher или глобальный cache.

## Конкретные удаления и границы сохранения

| Контроль | Решение | Что остаётся вместо него |
| --- | --- | --- |
| Все Work RUN + workspace на каждом stage finish | Удалить общий stageInputGuard | State/generation, нужные Work в transaction, check evidence для кода |
| Hash до/после собственного merge freeze | Удалить stage-перепроверку | Принятый source + существующий freeze receipt и target lock |
| Обязательное различие hash generated batch | Удалить | Сгенерировать и проверить batch из принятого PLAN |
| Один full-workspace hash на каждого reviewer | Объединить у владельца review | Один стабильный вход wave; standalone fallback |
| Неизменный пользовательский decision-file через repairs | Заменить принятым значением | Решение текущего цикла + связь repair, без скрытой подмены |
| Terminal operation → unconditional provider inspect | Не выполнять | Inspect только недостающего physical settlement |
| Quality заново из-за имени стадии | Не выполнять для пригодных deterministic receipts | Проверка реального изменения inputs |
| Hash импортированного snapshot и переносимого engine | Сохранить на границе | Проверка целостности до использования |
| Fingerprint в provenance/report без потребителя | Убрать вычисление после поиска readers | Оставить полезные version/commit/receipt ссылки |
| Ownership, stop fence, merge target, schema входа | Сохранить | Это защита действия, не ритуальная перепроверка |

Не удалять schema поля/DB columns массово: сначала перестать вычислять/требовать
ненужное в новых запусках, сохранить чтение исторических artifacts. В частности
workspace_fingerprint в review-context записывается, но finish его не читает;
перед удалением проверить snapshot/report consumers, не объявлять поле обязательным
только потому, что оно уже существует.

## Мысленный проход целевого пути

1. Eval выбирает checkpoint, flow/memorybank, engine и сценарий. Валидирует вход один
   раз на admission; повтор после переноса проверяет артефакты, не запускает всю quality матрицу.
2. dd-flow принимает идемпотентный launch, фиксирует владельца и generation. Повтор
   того же request возвращает ту же операцию. Eval не запускает второго владельца.
3. Адаптер создаёт Session и выдаёт binding. Потерянный ответ означает unknown;
   runtime восстанавливает receipt, а не создаёт новую Session вслепую.
4. Агент выполняет Stage/Work. CLI проверяет schema, право перехода, зависимости
   и сохраняет результат. Неправильный результат возвращается на исправление;
   ownership failure останавливает мутацию, не маскируется как просьба к модели попробовать снова.
5. Предусмотренный HITL получает canonical answer от eval. Неожиданный вопрос
   завершает эксперимент соответствующим отказом, без выдуманного ответа.
6. CODE запускает необходимые checks и сохраняет receipts. Review оценивает код;
   без repairs повторно использует пригодные checks, с repairs обновляет зависимые.
7. Finish принимает валидированный результат и актуальное состояние нужных Work.
   Нет общего hash-барьера. Check receipt связывает тесты с кодом. Freeze source сохраняет содержимое,
   не инвалидирует content identity удалениями/staging. Собственные побочные эффекты
   имеют receipt и не объявляются отсутствующими после последующего сбоя.
8. Merge берёт lock и проверяет актуальный target. При новом итоговом дереве выполняет
   нужный gate, затем публикует результат. Проверка target не заменяется source receipt.
9. Для resume capture подтверждает отсутствие писателей и создаёт snapshot. Его отказ
   сохраняет Stage done и capture_failed; не заставляет агента переделать завершённый Stage.
10. Завершение Turn принимается из authoritative receipt. Оставшихся детей/процессы
    завершает их владелец. Только при недостающем settlement наблюдает соответствующий ресурс.
11. Eval фиксирует execution и cleanup отдельно, оценивает стабильный candidate,
    публикует результат и причины отказа. Логи помогают расследованию, не создают
    самостоятельный конкурирующий источник состояния.

## Последовательность реализации и минимальные регрессии

1. **Сначала R1 + R11 + freeze/fingerprint:** удалить общий stage guard и требование
   изменения generated batch. Проверить state/generation/receipt границы вместо него.
   Тест удаления, добавления, rename и content edit;
   staging/commit без изменения дерева не инвалидирует результат, реальная мутация —
   инвалидирует. Fault injection между commit и enqueue; повтор не дублирует commit/merge.
   Проверить все три stageInputGuard callsites и корректность effect.
2. **R12–R13:** вынести стабильность review к владельцу wave, не вводя новых locks;
   принять decision один раз. Проверить самостоятельный read-only Work и старый sidecar.
   **R2:** одна детерминированная команда CODE→review без изменений запускается один
   раз; repair и существенный env/profile change инвалидируют; merge нового дерева
   не принимает чужой source receipt. Недетерминированные checks продолжают выполняться.
3. **R3–R5:** таблица исходов и tests с fake adapter: terminal complete не вызывает
   inspect; active child вызывает; persistence-only pending не опрашивает провайдера;
   unknown effect не повторяет мутацию; stop во время await запрещает новый dispatch;
   RPC не получает больше оставшегося recovery budget.
4. **R6–R9:** готовый baseline не прогоняется заново; capture failure не откатывает
   Stage; resume capture не перезапускает Stage; corruption импортируемого snapshot
   отклоняется; поздние events не переписывают terminal execution; Judge не читает живой candidate.
5. **R10/R14:** только если обнаружится лишняя модельная операция в конкретном пути —
   убрать её через существующий binding и добавить один контрактный тест этой упряжки.
   Просмотреть callers manifestDiagnostics и убрать ненужные health probes; fake
   entrypoint должен показывать отсутствие probe при обычном чтении binding.

Не запускать полный E2E после каждого изменения. Сначала профильные regression suites
по изменённым границам, затем один согласованный общий gate на финальном engine и
один checkpoint E2E. Исторический fork-017 не мутировать; новый прогон — отдельный fork.

## Критерий завершения

Для каждого оставшегося контроля названы факт, владелец и условие устаревания.
Не создаётся замена удалённому глобальному stage guard под новым названием.
Нет требования менять производный artifact, если корректная генерация дала те же bytes.
Неизменность входа проверяет его владелец, а не каждый слой и каждый reviewer независимо.
Нет повторных productive dispatch при неизвестном исходе, нет повторных
детерминированных checks на тех же inputs, нет проверки неизменности до/после
собственного штатного изменения git-представления, нет зависимости политики ошибок
от текста подсказки. Защиты файлов, merge-target, ownership, cancellation fence и
достоверности оценки сохранены. Не обещать процент ускорения без измерения.
