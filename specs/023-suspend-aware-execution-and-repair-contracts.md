## 2. Общие правила

1. Различать завершение Work, завершение provider Turn, состояние Session,
   итог стадии и остановку процесса. Ни одно не выводить автоматически из другого.
2. Ответ на status, heartbeat runner и действующая аренда процесса не означают
   продвижение модели. Статус running также не является новым событием работы.
3. Потеря RPC-ответа означает неизвестный исход операции, а не её отмену.
4. CLI проверяет форму, ссылки, идентичность, exit code и наличие артефактов.
   Достаточность доказательства и правильность исправления оценивает агент.
5. Использовать существующие journal, operation_id, managed_processes и
   managed_resources. Новая система очередей, новый DSL или отдельный сервис
   восстановления не нужны.

## 3. P1 — единое ожидание с учётом приостановки хоста

Места: dd-eval/lib/dd-zcode.mjs, dd-agy-daemon.mjs, runner.mjs/providerTurn,
dd-codex.mjs, dd-grok*.mjs, dd-opencode*.mjs; bootstrap/check timers в CLI.

- Оставить одного владельца проверки активности для продуктивной операции.
  У AGY сейчас одновременно работают callDaemon.arm и watchdog providerTurn.
  Убрать их соревнование; внешние RPC deadline оставить только для коротких
  запросов управления, не дублировать предел длительности продуктивного хода.
- У Codex есть абсолютный deadline ожидания Turn; Grok/OpenCode также имеют
  собственные транспортные таймеры. Привести их исходы к общему различению
  observation_lost / подтверждённая ошибка провайдера / подтверждённая отмена.
- Небольшой общий модуль учёта времени: wall timestamps для журнала,
  sequence/timestamps настоящих событий для прогресса, наблюдение задержки
  цикла исполнения для обнаружения разрыва наблюдения.
- Не считать любой длинный event-loop gap доказанным сном ОС. Сохранять
  observation_gap с источником и уверенностью; OS sleep/wake считать точным
  интервалом только при наличии соответствующих данных. Проверить свойства
  используемых часов на macOS/Linux; одна замена Date.now на performance.now
  без проверки поведения во сне не решает проблему.
- После разрыва сначала обработать накопленные события и сверить исходную
  операцию. Дать ограниченное окно восстановления соединения. Не превращать
  неизменный running в бесконечное продление.
- Нативный TOOL_TIMEOUT ZCode сохранять отдельно: наш таймер не может отменить
  внутренний таймер закрытого провайдера. Завершённый Work не перезапускать;
  дождаться исхода текущего Turn, после чего координатор продолжает ту же стадию.
  Если провайдер не восстановился — сохранить блокер и завершить дерево.
- Во время локального прогона использовать временное системное предотвращение
  обычного сна, привязанное к процессу запуска. Не менять настройки ОС глобально;
  аварийный сон и явный сон пользователя всё равно обрабатывать.
- Политика применяется к Subject, Judge, HITL Judge, reference build, smoke,
  capacity и merge server через общие функции вызова, с их явными deadline.

Проверки: длительный активный ход; тихий running без нового прогресса;
активность ребёнка; heartbeat без прогресса; перевод системных часов;
пауза хоста и поздний ответ; нативный child timeout после паузы;
отсутствие терминального ответа после ограниченного восстановления.
Использовать управляемые часы и fake provider, без десятиминутных sleep в тестах.

## 4. P2 — сохранение операции и позднего результата

Места: runner-events.mjs/recordOperation/reduceEvents, runner.mjs основной,
resume и reference пути; daemon productive/dispatch каждого адаптера.

- Пронести существующий operation_id до демона и сохранить параметры/их hash,
  исходную Session, состояние и ссылку на результат до ответа клиенту.
  Разрыв сокета не должен уничтожать владение provider-операцией.
- Повторное наблюдение по тому же id возвращает существующую операцию;
  несовпадение параметров — понятная ошибка, новый prompt не отправляется.
- Таймаут наблюдения записывать как observation_lost/awaiting_provider,
  пользуясь существующей моделью событий. Не записывать преждевременно failed
  для той же операции: reduceEvents запрещает противоречивые terminal events.
- После настоящего terminal: синхронизировать Work/Session, сохранить ответ,
  граф и usage; затем выбрать обычный следующий шаг того же координатора.
  Завершённые repair Work не дублировать; пройти обычную проверку стадии.
- Ошибка провайдера не становится success из-за Work completed. Сохранить её
  как дефект; продолжение возможно лишь после завершения старого Turn и
  штатного согласования состояния. Никакого ручного редактирования SQLite.
- Общий failure path сейчас теряет error.details. Сохранять структурированный
  code/details/cause, последнее событие, нативную ошибку и результат cleanup.
- Если приложение восстановилось после перезапуска и исход неизвестен,
  блокировать новый продуктивный вызов до reconciliation, а не угадывать исход.

Проверки: разрыв клиента после отправки prompt; ответ во время и после timeout;
crash после записи результата до ответа; повторный resume; отсутствие дублей
prompt, Work и терминальных событий; одинаковая логика normal/resume/reference.

## 5. P3 — одинаковая отмена и подтверждённая остановка дерева

Подтверждённые соседние дефекты:

- ZCode prepareStop вызывает cancel, но не использует его settled результат
  как обязательное условие успешного stop.
- Grok/OpenCode отклоняют daemon.stop при active ещё до обработки cancelTree.
- Codex daemon.stop возвращает stopped без проверки активности, полагаясь на
  вызывающую сторону. Это противоположная, столь же неверная крайность.
- В runner отмена после liveness timeout специализирована только на AGY.
- Ряд startup/shutdown catch подавляет ошибку остановки и может затем записать
  терминальное состояние managed process, хотя процесс ещё существует.

Единый контракт: обычный stop ждёт/отказывает при работающем дереве;
cancel-tree останавливает известных детей и root, ожидает фактический исход,
после чего закрывает bridge и socket. Управляющая отмена доступна во время
продуктивной операции. Проверить, что inspect не вызывает resume чужой сессии.

Двухфазное значение ответа: запрос остановки принят, затем остановка подтверждена.
Переиспользовать confirmDaemonStopped; исчезновение socket дополнять проверкой
принадлежащих запуску процессов. При неуспешной мягкой отмене разрешена
ограниченная эскалация только для проверенного собственного process group.
При провале сохранять cleanup_failed и живые process ids; не объявлять clean.
Ошибка cleanup не должна подменять исходную ошибку прогона.

Проверки на каждом адаптере: active root; active child; idle tree; повторный stop;
cancel acknowledged, но процесс жив; игнорирование SIGTERM; crash startup;
поздний end_turn во время stop; соседний запуск остаётся нетронутым.

## 6. P4 — аренды, процессы и проверки после сна/crash

Места: managed-processes.ts, code-checks.ts, managed-daemon.mjs,
runner-events.mjs/withLock и persist/heartbeat всех демонов.

- reconcileUnfinishedChecks блокирует дубль лишь при живом процессе И свежей
  аренде. Исправить: установленный живой процесс проверки блокирует повторный
  запуск даже после expiry. Сначала восстановить владение либо подтвердить
  остановку; затем читать completion.json и принимать exit code/артефакты.
- claimExpiredManagedProcesses сейчас сразу переводит запись в orphaned и
  меняет token. После сна это может лишить живого владельца его аренды.
  Перед отъёмом проверить идентичность владельца и связь операции; просрочка —
  повод для reconciliation. Нужны owner PID/start identity и ограниченное
  восстановление после разрыва наблюдения; захват делать атомарно после проверки.
- Результат heartbeat=false нельзя молча игнорировать. Он должен запускать
  проверку владения и запрещать новые действия старого владельца.
- У processTreeIsAlive путь проверки группы обходит сравнение pid_started_at;
  terminateOwnedProcess проверяет наличие старого значения, но не его равенство.
  Перед сигналом перепроверять PID/start identity. Если leader завершился,
  а принадлежность оставшихся членов группы не доказуема, не убивать чужие PID;
  сохранить явную невозможность безопасной очистки.
- Проверить периодическое продление аренды: persist на смене состояния не
  заменяет heartbeat во время длинного prompt. Здоровье владельца и прогресс
  модели учитывать отдельно.
- withLock удаляет каталог блокировки только по возрасту. Это тот же класс
  ошибки: владелец мог спать. Добавить проверяемого владельца/token и безопасное
  освобождение; старый владелец не удаляет новую блокировку в finally.
- Обработать восстановление/освобождение port claims при crash; TTL сам по себе
  не разрешает занять ресурс, который ещё использует живой процесс.
- runCheck имеет отдельный 15-минутный таймер по выводу; пауза хоста не должна
  приводить к убийству проверки после пробуждения. Тихая тяжёлая проверка требует
  явно заданной проектной политики deadline/наблюдения, без угадывания по команде.

Проверки: истёкшая аренда живой проверки; завершившаяся проверка с marker;
два reconciler; PID reused; leader exited/child alive; долгий prompt без persist;
два writer после сна; crash между выделением порта и bind; false heartbeat.

## 7. P5 — единый контракт доказательств CODE и repair

Места: work-registry.ts, vnext-code.ts, vnext-code-review.ts,
schema-validation.ts; dd-memorybank/.memory-bank/dd-flow/schemas/
code-work-result.schema.json и опубликованный project pack.

Обнаружен дополнительный блокер: схема @2 в каноне, dd-tasks и проекте прогона
описывает resolved_finding_refs и запрещает дополнительные поля. CLI требует
resolutions[] с finding_ref/summary/evidence_refs. Таким образом, будущий
CODE-REVIEW repair нельзя надёжно завершить по этому контракту.

- Определить одну актуальную схему; компактный resolutions[] сохранить, потому
  что он несёт результат исправления и доказательства. Убрать двойной контракт.
  Несовместимое изменение выпустить с новой schema version и обновить producers,
  validators, prompt, projection, fixtures и pair. Старые прогоны не переписывать.
- Поле criterion_id сейчас означает AC. Не расширять его молча до check id.
  В новой версии использовать единый evidence[].obligation_ref (назначенный AC
  или назначенная проверка). Каталог допустимых refs строить из Work packet.
  Никакой универсальной поблажки для произвольных POLICY/*.
- Repair хранит связь с причиной: исходный failed receipt уже находится в repair;
  это диагноз, не доказательство успешного исправления. Новое доказательство
  связано с изменённым кодом/тестом; CLI добавляет свежие выполненные проверки.
- Гейт, назначенный на code, остаётся на code. work finish не должен обещать
  исполнение всех проверок независимо от run_at. Координатор после repair снова
  вызывает stage finish; старый passed receipt на другом состоянии не подходит.
- В ошибке валидации возвращать allowed refs, schema path и минимальный пример
  текущей задачи. Не предлагать убрать evidence ради успешного finish.
- Обычному Work не выдавать фиктивный FIND; review repair получает ровно свои
  assigned findings. Не требовать от обычного Work несвязанных resolutions.
- Удалить примеры несуществующего 05-code/checks/receipt.json во всех result
  prompts, включая PLAN/CODE reviewers. Давать реальные receipt paths из CLI,
  а плейсхолдеры явно помечать как заменяемые; существование refs проверять.
- Семантическую достаточность evidence оставить координатору и Judge.

Проверки: реальная каноническая схема, а не упрощённый тестовый заменитель;
normal Work; gate repair; review repair; неизвестный ref; пустое/ложное
resolution; полный жизненный цикл CODE-REVIEW finding → repair → gate → finish.

## 10. P8 — отчётность, методика и ранбуки

- Сохранять wall duration, подтверждённые интервалы host suspension и неизвестные
  observation gaps отдельно. Не выдавать wall-minus-sleep за точное время работы
  модели. Отчёт/сайт должны показывать оговорку; отсутствующие данные не равны 0.
- Usage собирать после фактического завершения всех связанных Turn, включая
  поздние события; до этого явно неполный snapshot. Не суммировать повторные
  cumulative snapshots, не смешивать инфраструктурное ожидание с token usage.
- Judge оценивает достигнутые стадии и отдельные дефекты продукта/флоу/обвязки;
  не присваивает успешный E2E незавершённому запуску.
- execute-eval.md: убрать устаревшее ограничение launch set только AGY;
  выбранный run profile определяет эксперимент. Описать запуск, сон, resume,
  диагностику, stop и сбор итогов одной процедурой для всех упряжек.
- harness-backends.md, specs 019/021/022: сослаться на этот план и заменить
  противоречащие правила при реализации. В текущем документе planned != shipped.
- Сохранить исходный EVAL неизменным; для расследования добавить отдельный
  отчёт со ссылками. Канонические stage packs не блокируют новый E2E.

## 11. Порядок поставки и критерии готовности

1. Зафиксировать воспроизводимые тесты P1–P4, затем исправить общие helpers и
   всех перечисленных потребителей. Не добавлять искусственные задержки в flow.
2. Согласовать и реализовать P5 в CLI/каноне одним пакетом; проверить настоящую
   опубликованную схему вместе с engine. Завершить P6/P7, затем P8.
3. Проверить полный путь: stage start → child Work → check failure → repair →
   work finish → native end_turn → следующий coordinator turn → stage finish.
   Повторить с lost response, host gap, crash и поздним completion.
4. Запустить repo-required tests/typecheck/lint/build. В CI добавить сценарии,
   проверяющие контракт и результат, не grep исходного текста реализации.
5. Провести короткие живые smoke управления каждой изменённой упряжкой:
   create/prompt/child/terminal/stop. Локально симулировать потерю наблюдения,
   не усыплять машину с работающим Luna и не разряжать батарею.
6. Коммиты, пуши и релизы — по runbook каждого затронутого репозитория. Собрать
   согласованную пару engine + project flow pack и записать её в input checkpoint.
   Профили harness обновлять только по действительной смене/qualification runtime.
7. Новый ZCode E2E из начального checkpoint, независимо от canonical packs.
   Фиксировать все дефекты, остановиться только на блокере, затем Judge и отчёт.
   Старый EVAL не превращать ручным восстановлением в успешный контрольный прогон.

Готовность: нет дублей операций/проверок; реальная активность продлевает ожидание;
застывший running не делает ожидание вечным; сон не приписан агенту; все процессы
либо подтверждённо закрыты, либо явно учтены как незавершённая очистка; CODE и
CODE-REVIEW принимают один согласованный результат по опубликованной схеме.

## 12. Что изменено относительно первоначального плана

- Убрана неподтверждённая причина «не видим события ребёнка» и ненужная правка
  fanout только ради этого запуска; добавлена доказанная обработка host sleep.
- Недостаточный running-based черновик явно запрещён к публикации.
- Добавлены внутренний timeout ZCode, поздний ответ и обе конкурирующие AGY проверки.
- Добавлены противоположные ошибки stop в Codex и Grok/OpenCode.
- Добавлены expiry живой проверки, захват lease после сна, PID/group identity,
  небезопасное удаление journal lock и потеря деталей ошибок.
- Добавлен фактический конфликт схемы resolutions / resolved_finding_refs.
- Bootstrap уже устанавливает зависимости: вместо повторения install — проверка
  реальной причины, project-owned readiness и общий CODE/MERGE executor.
- Подготовлены проверки отрицательных и crash/suspend путей, а не только happy path.
