# 019. Надёжное выполнение SDLC: пакет системных исправлений

Статус: частично реализуется; изменения ниже ещё не квалифицированы новым
сопоставимым E2E-набором.
Дата: 2026-09-02.
Репозитории: `dd-flow-cli`, `dd-eval`, `dd-memorybank`, `dd-tasks`; `zcode-acp`
и другие упряжки — только при необходимости исправить их собственный контракт.

Документ — единый источник плана исправлений по трём E2E 2026-09-02 и
последующему обсуждению. Дополняет спецификации 008–012, 014, 017, 018.
В части будущего поведения заменяет противоречащие ему правила про абсолютный
таймаут, terminal `blocked`, идентификаторы сессий и освобождение ресурсов.
Не означает, что новые команды уже доступны. Ранбуки переключаются на
реализованный контракт после его проверок, одновременно с выпуском пары.

Журналы, базы и файлы сохраняются под
`$DD_EVAL_HOME/runs/<eval-id>/executions/e2e/`. Старые результаты не
переписываются под новый контракт и не объявляются успешными после исправления
движка. Точечные миграции runtime не меняют исторические доказательства эвала.

Цель: исправить причины, подготовить одну согласованную пару flow/engine и
провести новый сопоставимый набор Luna / Grok / ZCode, SPECIFY → PROTOCOLIZE →
PLAN → PLAN-REVIEW → CODE → CODE-REVIEW → MERGE, с последующей оценкой Judge.
По умолчанию оркестратор продолжает одну сессию; MERGE в этом наборе inline.
Server MERGE также остаётся поддерживаемым и проходит регрессионную проверку.

Не меняем содержательную сложность задачи ради успешности теста. Не меняем
веса оценок, не заставляем повторять смысловое ревью после каждого исправления,
не вводим новый DSL, отдельный планировщик или постоянный сервис уборки.

## 3. Минимальная архитектура и источники истины

| Данные | Владелец и источник истины |
| --- | --- |
| RUN, Work, принятие стадии и результата | `dd-flow-cli`, существующая SQLite |
| История запроса к раннеру и его исхода | существующий `runner-events`, append-only JSONL |
| Native Session и реальная активность | упряжка; адаптер сохраняет наблюдаемые факты |
| Управляемые процессы и владение ими | общий модуль `dd-flow-cli`, SQLite в общем resource home |
| Попытки проверок и подтверждённые результаты | существующее хранилище проверок `dd-flow-cli`, расширенное lifecycle |
| JSON/Markdown/HTML отчёты и индексы | проекции; не второй редактируемый источник |

Переиспользовать `runner-events`, `process-json`, `stage-pause`, `stage-blocker`,
существующие механизмы Work, check receipts и MERGE checkpoint. Не переносить
журнал раннера в новую параллельную operation DB. Registry процессов хранит
владение OS-процессом, а не копию флоу, сессий или токенов.

Общий модуль процессов расположен в `dd-flow-cli`; проверки вызывают его
непосредственно, раннер/адаптеры — через документированную публичную границу
закреплённого движка. Не копировать SQL и алгоритм lease в `dd-eval`, не
импортировать приватные `vnext-*` для обхода CLI. Минимальные операции границы:
запуск/регистрация, наблюдение, остановка и сверка просроченных владельцев;
продление выполняет инфраструктура, а не модель. Окончательные формы команд
фиксируются с контрактными тестами перед переключением вызывающих мест.

Извлечь один выбор следующего действия для live/recovery/reference: второй и
третий пути уже существуют и расходятся. Не создавать framework исполнителей;
выделить обычные функции с явными входами и таблицей переходов.

## 4. Принятие результатов и ссылок

### 4.1 Общий путь

1. Разобрать вход и определить контракт Work и фактический workspace.
2. Проверить схему, назначенные аспекты/критерии, уникальность находок,
   согласованность вердикта и доказательств.
3. Разобрать ссылки одним парсером для PLAN/CODE reviewers и coding/repair Work.
4. При ошибке вернуть все найденные ошибки, не закрывая Work.
5. При успехе атомарно принять нормализованный результат и обновить проекции.

Не записывать невалидный вход поверх принятой проекции. Для диагностики
сохранять отклонённый payload в существующем журнале/каталоге попытки, отдельно
от авторитетного результата. В ошибке указать путь поля, исходное значение,
разрешённые формы, разрешённый корень, ожидаемый/фактический набор аспектов,
состояние Work и точную команду следующего действия.

Схему выбирать из действующей пары и workspace, не случайно из устаревшего
интеграционного checkout. Общий валидатор не должен требовать, чтобы Work уже
был completed: эта проверка относится только к агрегированию результатов.

### 4.2 Ссылки

Поддержать без усложнения внешнего JSON:

```text
src/service.ts
src/service.ts:42
src/service.ts:42-57
src/service.ts:42,51-57,80
run://RUN-001/03-plan/stage-report.json
```

Существующие документированные JSON-fragment формы сохранить и явно описать.
Диапазоны — положительные целые, начало ≤ конца; ошибку не исправлять
угадыванием. Парсер отличает путь, line suffix и fragment; неоднозначные
комбинации отвергает с примером. Пробелы в путях допустимы.

Абсолютный путь внутри известного workspace/RUN преобразуется в относительный
или `run://` кодом. Корни проверяются по реальному пути, включая symlink;
чужой RUN, `..`, выход за корень не принимаются. Не делать глобальный
case-insensitive поиск: точные имена файлов сохраняются, неоднозначность —
ошибка. Короткие системные ID разрешает существующий resolver отдельно от
файловых путей.

При принятии проверять файл и диапазоны относительно рассмотренного материала.
В принятом результате/метаданных хранить идентичность этого материала (путь и
checksum, при необходимости сохранённый исходник в имеющемся evidence-каталоге).
После repair поздний gate проверяет принятые доказательства исходной версии,
а не их номера строк в переписанном файле. Отдельно проверяет новые доказательства
исправления. Это не повторное ревью и не новый полный snapshot репозитория.

Изменение общего workspace другим разрешённым исполнителем не доказывает,
что именно read-only reviewer что-то записал. Сохранить фазу fan-in до repair;
при реальной конкурентной смене входа сообщать input drift и сверять материал,
а не обвинять конкретного агента по одному общему fingerprint.

Ревьюер вправе закончить анализ с находками или указанием препятствия;
успешность исполнения reviewer Work не равна одобрению плана/кода. Оркестратор
должен разобрать препятствие, исправить или приостановить стадию. Нельзя
заставлять ревьюера выдумывать `pass` ради завершения Work.

### 4.3 Повторы и старые результаты

- Повтор finish с тем же нормализованным payload после принятия возвращает
  сохранённый ответ, не выполняя проверки ещё раз.
- Другой payload для принятого Work — понятный conflict, не перезапись.
- Старое уже принятое malformed evidence не правится моделью через SQLite или
  проекции. Для незавершённого RUN возможна только адресная проверяемая миграция
  формата с сохранением оригинала; при смысловой неоднозначности — явное
  восстановление попытки после остановки исполнителя и проверки потребителей.
  Не вводить общую команду `set status` и не переписывать законченный эвал.

Приёмка: воспроизвести список диапазонов Luna и абсолютные внутренние ссылки
Grok; ошибки обнаруживаются в Work, исправленный ответ принимается с первого
повтора, итог стадии не читает расходящиеся копии.

## 5. Единая идентичность сессий

Публичная ссылка:

```json
{"harness_id":"zcode-acp","session_id":"sess_..."}
```

`session_id` всегда opaque native ID. Не добавлять префикс упряжки, не менять
регистр, не выводить его из имени файла. `harness_id` — стабильный namespace
реально выбранной упряжки, не модель и не имя демона.

Работы:

1. Объявить общий тип и соответствующие схемы; ID проектов/RUN/Work не менять.
2. Обновить hooks, work/session bindings, usage, parent links, manifests,
   driver replies, журналы, prompt lookup, MERGE adapter receipts, отчёты/Judge.
3. SQL-сравнения и уникальность учитывают пару, а не только native ID.
   Привязка к проекту/RUN остаётся отдельным отношением, сессия не клонируется
   логически при выполнении следующего Work.
4. Иерархия Work не подменяет native parent Session. Отдельный provider root,
   исполняющий child Work, не становится включённым в usage родителя по догадке.
5. Транспортный `adapter_session_id`, если нужен упряжке, скрыть внутри её
   адаптера; инфраструктура сохраняет его mapping для восстановления. `agent_id`
   остаётся дополнительным реальным фактом, не третьим ID сессии.
6. Удалить временные конструкции вида `harness + ':' + sessionId` во всех
   продуктивных путях, включая незакоммиченный `workerPromptPath`.

Миграция: инвентаризация текущих таблиц/схем → SQLite backup → транзакционное
преобразование по имеющимся harness/native полям → проверка ссылок и уникальности
→ новые проекции. Не разрезать произвольный native ID по `:`. Неоднозначные
записи — отчёт миграции, не догадка. Архивы эвалов читаются по их собственной
версии схемы; не поддерживать бесконечно старые входы нового live-контракта.
Смешанные версии writer/reader отвергаются preflight, а не пишут разные ID.

Приёмка: одинаковый native ID двух упряжек не конфликтует; одна сессия с несколькими
Works не дублирует токены; найден существующий prompt GLM; смена daemon/transport
не меняет identity; native parent и логический parent не смешиваются.

## 6. Состояния и повторяемое завершение

### 6.1 Общие правила

| Событие | Состояние и действие |
| --- | --- |
| Неверный submit | Work остаётся running; исправить вход, повторить finish |
| Проверка не прошла | Сохранить failed receipt; Work/gate не принимать; исправить причину |
| Нужен ответ пользователя | pause; raw answer → resume того же Work/этапа |
| Устранимый runtime blocker | paused Work, blocked выполнение стадии; unblock после ремонта |
| Потерян клиентский ответ | Сверить операцию; wait/получить уже готовый результат |
| Исполнитель действительно умер | Сохранить interrupted/aborted факт; проверить последствия; явное продолжение/новая попытка |
| Пользователь отменил | Запросить остановку дерева; подтвердить результат; затем закрыть логические работы |
| Финальный успех | Все обязательства и дочерние работы завершены; принять один итог |

Удалить terminal `blocked` из активного PLAN-REVIEW finish-контракта; использовать
существующий `stage block/unblock`. Исторический terminal blocked остаётся
историей, не шаблоном новых запусков. HITL никогда не закрывает стадию/Work.

Обновление Work и записи выполнения стадии согласовать транзакцией. Файлы
материализуются из принятого состояния; незаписанная проекция восстанавливается
без повторения семантической операции. RUN running, пока есть выполняющаяся
ветвь; paused не должен скрывать работу соседнего дочернего Work. Статусы
запланированных зависимых Works не означают реальную активность.

Подсказки `start/status/finish/resume/unblock` формируются из одного resolver:
активному этапу — continue/wait, paused — resume/unblock, новому — start,
завершённому — сохранённый результат/легальный следующий этап. В каждой ошибке
есть конкретный scope, состояние, путь доказательств и команда с закреплёнными
`DD_FLOW_HOME`, `DD_FLOW_BIN`, абсолютным project root и коротким WRK-ID.

Проверить paused children, failed/retry, queued dependencies, отмену root и
частично завершённые ветви. Дочерние процессы не «переподвешиваются» к другому
родителю; родитель не завершается с живыми детьми. Retry архивирует артефакты
из фактического stage/work workspace, включая checks, а не из выдуманного
`RUN/works/<id>`; старые попытки сохраняют ссылки на свои доказательства.

### 6.2 Ошибки и поток прогресса

Сохранить конкретные `code`, `message`, `details`, причину и известный исход
операции через CLI → `process-json` → adapter → `runner-events` → отчёт.
Нельзя превращать любой nonzero exit в `flow_reconciliation_failed` или
сохранять в terminal event только текст. Не подбирать recovery по строке stderr.

Сохранить простой wire-контракт: один итоговый JSON в stdout, структурированный
построчный прогресс в stderr; не ломать `--json` потоком нескольких результатов.
События содержат operation/check ID, начало, реальную активность, время
ожидания, завершение и время следующего сообщения. Heartbeat отделён от
полезного прогресса. Вывод не должен расти целиком в памяти; полные логи — файл,
в ответе ограниченный хвост и ссылка. Секреты не попадaют в environment dump.

### 6.3 MERGE и двухфазное завершение

До коммита source проверить target branch/workspace, обе схемы check profile,
эффективные gates, права и необходимые данные запроса. Проверка совместимости
не означает незаметную миграцию файлов target агентом.

Продолжить существующий checkpoint-подход:

1. Сохранить принимаемый вход и исходный набор изменений.
2. Выполнить обязательные проверки/подготовку.
3. Зафиксировать source commit и freeze.
4. Создать один MERGE request/Work транзакционно.
5. Принять завершение предыдущей стадии и вернуть точный следующий шаг.

Повтор после шага 3 берёт принятые paths из freeze, а не из пустого `git status`.
Проверяет HEAD и отсутствие новых непринятых изменений. Сбой между коммитом и
записью freeze требует проверки сохранённого намерения/коммита; нельзя делать
ещё один коммит или объявлять любой HEAD правильным. Сбой после DB commit, но
до проекции/ответа — восстановить ответ. Обеспечить одного владельца операции,
чтобы два finish не запускали одинаковые проверки/коммиты одновременно.

Не обещать exactly-once для произвольного Git/OS действия; при неопределённом
исходе сверять факты. Сохранить единую очередь/lock для inline и server MERGE,
прогресс ожидания и восстановление lease без второго исполнителя.

## 7. Выполнение раннера, восстановление и ожидание

Общий выбор действия использует три факта: состояние dd-flow, наблюдение
упряжки, существующую запись операции. Нормальный запуск, `runner resume`,
reference chain, worker и server MERGE не должны независимо интерпретировать
эти факты. Извлечь повторяемую логику, а не переписать всё одним большим модулем.

- Сохранить существующий operation ID на стороне раннера и довести его до
  управляемого адаптера. При потере клиентского соединения операция остаётся
  наблюдаемой; повторный клиент получает статус/итог, не отправляет новый prompt.
- Native API без идемпотентности: локально сохранить намерение и полученный
  handle, после сбоя сверить native history; если установить исход невозможно,
  остановиться с причиной, а не повторять потенциально выполненный запрос.
- `recordOperation` не пишет terminal failed только из-за утраты наблюдения.
  Отдельное событие observation error не создаёт второй реестр или состояние Work.
- Не выбирать recovery bridge по любому исключению status: timeout связи не
  доказывает смерть исходного daemon. Проверять PID/identity и live handshake;
  недоказанная смерть не разрешает второго writer.
- Охватить cleanup всем периодом от запуска daemon, включая doctor, create,
  profile validation и первую отправку prompt. Ошибка cleanup добавляется к
  исходной, не заменяет её; отказ остановки никогда не игнорируется.
- Освобождать permits по подтверждённому завершению работы, не по выходу
  RPC-клиента. Иначе после timeout фактическая конкурентность превышает лимит.
- Проверять durable prompt/context при подтверждённом `work start`; отсутствие
  binding/prompt — немедленная понятная ошибка, не сюрприз через полчаса.

Политика времени:

1. Нормальный activity window — 10 минут, обновляемое новыми событиями модели,
   инструментов и относящихся к операции детей. Значение в одном разрешённом
   execution setting, не пять разных constants.
2. По истечении окна — inspect с ограниченным временем восстановления связи.
   Это подозрение на отсутствие прогресса, не доказанное зависание.
3. Живой молчаливый tool проверяется по своему deadline/состоянию; повторный
   heartbeat наблюдателя и одинаковые старые события не считаются прогрессом.
4. HITL приостанавливает ожидание активности модели; пользователь не обязан
   ответить за 10 минут. Ошибка авторизации/лимита — отдельный известный исход.
5. Если задействован пользовательский общий бюджет времени/денег, он отдельный
   и явный. Не сохранять скрытый абсолютный 30-минутный предел активной сессии.
6. При доказанной ошибке/отсутствии прогресса выполнить контролируемую остановку
   с фиксацией причины. Пока исход остановки неизвестен, не запускать дубль.

Сохранить уже исправленные правила: live `turn/started` имеет приоритет над
устаревшим persisted `interrupted`; provider terminal не равен завершению Work;
закончившийся reviewer освобождает слот только после окончания хвоста сессии.
Не вводить таблицу Agent Turn: native turn/request IDs могут оставаться
корреляционными фактами журнала.

## 8. Общий реестр управляемых процессов

### 8.1 Хранение и владение

SQLite-файл в `DD_FLOW_RESOURCE_HOME` (например, `runtime.sqlite`); тот же root
используется для всех параллельных запусков. Вне эвала — обычный resource root
dd-flow. Путь фиксируется в manifest/контексте инфраструктуры; не требует
новой переменной окружения. Work/session DB каждого RUN остаётся отдельно.

Запись процесса: внутренний ID, PID + время рождения/boot/host identity,
принадлежащая ему группа/дерево, владелец, lease token/expiry, связанный RUN/Work/
check/operation, состояние, пути журналов, время и причина окончания. Не
складывать в БД секретные argv/env без редактирования. Выдать каталогу/БД
права текущего пользователя. Все конкурентные переходы — условное обновление
по владельцу/token, не слепой UPDATE по PID.

Запуск: starting record → spawn → подтверждение identity → running. Закрыть
окно падения между spawn и регистрацией: исполнитель подтверждает назначение
до продуктивной работы; при отсутствии подтверждения не продолжает бесхозно.
Не использовать name-based `pkill` или убийство произвольного дерева по PID.

Не обещать распределённую транзакцию между RUN DB и общей resource DB:
сначала сохраняется намерение с устойчивым operation/check ID, затем владелец
процесса; при разрыве последовательности reconciliation связывает записи по
этому ID или завершает неподтверждённый запуск. Исполнитель не выполняет
продуктивное действие до принятия назначения. Registry управляет только
процессами, которые система сама запустила; подключение к чужому серверу не
даёт права завершать его при cleanup.

Lease показывает владение, не прогресс. Текущий владелец продлевает его, пока
назначение действительно активно. Короткий CLI-клиент не владелец долгой
проверки: её контролируемый исполнитель переживает разрыв клиента. Сам факт
существования idle daemon не продлевает lease бесконечно. Терминальный запуск
не оставляет намеренно работающие принадлежащие ему daemon/check процессы.

Уборка при запуске/возобновлении раннера и периодически при его работе:
claim просроченной записи → проверить token, владельца и identity → штатная
остановка → ограниченное ожидание → принудительная остановка только своего
процесса при необходимости → проверить смерть → terminal запись и release.
Если identity уже другая, чужой процесс не трогать. Ошибку остановки сохранить,
не писать `stopped=true`. Не пересоздавать удалённый RUN ради уборки.

Без живого контроллера уборка произойдёт при следующем запуске. Постоянный
host supervisor не входит в пакет; добавить только при требовании уборки
независимо от всех запусков. Это известное ограничение, не обещание TTL-магии.

### 8.2 Демоны и упряжки

Один путь закрытия для normal stop, SIGINT/SIGTERM, startup failure и исключений.
Ошибка inspect или flush не отменяет освобождение принадлежащих ресурсов.
Ответ различает «остановка принята» и «остановка подтверждена»; клиент ждёт
подтверждённого конца. Итог содержит первичную и cleanup ошибки отдельно.

Начальная сессия без первого Turn не обязана поддерживать read/subagents;
`Session not found` не означает, что daemon/backend уже выключен. Владение
процессом проверяется независимо от доступности метода истории сессии.

Переиспользовать shutdown дерева в `zcode-acp/src/backend/client.ts`, graceful
handling в `src/index.ts`. Не дублировать убийство групп в каждом уровне.
Проверить аналогичные ветви Grok, Codex, OpenCode, Agy; исправлять общий
consumer-контракт, а native реализацию менять только при подтверждённом дефекте.

Старые демоны: сначала read-only inventory по state-dir/EVAL/identity и
состоянию владельца; затем адресная уборка подтверждённых сирот с протоколом.
Не считать все canonical/reference демоны мусором по возрасту.

## 9. Проверки, переживающие падение клиента

Расширить существующие записи check receipts жизненным циклом; не делать
вторую независимую таблицу «успешных проверок». Попытка: starting → running →
passed/failed/aborted. Номер резервируется атомарно до spawn, с project/run/work
scope; не `COUNT(*) + 1` после завершения. Повтор/конкурентный запуск не
переиспользует каталог логов. Архив Work сохраняет исходные ссылки.

Маленький отдельный исполнитель проверки запускает команду, пишет stdout/
stderr напрямую в файлы и сохраняет exit/result независимо от CLI-клиента.
Сам зарегистрирован в общем process registry. Новый клиент присоединяется к
той же попытке. Никакой shell-команде не приписывается возможность продолжения
с середины: если исполнитель умер без доказанного исхода, попытка aborted,
дальнейший запуск — новая попытка после сверки возможных побочных эффектов.

До запуска сохранить: определение/alias, gate, scope, cwd, профиль проверки,
входной fingerprint, необходимые артефакты, разрешённые параметры среды и
выделенные ресурсы. Check availability/planned provider Work и `depends_on`
проверять как раньше; агент PLAN выбирает смысл и назначение проверок, CLI
не классифицирует их по длине команды или специфике Task Priority.

Управление ресурсами:

- порты принадлежат попытке до подтверждённого выхода использующих их процессов,
  а не до разрыва ожидающего CLI;
- lock-файл без живого владельца очищается тем же механизмом владения, не
  вечным накоплением файлов;
- свободный port probe не гарантирует, что внешний процесс не займёт порт
  между probe и bind; EADDRINUSE обрабатывается как отказ запуска с безопасным
  перевыделением до продуктивной проверки, не как дефект продукта;
- stdout/stderr heartbeat отличается от вывода реально работающего теста;
  hard deadline отдельной команды, если нужен, объявлен явно и не спрятан в
  универсальной константе 15 минут.

Принятие проверки: подтверждён exit, считаны все логи, найдены обязательные
артефакты с hash, проверены запрет незаявленных изменений и входной мир.
Сначала сохранить итог в БД, затем детерминированную JSON-проекцию; после сбоя
между ними восстановить проекцию, не запускать тест. Терминальный результат
попытки не перезаписывать.

Повтор finish в той же незавершённой операции использует принятые проверки
этой операции при совпадающем входе. После реального repair — новая verification
epoch и свежие требуемые проверки, включая browser/readiness. Не считать старый
успех доказательством нового кода. Тяжёлую упавшую проверку не повторять без
изменения причины; но ремонт среды может не менять Git. Учитывать версию
профиля/команды и проверяемые параметры среды; для внешнего ремонта разрешить
явный мотивированный retry новой попыткой, не требовать фиктивной правки кода.

Не смешивать ошибки запуска/среды, failed assertions, отсутствие evidence и
aborted execution. Они требуют разных подсказок. После окончательного CODE
gate repair сохранять контекст исходных Works + точный failure delta;
несоответствие hard boundary эскалировать, soft planned_write_areas не запрещает
нужные изменения. SCN/документация и содержательное закрытие находок обязательны
там, где объявлены; формальный `resolved` без доказательств не принимается.

## 10. Подготовка проекта, профилей и среды

1. Для нового набора взять один исходный checkpoint на базе cp-058 или его
   явно зафиксированного продолжения; Task Priority не должен быть уже
   реализован во входном продукте.
2. Проверить обе рабочие папки: source feature worktree и integration target.
   Схемы политик/проверок должны подходить движку до запуска модели; агент
   не обновляет target для обхода инфраструктурного несоответствия.
3. Исправить Vitest setup/config в `dd-tasks`: уникальный DB namespace на
   проверку/изолированный запуск; reset/migration/API process используют одну
   конфигурацию. Shared PostgreSQL допустим, общий resettable test DB — нет.
4. Браузерный cache/install location согласован для root/worker/check независимо
   от изолированного harness HOME. Не переносить пользовательский HOME целиком
   и не копировать секреты; применять существующую политику worktree/bootstrap.
5. Bootstrap receipt учитывает lockfile/config и проверяемые prerequisites,
   а не только успешный `pnpm bootstrap` с пустым readiness. Не повторять
   installation на каждом Work, если среда действительно проверена и неизменна.
6. Разобрать auth timeout GLM по check logs и воспроизведению. Фиксированный DB
   подтверждён кодом, но его участие в конкретном timeout не доказано. Не
   увеличивать все таймауты тестов и не менять acceptance ради зелёного прогона.
7. Три профиля закрепляют нужные модели/режимы; engine/flow identity берётся из
   существующего SSOT checkpoint/manifest, не копируется вручную во все JSON.
   Проверить observed model, `same_session`, inline MERGE, hook binding и
   изолированные resource roots до продуктивного запуска.

Не переделывать каноническую цепочку ради E2E. Переносимые stage-entry пакеты
обновляются только если изменились сохранённый вход, схема или необходимый
контекст соответствующей стадии. Обычный E2E начинается с исходного проекта.

## 11. Наблюдаемость, статистика и аудит

Один финализатор normal/recovery/failure/cancel:
сохранить исход, сверить живую активность, собрать доступную статистику/журналы,
сохранить доказательства и выполнить cleanup; ошибки каждого шага не стирают
уже полученные данные. Там, где последняя статистика требует живого daemon,
снять её до его закрытия, после окончания productive activity.

### Сессии, usage и время

- Work finish закрывает назначение Work, но не выдумывает terminal native
  session. Один оркестратор может продолжать этапы и Works в той же сессии.
- Снимать usage после фактической остановки активности и повторно по запросу
  всего RUN, включая root, reviewers, coding/repair workers. Нельзя исключать
  failed/cancelled сессии и хвост текста после lifecycle-команды.
- Различать request delta, cumulative physical-session и tree-inclusive
  счётчики. Адаптер сообщает источник и область включения; агрегатор не
  прибавляет детей второй раз к уже включающему их родителю. Упряжки могут
  различаться источником данных, но не трактовкой публичного контракта.
- Источник включает пару session identity, native event/request locator,
  время измерения и время импорта. Повтор импорта идемпотентен по исходному
  событию/снимку, а не новому времени опроса. Сброс cumulative counter — явный
  разрыв ряда, не отрицательные токены или молчаливое обнуление.
- Стадия в общей сессии считается по граничным снимкам/окнам. Сумма непересекающихся
  интервалов не превосходит измеренный итог; перекрывающиеся Work не удваивают
  usage. При отсутствии точной границы показывать ограничение точности, не
  распределять токены выдуманной пропорцией. RUN total доступен независимо.
- Показывать total/input/cache-read/uncached-input/output/reasoning по
  возможностям источника. Reasoning/cache могут входить в другие счётчики;
  не суммировать вложенные метрики. Неизвестное — null/объяснение, не ноль.
- Количество Works, физических Sessions, tool calls и tool failures — разные
  величины. Tool calls дедуплицируются по native ID с областью Session/request;
  вложенный сериализованный transcript не считается второй раз.
- Время RUN — настенные часы, не сумма параллельных работников. Отдельно:
  подготовка, стадии, HITL, ожидание/очередь, проверки, cleanup, Judge. Стадии
  используют lifecycle timeline; interrupted стадия не получает дату успеха.

### Доказательства и отчёт

Граница стадии должна ссылаться на реально сохранённое состояние RUN и
артефактов. Проверить `stage.boundary_captured`: имя события без snapshot/hash
не достаточно. Снимок делается до запуска следующего этапа и при согласованном
состоянии writers; не восстанавливается задним числом из финального дерева.
Сохранять реальные сессии, модель, профиль, источник, flow/engine версии,
запросы и ответы HITL. Не вводить требование абсолютной воспроизводимости
внешних сервисов или полных OS-снимков.

Аудит «целостности раннера» назвать проверкой обхода публичного CLI:

- агентские drafts/results разрешены; SQLite/runtime states, принятые receipts
  и MERGE freeze принадлежат движку;
- read-only чтение runtime/evidence допустимо; `sed -n` не нарушение;
- проверять структурированные вызовы shell и файловых tools, включая дочерние
  журналы, а не только поле `command` root-сессии;
- подтверждённая ручная подмена фиксируется с событием/путём; неизвестная
  семантика произвольного скрипта — материал для Judge, не автоматический verdict;
- выполнять на failed/cancelled/recovered путях тоже; это аудит, не security sandbox.

Большие payloads/повторные tool snapshots хранить как ссылки на исходные логи,
не рекурсивно вкладывать в каждый event. Полезные исходники не теряются;
обычный status/ошибка остаётся компактным и содержит locators.

Не регрессировать недавно исправленный HITL: semantic matching по `hitl-match@1`,
проверка checksum фикстуры, классификация причин отказа, точные answer bytes,
структурированный receipt и `max_rounds` одинаковы в live/recovery/reference.
Повтор доставки принятого ответа не вызывает Judge снова и не расходует ещё
один раунд. Неожиданный или не покрытый ответами вопрос сохраняется как исход
эвалa, без сочинения контроллером новой продуктовой договорённости.

Judge запускается по выбранной политике и получает доступные доказательства
также при неполном прогоне; не выдавать неисполненным стадиям оценку успеха.
Для автоматической оценки неполного результата обновить существующий evidence
packet, без второго типа эвала/классификации «публикуемый». Если Judge запросили,
но заблокирован его запуск, отчёт говорит почему; не писать `not requested`.
JSON, Markdown и HTML используют одну статистику и одинаковые ограничения.

## 12. Промпты, справка и сохраняемые правила

Изменить канон `dd-memorybank/.memory-bank/dd-flow/vnext/`, схемы и
генерируемые start/finish/recovery сообщения CLI одновременно:

- первый lifecycle-вызов стадии — отдельная точная команда, с pinned executable
  и необходимыми env; shell parser всё равно корректно разбирает compound
  команды или явно отказывает, heredoc не переписывается небезопасно;
- `work start` отдаёт задачу, контекст, схему, нормальные непустые примеры
  evidence/review_groups/document_updates, команды finish/pause/block;
- какие файлы подготовлены, что в них заполняет агент, что является проекцией;
- как исправлять отклонённый submit, что делать при проверке/блокере/утрате связи;
- не редактировать runtime DB, принятые результаты и freeze, не импортировать
  приватный engine API ради обхода lifecycle;
- не объявлять работника зависшим по тишине, не отменять работающего ради
  освобождения capacity, не менять назначение reviewer без причины;
- проверять фактический конец сессии перед освобождением одноразового worker;
- CODE verification обязательна, CODE-REVIEW отдельно опционально; качество
  исправления оценивает оркестратор, CLI проверяет только доступные ему факты;
- каталог доказательств разрешён целиком в объявленных границах; не гадать
  минимальный список для каждого reviewer;
- не возвращаться на SPECIFY ради вопроса возникшей стадии; не запускать
  автоматический второй полный круг ревью после устранения находок;
- короткие WRK-ID и точные пути, soft coordination отдельно от hard restrictions.

Capacity probe не делать Work и не регистрировать probe-сессии как продуктивные
Works. Сохранить согласованный алгоритм одной быстрой пачки из 15 попыток
запуска, без добивания до 15 успехов. Проба ждёт 60 секунд и возвращает свой
AGENT-NN; общее ожидание всех проб не превышает 3 минут. Отказ старта из-за
лимита штатный; учитывать подтверждённые старты, отдельно сохраняя завершение,
по deadline останавливать оставшиеся пробы и освобождать слоты. Не замерять
вместо ёмкости упряжки искусственную очередь самого контроллера. Для
обычных reviewers/кодеров — реальный Work start/finish с trusted hook identity.
`depends_on` проверяется до исполнения; `informs` не превращается в жёсткую
зависимость. Предпочтительна одна разумно сгруппированная волна, но не ценой
пропуска аспектов или нарушения зависимостей.

## 13. Последовательность реализации и проверки

Пакеты выполняются последовательно; частичная реализация не заменяет их
приёмочные проверки и не разрешает объявлять новый E2E квалифицированным.

| Пакет | Изменения | Минимальная доказательная проверка |
| --- | --- | --- |
| P0 | Зафиксировать воспроизводящие payloads/последовательности трёх запусков, сохранить текущие пользовательские изменения | Воспроизведение D01/D05/D07/D08/D10 без живых оплачиваемых моделей |
| P1 | Общий валидатор результата/refs, ошибки и idempotent accepted result | Невалидный Work остаётся running; диапазоны/внутренний абсолютный путь принимаются; чужой путь отвергается; повтор не перезаписывает |
| P2 | Пара Session identity и все потребители/миграция | Native ID коллизии двух harness, multiple Work, parent/self/tree usage, recovery lookup, migration rollback |
| P3 | Единые переходы/подсказки, исправление MERGE checkpoint и общих ошибок | HITL/block/paused child; lost reply; target profile failure до commit; crash после commit/перед DB и после DB |
| P4 | Реестр процессов и единое завершение демонов | Startup exception, signal, inspect/flush error, PID reuse, lease race, active sibling, orphan cleanup |
| P5 | Сохраняемые проверки и ресурсы | CLI погиб, check продолжился; executor погиб; лог/exit сохранён; один check при двух клиентах; port release после выхода |
| P6 | Общий live/recovery выбор действия и activity-window | Продуктивный ход дольше прежнего deadline, потеря RPC, молчаливый tool, тишина, HITL, отмена, original daemon всё ещё жив |
| P7 | Изоляция среды, bootstrap, актуальный вход | Два параллельных набора API/browser не делят resettable DB/порты; source/target preflight; reproducible browser prerequisite |
| P8 | Общий финализатор usage/time/evidence/Judge/audit | Tail tokens, inclusive usage, reset counters, partial failure, readonly sed, явная DB-подмена, native edit tool, duplicate journal event |
| P9 | Канон/схемы/start packets/ранбуки/релиз | Схемы и примеры валидны; нет мёртвых recovery-команд; новый engine+pack закреплены; все профили проходят preflight |
| P10 | Контролируемые живые smoke, затем три полных E2E | Прогресс, checkpoints, cleanup, статистика, Judge и отчёт для каждой попытки |

P4 может разрабатываться независимо от P1–P3, но P5 использует P4; P6 зависит
от P2/P3/P4, общий финализатор — от P5/P6. Не включать частично обновлённые
продуктивные callers до совместимой миграции. Публичные контракты и caller tests
меняются одним содержательным пакетом, без долговременных fallback-ветвей.

Тесты дополняют существующие `node --test` и Vitest suites; новый framework не
нужен. Сохранять небольшие регрессионные fixtures, не копировать многомегабайтные
журналы/секреты в Git. Запускать build/typecheck/lint там, где они предусмотрены,
полные suites затронутых репозиториев и targeted межрепозиторные проверки пары.

### Обязательные сбои для испытания

1. Потеря ответа сразу после work/stage acceptance: один принятый результат.
2. Конкурентные одинаковые finish: один check/commit; разные payloads: conflict.
3. Исправление плана с переносом строк/удалением файла после reviewer acceptance.
4. Падение между каждым внешним действием MERGE и его сохранением.
5. `kill` только тестового CLI-клиента проверки: сохранение результата исполнителем.
6. Смерть исполнителя: aborted, не fake pass и не перезапись старых логов.
7. Controller restart во время активной модели/проверки и сразу после terminal.
8. Старый PID повторно занят другим процессом; два cleanup-контроллера одновременно.
9. Невозможность читать ещё не начатую native session при daemon shutdown.
10. Поломка flush журнала при завершении: процесс всё равно убран, ошибка сохранена.
11. Среда исправлена без изменения Git: допустим мотивированный новый check.
12. Модель отправила work finish и продолжила писать: учтён tail, слот не освобождён раньше времени.
13. Разные упряжки с совпавшими native ID; включающий детей usage и отдельные workers.
14. Root остановлен по блокеру: данные всех завершённых стадий и неполной текущей доступны Judge.
15. Ошибка hooks в compound/heredoc, зависимости и отсутствие доступного reviewer slot не создают дубль Work.

## 14. Документация, выпуск и следующий эвал

Обновляемые места:

- `dd-eval/specs/014`, `017`, `018`: identity, observation vs execution,
  lifecycle/recovery, daemon contract; ссылка на 019 без копии полного плана.
- `dd-eval/runbooks/execute-eval.md`: точный обычный запуск, progress, recovery,
  остановка только на блокере, статистика/Judge и уборка также при failure.
- `runbooks/harness-backends.md`, `dd-zcode-daemon-plan.md`, `eval-storage.md`:
  публичная пара identity, процессы/TTL, расположение ресурсов и история.
- Канон flow/схемы и инженерные спецификации `dd-memorybank` (включая SPC-010,
  SPC-011, SPC-012), публичная CLI-справка и generated packets.
- `dd-tasks` engineering policy/check profile/tests/bootstrap; новый исходный
  checkpoint содержит необходимые инфраструктурные исправления, не готовую
  пользовательскую реализацию Task Priority.
- Методика и Judge packets: содержательная оценка отдельно от надёжности,
  время/tokens/tool calls как статистика; ограничения неполного прогона явны.

Выпуск по существующим runbooks: содержательные коммиты по репозиториям →
проверки → публикация нужных пакетов/канона → фиксация фактической пары в SSOT →
проверка установленного исполнения, не только исходников. Не коммитить runtime
логи, БД, секреты, build junk. Не выполнять broad cleanup старых данных.

Перед тремя E2E провести короткие живые проверки управления daemon/check и
восстановления на ограниченных заданиях; не подменять ими полный прогон.
После этого три независимых параллельных запуска на одном исправленном input:
Luna xhigh, Grok 4.6 high, ZCode GLM-5.3-Flash max; Judge Sol high, если
согласованный профиль не изменён пользователем. Реальные точные model IDs
берутся из проверенных текущих профилей, не печатаются наугад.

Следовать обычным пользовательским промптам, без технической подсказки под
конкретную модель/дефект. Фиксировать все отклонения; продолжать при исправимой
ошибке в рамках штатного флоу; останавливать конкретное выполнение при настоящем
блокере. Не чинить SQLite/projections/freeze руками ради зелёного результата.
Независимые соседние эвалы не останавливать автоматически без общей причины.

При неуспехе сохранить частичные результаты и провести доступную оценку,
отметив неисполненные этапы. Не начинать бесконечный цикл новых запусков и
исправлений без доклада. При успехе зафиксировать все семь стадий, MERGE,
сопоставимые метрики и отсутствие принадлежащих попытке сиротских процессов.

## 15. Что изменилось относительно предыдущего плана

1. Закрыт конфликт `blocked` как паузы и как terminal RUN; включены подсказки,
   paused children, отмена и физическое подтверждение остановки.
2. Восстановление больше не начинается с cancel/re-prompt; timeout наблюдения
   не делает продуктивную операцию неуспешной. Существующий журнал переиспользуется.
3. Добавлены общие ошибки: конкретный code/details не теряются в CLI-wrapper
   и `runner-events`; нормальный и восстановленный пути должны совпадать.
4. Уточнён lifecycle checks: отдельный сохраняющий итог исполнитель, резервирование
   ID до spawn, ресурсы до выхода, безопасный retry после ремонта среды без Git.
5. Процессный TTL отделён от активности модели, предусмотрены PID reuse,
   ownership races, startup/cleanup окна и отсутствие вечного само-продления.
6. Принятые ссылки ревью привязаны к исходному материалу; поздний gate не ломает
   старое доказательство после исправления плана. Расширен удобный формат refs.
7. Session migration охватывает все связи и usage; временный prefix patch не
   оставляется вторым способом идентификации.
8. Возвращены обязательные пункты среды, исходного checkpoint, tail usage,
   inclusive counters, времени, фактических checkpoints и Judge при неуспехе.
9. Сохранены предыдущие полезные исправления: HITL semantics/answer bytes,
   hooks/fingerprint, DRY, soft boundaries, SCN/repair evidence, capacity/DAG.
   Они проверяются регрессиями, а не перепроектируются заново.
10. Убраны лишние направления: новый workflow DSL, параллельный operation store,
    agent-owned статистика, обязательный полный canonical rebuild и постоянный
    reaper-сервис. Это применение ponytail без урезания требуемых функций.

## 16. Условие готовности пакета

Пакет готов, когда для D01–D20 есть проверка или явно сохранённый результат
расследования, P0–P9 реализованы и проверены, а P10 дал фактические отчёты трёх
запусков. Успех E2E заявляется только для реально завершившего всю выбранную
цепочку исполнения. Оставшийся blocker не скрывается «подготовкой системы»:
его причина, последнее состояние, живые ресурсы и доступные доказательства
доложены отдельно. У каждого принятого результата один источник истины;
никакое восстановление не требует правки служебной БД моделью.

## 17. Зафиксированное состояние реализации — 2026-09-02

В первом реализованном поднаборе закрыты безопасные основания P2, P4 и часть
P5: внутренний SQLite-ключ Session отделён от публичной пары
`harness_id`/native `session_id`; перед единственной non-additive миграцией
создаётся согласованный SQLite-снимок; есть общий host-level реестр процесса
с lease/PID-start-time/ownership и публичными командами `runtime process`.
ZCode daemon регистрируется до запуска, подтверждает PID, продлевает lease и
закрывает запись при штатной остановке. Незавершённая проверка теперь не
выдаётся за успешную: живой процесс блокирует дубль, мёртвый превращается в
явный `aborted` receipt, доступный для повторного запуска.

Это не заменяет P5–P10: отдельный executor проверки, полный набор crash-window
проверок, канон/релизы, живые smoke и три квалификационных E2E остаются
обязательными до объявления пакета готовым.
