# 056 — CP185: исправления флоу, runtime и EVAL-чекера для трёх упряжек

Дата: 2026-09-29. Ревизия R4 после проверки готовности к реализации: закрыты развилки projection/gates, уточнены process proof и final receipt resolution, добавлены отрицательные и совместимые сценарии. Статус: готов к реализации с обязательными regression/release gates ниже; это не свидетельство, что исправления уже выполнены или новые E2E пройдут. Код по этому плану ещё не менялся. Продолжает [055](055-provider-capacity-same-session-plan.md), не переписывает его исторические результаты и не возобновляет frozen EVAL.

## 1. Область и критерий результата

- Исправляем **dd-flow, dd-eval и их проверки**, а не продукт в scored workspace. Ошибки продукта, неполный PLAN и ошибочные решения CODE/CODE-REVIEW — наблюдаемый результат работы флоу/агента. Их должен обнаруживать и оценивать Final Judge. Не подменять эту оценку ручной правкой продукта или case-specific кодом, который «чинит» решение агента.
- Grok `EVAL-20260928233624-8d5c2012` остановился из-за native HTTP 402 `Grok Build usage balance exhausted`, не из-за `serverOverloaded`. Лимит, по сообщению пользователя, действует до 2026-10-02. Grok временно выведен из текущей работы: ни preflight, ни scored запусков, ни отдельного Grok-исправления до подтверждения доступности после указанной даты. Старый EVAL остаётся frozen; уже написанный `63a608f` может находиться в общем engine release, но не служит поводом сейчас запускать Grok. Не придумывать `reset_at` по сообщению пользователя как provider timestamp.
- Целевая матрица этой итерации: **Luna, AGY, ZCode**, отдельные новые home и scored EVAL на одном pinned release/case checkpoint, Judge `gpt-6-sol/high`. Технический full cycle означает SPECIFY → PROTOCOLIZE → PLAN → PLAN-REVIEW → CODE → CODE-REVIEW → MERGE, затем Final Judge, case acceptance и clean settlement. Это отдельно от продуктового PASS: полный EVAL с отрицательным выводом Judge остаётся валидным измерением, а не поводом вручную править кандидат.
- CP185: Luna `EVAL-20260928230857-7a8aed69` остановилась в CODE из-за преждевременного browser check; AGY `EVAL-20260928232715-7474bbe2` — на MERGE boundary capture; ZCode `EVAL-20260928231707-9f4c550e` дошёл до MERGE/Final Judge, но продуктовая приёмка отрицательная. Исторические отчёты не пересчитывать и не «исправлять» задним числом.

В `dd-eval/lib` второй реализации case checker с жёстким PRT-суффиксом не обнаружено. Это разделение исключает массовую замену локальных гардов и универсальный парсер как неоправданные «системные» фиксы.

## 3. Реализация в dd-flow

### P1. Один смысл ссылок на check от PLAN до CODE

1. Сохранить существующий carrier `packet.checks`, без нового каталога/схемы packet и без чтения mutable PLAN из CODE. В `vnext-plan.ts` один projection helper оставляет item-local refs плюс refs связанных AC **только для non-work checks**. Таким образом `run_at=work` попадает в packet только из `item.verification.check_refs`, а acceptance-only CODE/readiness/merge declarations продолжают доходить до CODE, CODE-REVIEW и repair. Контекст AC остаётся полным. В `renderCodeTask` и общих PLAN/Work инструкциях различать Work-local исполнение и последующий aggregate gate: нельзя текстом требовать от P1 немедленно выполнить проверки P2, даже если их ID присутствует в контексте общего AC. Существующий тест `vnext-protocolize.test.ts:524–561` сохранить. MERGE уже читает весь PLAN catalog — его путь не переписывать.
2. В PLAN validation проверять planned-provider ancestry у фактического исполнителя **work check**, назначенного через `item.verification`. Non-work gate запускается после CODE Works: не требовать искусственной P1→P2 зависимости только из-за общей ссылки на aggregate check. Каждый `run_at=work`, на который ссылается AC, должен иметь явное назначение хотя бы одному item этого PLAN; исполнитель не обязан входить в `AC.plan_item_ids` — отдельный verification Work допустим. Для current CODE acceptance дедлайн `work|code|readiness` один: финальный CODE gate; разрешённый check тоже `work|code|readiness`. Для AC `merge` разрешены предыдущие gates и `merge`; `release` позже всех. Проверять **каждый** ref, поскольку критерий требует все refs, а не хотя бы один. Для `merge_completed` отклонять и check, и AC с `release`, даже если они нигде не используются. Не вводить RELEASE executor и не превращать gate `work` в новый ранний AC barrier, которого сейчас нет.
3. Отклонять дубликат `criterion_id` внутри одного PLAN. Межпротокольные вклады не терять: в `verificationProjection` группировать по `(criterion_id, gate)`, объединять refs и evidence; одинаковые копии из нескольких Work/repair packets идемпотентны. Разные gates общего AC сохранять отдельными вкладами: ранний unresolved блокирует CODE, поздний остаётся not_due; не заставлять все протоколы искусственно выбирать один gate. Stage report может содержать несколько записей одного AC с разными gate; проверить всех читателей этой проекции (CODE finish/report, CODE-REVIEW, тесты), отсутствие first-wins и сохранность всех refs. MERGE проверяет все namespaced declarations, поэтому поздний вклад не теряется. Это заменяет неопределённое «отклонять несовместимые gates» из R3.
4. Регрессии: P1 API → P2 browser с общим AC и обязательными PNG; P2-provided planned check у общего AC; acceptance-only readiness; orphan work check; ранний AC с MERGE/RELEASE check; merge AC с RELEASE check; дубль AC в одном PLAN; общий AC двух протоколов (один check отсутствует → unresolved, оба passed → confirmed). Проверять **реальные generated packets и Work finish**, не только вспомогательную функцию. Не ослаблять missing-artifact failure.

### P2. Точное terminal proof сейчас; инвариантная PID identity для общего пути

1. Исправить `18df7d6` для нынешних записей: один небольшой predicate `terminalCheckSettled` в существующем `code-checks.ts` проверяет exact `kind`, role, `owner_id=check:<check_id>`, project/run/work/check ID, terminal process с сохранённой физической identity и terminal DB receipt того же check в **его RUN DB**. В check receipt **нет lease/PID birth**: не планировать сравнение несуществующих полей. Lease/PID/metadata проверять повторным чтением самой resource registration перед принятием proof; неоднозначные registrations того же check не принимать. Убрать `receipt.finished_at >= process.finished_at`: normal и reconciled paths сохраняют разные причинно допустимые времена. Различать terminal/settled и passed: failed/aborted receipt также допускает settlement, но не успех check. Проверить normal/reconcile/catch/stop paths: receipt без terminal registration, один completion marker, истёкшая lease или terminal registration без receipt сами по себе этот shortcut не разрешают. `run-control.ts` применяет predicate до повторной физической проверки.
2. В `runtime-scope-stop.ts` для terminal check принимать прежнее доказательство `!processTreeIsAlive(record)` **или** тот же exact receipt. Второе нужно потому, что EVAL cancellation идёт из `control-runtime`, а check receipt находится в RUN-home: брать home из точной process registration через `managedProcessRuntimeHome`, валидировать scope/project/run и открыть DB в `read_existing` без создания. При чужом/missing home или receipt оставлять прежний консервативный результат. Не переносить predicate в `managed-processes.ts`: его resource registry не владеет RUN check receipts, а `code-checks.ts` уже является общим владельцем check semantics.
   - `managedProcessRuntimeHome` возвращает absolute metadata home, но не доказывает его содержимое. Сверить RUN/project/work receipt с registration, runtime scope из budget inventory и существующую DB, не fallback на caller control-runtime с такими же локальными `PRJ-001/RUN-001`. Открытые helper-owned read handles закрывать в `finally`; caller-owned DB не закрывать. Ошибка открытия/чтения = отсутствие proof с причиной, не создание/migration пустой базы. Повторно проверить binding перед возвратом completed; гонка смены lease/metadata означает pending, не чужой terminal outcome.
3. Pre-terminal sibling включён в обязательную реализацию, а не оставлен неопределённым исследованием. Добавить в существующий `metadata_json` новый versioned birth token `ps-lstart-utc-c@1`, снятый с `TZ=UTC`, `LC_ALL=C`; legacy `pid_started_at` не мигрировать и не переинтерпретировать. Снимать токен в register/confirm, включая self-register observer, и для owner при его регистрации; внешние `ps` выполнять до writer transaction. Одна общая identity comparison используется в managed liveness и сигнализации; для новых записей не смешивать invariant сравнение с raw legacy строкой. Только достоверное различие нового токена у **живого PID** и `PGID=PID` позволяет признать старую группу чужой. PID отсутствует → проверить leaderless group; `PGID!=PID`, неизвестный формат, ошибка/timeout/permission чтения, одинаковый токен с секундной точностью → не применять shortcut. Ни одного сигнала при mismatch/unknown identity. Legacy сохраняет консервативный путь; это известное ограничение, не основание менять frozen EVAL. Рефакторинг не должен добавлять subprocess/network I/O под SQLite writer.
   - Отдельно проверить места, которые собирают урезанный `{pid, pid_started_at}`: observer admission и `managedOwnerIsAlive` не должны терять новый marker и незаметно возвращаться к legacy сравнению. Token формирует runtime, а не caller metadata; неизвестный/подложенный формат не даёт ownership proof. В cancellation inventory повторная проверка должна учитывать identity metadata наряду с lease/PID. Не расширять вторую систему учёта владельцев — это поля существующей registration.
4. Для native-history использовать тот же общий новый identity path и сохранить существующее exact clean native proof/owner matching. Отдельного исключения «clean значит можно игнорировать любую живую группу» не добавлять. Тест archive с новым invariant token должен закрыть recycled-PGID sibling; legacy archive без достаточной identity может остаться unsettled с точной причиной. Не ослаблять live/unclean/unknown daemon guard. Если адресный тест обнаружит, что новый общий path недостаточен, это **release blocker P2**, требующий уточнения плана, а не разрешение незаметно пропустить пункт.
5. Тесты: normal/reconciled check с более ранним native `finished_at`; terminal check и чужая живая группа; `runtime scope stop` из другого EVAL control-runtime, неверный RUN-home/lease/receipt; pre-terminal completion, лидер исчез, но настоящий потомок старой группы ещё жив; одинаковый живой PID при разных `TZ` и locale; новый PID с доказанно другим invariant birth; native archive clean/unclean. Переписать два теста, симулирующих физически невозможное повторное использование PID при живой старой группе (`managed-processes.test.ts:263`, `run-controller.test.ts:474`), сохранив отдельный тест на живую leaderless-группу. Проверять и отсутствие ложного settlement, и отсутствие сигнала чужому процессу.

## 4. Реализация в dd-eval

### P3. Case acceptance v2 без фиктивных gaps и stale proof

1. Оставить `task-priority@1` с прежним сериализуемым результатом для пересчёта старых immutable receipts (`runner.mjs:1388–1393`). Для новых case definition/checkpoint ввести `task-priority@2`; не применять его к CP185. Envelope `dd-eval/case-acceptance@1` можно сохранить: новые факты входят в существующий `facts`, версия алгоритма — поле `checker`. В frozen boundary брать точные `protocol_id` из `03-plan/code-work-batch.json.sources`, сверять множество с `02-protocolize/stage-report.json.semantic.acceptance` и финальным MERGE protocols; сверять `plan_id`, `protocol_id`, revision и raw-file SHA256 каждого PLAN. Это поддерживает разные суффиксы и split PSET без поиска по строке `priority`. Привязка AC — по accepted SPECIFY/PROTOCOLIZE ownership этого RUN, не по номерам/названиям. Отсутствие/неоднозначность identity — `unavailable`; идентифицированный PLAN без обязательных AC — `failed`. Не считать «пустой набор выбранных протоколов» успешной проверкой.
2. Собрать критерии всех участвующих PLAN без first-wins. Матрица должна явно покрывать эти протоколы и `SCN-002` в требуемом local contour; один общий row может покрывать несколько явно перечисленных protocol IDs, если документ их действительно связывает. Не требовать отдельную строку на каждый Work/AC. ## 6. Проверка по `$ponytail`

- Не создавать универсальный retry/settlement framework. Новый token закрывает достижимый pre-terminal sibling в общем predicate, без SQL migration и provider-specific обходов; legacy не мигрировать догадкой. Native-history сохраняет своё clean proof, отдельный exemption не добавляется.
- Не писать case-specific алгоритм исправления ZCode-продукта, не заставлять mechanical checker оценивать бизнес-семантику вместо Judge и не переписывать Judge prompt без доказанного пробела. Существующий Judge уже обнаружил материальные дефекты.
- Сохранить существующий packet carrier и aggregate consumers; не добавлять новый каталог и **не** удалять acceptance-only aggregate checks ради меньшего diff.
