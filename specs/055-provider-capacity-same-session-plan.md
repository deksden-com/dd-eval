# 055 — перегрузка модели: ограниченное продолжение той же Session

Дата: 2026-09-28. Ревизия: **R4 — реализация, release и CP185 scored matrix выполнены; full-cycle цель матрицей не подтверждена**. Дополняет [054](054-cp173-179-post-e2e-repair-plan.md) и не меняет frozen EVAL. Область — подтверждённый Codex `serverOverloaded` (включая Codex Judge у остальных упряжек) и отдельно исчерпанная квота. Это не разрешение повторять произвольные ошибки или lifecycle-команды.

R2 проверена по dd-flow `4f3a8344c56c5df5c9149b68760f6e8230b2e637` (beta.119), dd-eval `0ab3f7a30d788e6350b6fee935e2b930c94edeb5`, локальным исходникам Codex `40eac3ce8a`. Последние объясняют протокол, но не считаются доказательством совпадения с установленным бинарём. Перед реализацией сверить актуальные commits и сохранить чужие изменения.

Ранее [052, P7c](052-cp157-158-systemic-runtime-repair-plan.md) откладывал bounded retry до отдельного проекта и ограничивал безопасный случай Judge до выдачи HITL-ответа. Этот план закрывает именно оставленную развилку и добавляет обнаруженные sibling paths. Реализованные в 054 исправления модели, tool evidence, acceptance, fixture и startup здесь не переизобретаются; их release/qualification остаются входными gates для нового E2E.

## 1. Факты и решения, согласованные до этого аудита

- В ZCode CP-184 `EVAL-20260928150631-51622a95` Interaction Judge получил native `error.codexErrorInfo=serverOverloaded`, `willRetry=false`, затем terminal `turn.status=failed` с тем же кодом. В том turn не было assistant/tool items; HITL-ответ Subject не отправлен. Один `session.prompt` завершил попытку.
- В Luna CP-184 `EVAL-20260928150054-037e9c38` ошибка перегрузки возникла в продуктивном CODE, включая child. До неё были native tool/file-change events; слепое повторение исходного Stage/Work prompt или lifecycle command может удвоить эффект. Нужна сверка RUN/Work/native tree перед продолжением.
- `dd-codex.mjs` умеет отправлять новый `turn/start` с прежним `sessionId`; `dd-codex-daemon.mjs` освобождает `active` после завершения prompt. В исходниках Codex `app-server/src/thread_status.rs` метод `note_turn_started` сбрасывает `has_system_error`; тест `system_error_sets_idle_flag_until_next_turn` прямо проверяет этот переход. `turn_processor.rs` не запрещает root turn из-за `systemError`. Совместимость установленного бинаря проверяется детерминированной native пробой P0, без ожидания случайной перегрузки живого провайдера.
- Общий RUN recovery уже умеет продолжать сохранённую Session через fenced recovery с новым daemon и проверкой генерации. Продолжение после перегрузки при ещё живом владельце выполняется **до** sealing; это обычный следующий turn, которому recovery ACK не нужен. После sealing разрешён только существующий recovery-контракт. Эти два режима в R1 были описаны недостаточно раздельно.
- Пользовательское правило: при **перегрузке** дать короткое «продолжай» в *той же* Session, ограниченно и с backoff; при **исчерпанной квоте** завершить текущую EVAL-задачу ошибкой, не ждать часы. Время сброса показывать только при достоверном provider timestamp для соответствующего лимита. `Retry-After` означает время, раньше которого не следует повторять запрос, и само по себе **не доказывает время сброса квоты**.

## 3. План реализации

### P0. Совместимость и точная классификация

1. Зафиксировать native vector из CP-184: matching `threadId`/`turnId`, terminal `failed`, `codexErrorInfo=serverOverloaded`; `willRetry=false` сохранить как diagnostic, но его отсутствие в terminal snapshot не блокирует продолжение. Пока native сам повторяет и terminal outcome отсутствует, новый turn не отправлять. Fake app-server покрывает adapter; отдельная проба **установленного Codex binary** с изолированным home и localhost mock Responses endpoint проверяет настоящий переход: mock сначала отдаёт 503 с `error.code=server_is_overloaded`, затем successful response. Такое отображение ошибки подтверждено `codex-api/src/api_bridge.rs` и `core/tests/suite/retry_after.rs`. Проба не использует реальные credentials, production proxy и scored homes. Проверить второй turn той же thread, cwd, model и сохранение контекста. Если binary отвергает продолжение — точный blocker, без скрытой замены Session. Случайная внешняя перегрузка больше не является обязательным условием теста.
2. В уже существующих error records/adapter cause сохранить structured `codexErrorInfo`, provider message, native thread/turn и terminal status до EVAL report. Один контракт распознавания, с маленькими реализациями там, где dd-flow и dd-eval не делят модуль: `terminalCodexOverload` принимает только подтверждённый terminal native факт; не полагаться на слова `capacity`, HTTP 5xx или вложенный код без identity/settlement. Отделить **причину** от **разрешения продолжить**: второе проверяет владелец. Общие contract vectors не требуют нового package.
3. Cause extractor читает только известные error envelopes (`cause`, `details.cause`, retained primary), с ограничением глубины. Подтверждённый hook/lifecycle/storage/ownership primary побеждает сопутствующую перегрузку. Не искать разрешающий код в произвольном содержимом tool output или assistant text. Native `usageLimitExceeded` — quota; `rateLimitExceeded` — rate limit; `sessionBudgetExceeded` — отдельный бюджет Session, без overload continuation. Сохранить первичную ошибку и сериализуемый cleanup detail до report; время сброса не выводить из null/чужого bucket.

### P1. Judge: минимальный локальный same-Session retry

1. В двух Judge callers использовать одну небольшую функцию продолжения Codex Session, вызываемую только до `daemon.stop`. Три turn максимум: исходный + два коротких continuation, паузы 5 и 15 секунд. Это выбранные defaults данного плана. Existing qualification timeout относится ко **всей логической Judge operation**: deadline вычислить один раз, каждый wait/turn получает остаток, а не заново 600 секунд. Для продуктивного RUN новый watchdog не вводить. Тот же `sessionId`, model/profile, cwd, packet/candidate hash и daemon. На каждый turn — новый operation ID, запись связи с первоначальным prompt и ordinal в существующем client ledger/journal. Один native journal может хранить все turns.
2. Перед каждым новым turn проверить terminal failed outcome, ту же Session, отсутствие active operation и release predecessor budget через session.inspect. Локальный semaphore отпускать между attempts, затем снова получать через `permits.use`; после ожидания permit и сразу перед dispatch повторять EVAL/RUN admission. Delay должен реагировать на stop; cancel/новая generation во время delay или очереди исключает отправку нового prompt. Timeout/connection loss/invalid JSON/fixture gap/auth/quota не продолжаются. Если все попытки перегружены — сохранить исходную и последнюю ошибки, attempts и stop reason. При смене причины на quota/auth primary итогового отказа — новая причина, а overload остаётся в истории.
3. Продолжение ссылается на **прежний путь packet**, hash которого проверен: «Продолжай предыдущую задачу; прочитай тот же packet; верни только требуемый JSON». После первой перегрузки packet мог ещё ни разу не быть прочитан; доказательства предыдущего чтения не требовать. Обычная native compaction допустима, требование byte-for-byte неизменной истории не вводить. Assistant output брать по новому успешному `turn_id`, при необходимости гидратировать именно его items. Старый top-level assistant message и частичный ответ failed turn не использовать. Один итоговый receipt и один HITL answer; schema/semantic invalidity не запускает capacity retry.
4. Если у exact overload есть достоверный `Retry-After`, использовать не меньшую задержку, чем 5/15 секунд и этот срок. Без такого metadata — defaults; не извлекать его из произвольного текста. Не ждать неограниченно: автоматический backoff одной попытки ограничен 30 секундами и оставшимся caller deadline. Если требуемое ожидание больше, завершить существующим failure/recovery с причиной `retry_after_exceeds_budget`, сохранив overload и рекомендуемый срок. Предел применяется и к P2; он не является новым watchdog всей продуктивной работы.

### P2. Продуктивный RUN, external Work и MERGE

1. После exact overload не переходить немедленно в recovery_required: сначала сверить durable daemon operation, native tree settlement, controller/worker/merge owner, PID/lease, RUN generation, HITL pause и текущие Work/Stage/merge receipts. Никаких провайдерских вызовов/задержек под SQLite writer transaction. Ошибка одного child не равна успеху Work; живой или unknown child запрещает второй prompt, пока не reconciled.
2. Если состояние согласовано, создать **новую** записанную prompt operation (не повтор старого ID), подождать 5/15 секунд и продолжить прежнюю Session. Текст continuation определяется существующим RUN continuation/Work graph/merge состоянием и общей lifecycle-инструкцией; он требует сверить выполненные действия и запрещает без exact issued successor повторять `stage start/finish`, `work start/finish`, HITL answer, checks и merge apply. Не отправлять исходный launch/stage prompt повторно. Если нет законного continuation или эффект команды неясен — сохранить старую recovery_required/capture policy.
3. Лимит тот же — максимум два дополнительных native turns на одну overload-цепочку. Счётчик/связь попыток хранить в существующих `run_controller_operations`, `work_launches.adapter_receipt_json`, `merge_requests.adapter_receipt_json` и native operation/event journals; после crash новый владелец **не** сбрасывает лимит и не делает слепой auto-retry. Восстановление через уже существующий sealed recovery с тем же native Session и exact ACK. При повторной перегрузке recovery ACK не рекурсировать.
4. Не переносить этот механизм в низкоуровневый `runHarnessAdapter`: он не знает, сделал ли Subject файл, Work, HITL или MERGE. Общим остаётся только predicate/формат cause и краткая инструкция; решение о новом turn остаётся у конкретного владельца. Это закрывает три sibling dispatch paths без ложной общей семантики.

#### P2a. Порядок перехода и защита от повторной отправки

Порядок обязателен для каждого owner path, а не только для happy path controller:

1. Получить terminal cause и точные Session/Turn/operation IDs. Исключить более приоритетную lifecycle/hook/storage/ownership ошибку; ошибка tool сама по себе не даёт разрешения.
2. Через native inspection установить отсутствие выполняющегося predecessor и reconcile budget reservation. Failed daemon operation **остаётся failed** в журнале; нельзя переписать её в completed ради освобождения слота. Новая попытка — отдельный факт. При живом native tree не объявлять его settled и не освобождать reservation по одному terminal root turn.
3. Считать свежие RUN/Work/HITL/MERGE receipts и выбрать действие по таблице ниже.
4. Короткой существующей owner transaction записать intent: chain/root operation, predecessor operation и turn, Session ID, ordinal, generation, prompt hash, `not_before`. Operation ID детерминированно выводится из chain и ordinal; повторный наблюдатель читает существующую операцию, а не порождает новый ID. Использовать существующие записи/JSON receipts; новая таблица retry не нужна.
5. Backoff выполнять вне transaction и provider semaphore. После ожидания/получения permit заново проверить admission, generation, отмену и native settlement. Изменившееся состояние требует reconciliation, а не отправки устаревшего prompt.
6. Dispatch через существующий durable journal. При crash после intent, dispatch или native success сначала inspect journal/native outcome. Неизвестный результат не допускает повторной отправки. Нельзя обещать exactly-once сеть: обеспечиваем отсутствие слепого дубля и fail-closed на неопределённом исходе.
7. Записать связь attempts/result. Сбой владельца не обнуляет ordinal; sealed recovery не создаёт новую бесконечную overload-цепочку. Успешный turn завершает цепочку; следующая самостоятельная controller operation имеет собственный предел. Неуспешный parent followup без фактического child dispatch не должен считаться успехом и запускать неограниченный цикл.

Старые receipts без chain metadata остаются читаемыми. Не присваивать им молча ordinal=0 и не возобновлять исторические failures: автоматическая цепочка создаётся только для новой поддерживаемой операции текущего владельца. Если история после crash не позволяет однозначно восстановить attempt, применяется существующий recovery/failure. При одновременной перегрузке root и child один parent continuation расходует один root attempt, фактический child followup — один child attempt; ни один счётчик не сбрасывается успехом другого. Число child-цепочек ограничено уже существующим графом, новые children retry-механизм не создаёт.

| Durable состояние после ошибки | Действие |
| --- | --- |
| Stage/Work/MERGE уже законно завершён, эффект подтверждён receipts | Не посылать лишний prompt для завершённой задачи; штатно обработать результат/следующий Stage, сохранить incident в evidence. Ошибка native turn не аннулируется и не считается сама по себе успешным Work. |
| Новый HITL pause, принятого ответа нет | Штатное ожидание HITL; никакого автоматического ответа под видом capacity continuation. |
| Задача не завершена, эффекты известны, предшественник settled, owner действителен | Ограниченное продолжение той же Session по текущему состоянию. |
| Живой/unknown child, неизвестный эффект команды, утрата ownership | Не отправлять второй prompt; reconcile/observe в пределах действующего контракта, затем существующий recovery/failure при невозможности доказать допуск. Не вводить бесконечное ожидание. |

Пока допустимое продолжение ожидает/исполняется, owner не публикует terminal failure, из-за которого EVAL успеет отменить дерево. Публикуется non-terminal событие попытки; terminal failure — после исчерпания лимита или появления иной блокирующей причины. При живом владельце не перезапускать daemon и не повышать recovery generation ради перегрузки.

#### P2b. Native children и принятый HITL

- Решение по child overload принимается **до** `reconcileVnextFanout → failWork`. Расширить `controllerNativeChildren` точными terminal Turn ID/error, а не делать вывод из одного `status=failed`. Сохранить существующую WorkSession; terminal Work никогда не открывать заново. При неопознанной причине и при исчерпании лимита оставить обычный failWork.
- Обработать три разных случая: root overloaded; root успешно закончил turn, но child overloaded; root и child overloaded одновременно. Не отправлять два конкурентных root продолжения: одно решение owner объединяет необходимые действия для того же tree. Если root ещё работает, не вмешиваться вторым turn; наблюдать его естественное разрешение child и заново сверить факты.
- В используемом Codex multi-agent v2 продолжать child через **родителя** и native `followup_task` с прежним child ID. Не делать запрещённый прямой app-server `turn/start` в child и не заменять child новым spawn. Native capability подтвердить в P0; alternative tool для иной версии допустим только после её квалификации. Общая lifecycle-инструкция остаётся в существующем `delegation-instructions.mjs`, harness-блок называет только конкретный native инструмент.
- Допуск parent turn и освобождение budget требуют settlement всего затронутого дерева. Не вычитать живых siblings из reservation. Если child ещё не успел выполнить Work start, не угадывать Work binding по тексту: сохранить native parent/child identity; нормальный Work admission всё равно обязателен. Лимит child-цепочки привязан к исходной child задаче и не сбрасывается от parent turn. Parent mediation также ограничена исходными двумя continuation attempts; отсутствие подтверждения native followup не запускает новую цепочку автоматически.
- Исправить `CodexBridge.observeTopology`: terminal монотонность действует в пределах **Turn**, не всей Session. Новый подтверждённый turn делает тот же child running; поздний completed старого turn не закрывает новый. Если activity event не имеет Turn ID, уточнить текущий turn native inspection, а не сбрасывать completed по любому позднему started. Переписать тест, который сейчас закрепляет вечный completed.
- Для accepted HITL continuation хранить reference на исходный answer operation, pause, answer hash и generation. `controllerHitlAdmission` должен допускать только зарегистрированного successor этого accepted answer, а не произвольный новый ID с похожим suffix. Если stage resume ещё не выполнен, продолжение доставляет **тот же** принятый intent через штатную команду; если resume уже committed — не повторяет ответ, а работает с новым состоянием; если возник другой pause — старый ответ к нему неприменим. Ровно один delivery receipt и одно принятие ответа. Изменение prompt hash successor не изменяет hash принятого ответа.

### P3. Quota и отчёт

1. Точный hard quota/credit/billing outcome во всех harnesses завершает EVAL failure; не ставить таймер до сброса и не запускать новую scored попытку. Отличать rate-limit с известным сроком от исчерпанной квоты и от `serverOverloaded`; ambiguous 429 без reset не считать ни подтверждённой квотой, ни разрешением на replay. Проверить порядок распознавания смешанных сообщений в ZCode/OpenCode и не терять structured native body в AGY/прочих адаптерах.
2. Нормализовать в EVAL error report `category=provider_quota`, provider identity, message, время наблюдения и `reset_at` **только** из проверенного structured provider field/header соответствующего лимита. Сохранять UTC ISO timestamp, источник, наблюдение и bucket, если он известен. Если timestamp отсутствует или относится к другому bucket — `reset_at=null`, «неизвестно». `Retry-After` хранить отдельно как `retry_after_at`, не как quota reset. Не угадывать дату из свободного текста и не запрашивать лимиты другого аккаунта. Прошедшая дата сама по себе не разрешает повтор quota failure. Информационный `retryable` старого adapter не превращать в `retry_now`; автоматическое действие задаётся явным узким predicate, старые records остаются читаемыми.
3. Исключить quota, account/auth, invalid JSON, fixture gap, user HITL, cancellation, observation loss и неопределённый side effect из overload-пути. Никакого перехода на другую модель/провайдера в frozen scored EVAL.
4. Сохранить primary cause и secondary cleanup в сериализуемых `details`, а не произвольном свойстве Error, которое теряет `errorRecord`. External Work/MERGE receipts не должны ограничиваться `String(error)`. Для exhausted overload показать исходную/последнюю причины и attempts; если последняя причина — quota/auth, именно она объясняет окончательную остановку. В status во время backoff показывать non-terminal `capacity continuation 1/2`, не ложный terminal error. Проверить report/failureEvidenceRevision projection: существенный normalized cause/reset metadata входит в evidence, тикающий countdown не создаёт новую revision каждую секунду.

## 4. Проверки и порядок поставки

| Gate | Обязательная проверка |
| --- | --- |
| Native/adapters | Один failed Codex turn, затем successful second turn с тем же Session ID и новым Turn/operation ID; mismatched identity, active predecessor, duplicate result, lost socket, quota, auth и иной `systemError` не продолжаются. Проверить сохранение структурированного cause через `harness_adapter_failed` и EVAL classifier. |
| Judge | Fake driver: перегрузка→success на второй/третий turn; три перегрузки→failure; quota→один turn; cancel во время backoff; invalid JSON→без повтора; immutable packet/profile; ровно один HITL answer/final receipt; cleanup failure не перекрывает primary. Квалификация HITL идёт через тот же код. |
| Productive | Для controller, external Work и MERGE отдельно: error до tool, после file/CLI effects, active/unknown child, settled failed child, accepted HITL, stale generation/lease, crash между terminal event и записью попытки. Проверять точные Work/Stage/merge receipts и отсутствие повторной lifecycle-команды, а не только число вызовов. |
| Integration | Запустить существующие dd-flow native/controller/external/merge tests и dd-eval `eval`, `runner-recovery`, `e2e-reliability`, capacity-qualification tests; typecheck/build. Затем non-scored same-Session protocol probe и release/qualification с exact pinned engine. Новые scored четыре E2E — только после этих gates, со свежими homes; старые CP-184 не переписывать. Успешный E2E без перегрузки не заменяет адресную regression. |

Обязательные дополнительные R2 vectors:

- Budget=1: failed predecessor reservation действительно освобождена observation proof, следующий turn допускается; при живом sibling она не освобождается преждевременно.
- Native retry ещё идёт / terminal event пришёл дважды / старый Turn ID / чужой thread / nested tool text с `serverOverloaded`: никакого ложного нового turn.
- Root success + child overload; root+child overload; completed child → новый running turn → поздний completed старого turn. Child direct input запрещён; parent followup сохраняет identity. Неудавшийся parent followup не обнуляет предел.
- Accepted HITL до resume, после committed resume и после нового pause; exact admitted successor; один ответ. Overload после durable Stage/Work/MERGE finish не вызывает повтор finish/apply.
- Cancel/stale generation во время delay **и очереди permit**; crash до intent, после intent, после dispatch и после success до receipt; единый ordinal и отсутствие слепого дубликата.
- Judge: старый valid JSON в history + failed partial JSON + новый успешный ответ; принимается только новый turn. Deadline не начинается заново; просроченный deadline запрещает следующий turn. Packet ещё не прочитан при первой ошибке — продолжение всё равно возможно.
- Overload → quota/auth, failed prompt + cleanup failure, mixed quota+429, отсутствующий/невалидный/прошедший reset, секунды против миллисекунд, Retry-After delta/date. Primary/secondary и unknown reset сохраняются после сериализации.
- Retry-After меньше/больше default, больше 30 секунд или остатка deadline; legacy receipt без chain; неоднозначная история попыток. Не возникает ни раннего dispatch, ни бесконечного ожидания, ни сброса счётчика.
- Capacity probe: отсутствие children подтверждено → bounded continuation; хотя бы один child уже начат → failure, без второй волны. Успешный частичный fanout не выдаётся за полную параллельную ёмкость.

## 5. `$ponytail`: что убрано из первоначальной идеи

- Не нужен универсальный retry engine, новая БД, очередь задач или конфиг для одного подтверждённого Codex error. Используем существующие daemon operation journals, RUN recovery, controller state и Judge callers.
- Не нужен общий retry в `providerTurn`/adapter: такой слой не знает, можно ли повторить действие. Один маленький shared predicate и повтор в owner path меньше и безопаснее, чем исключения после глобального retry.
- Не нужен restart EVAL или новая Judge Session при перегрузке; не ждать quota reset и не делать скрытый score reroll. Существующий failure/recovery путь остаётся для случаев без доказанного безопасного продолжения.
- Не объявлять любую `retryable=true` или строку `capacity` доказательством. Структурированная native причина плюс settled identity — необходимый минимум; при отсутствии факта честный failure/recovery.
- Не требовать неизменности native conversation/history: штатная compaction допустима. Фиксированы задача, packet/candidate, профиль и identity; это защищает смысл scored попытки, а не служебные файлы упряжки.
- Не ждать естественной перегрузки ради теста. Local mock + установленный binary проверяют необходимое поведение детерминированно; реальные E2E проверяют весь цикл, а не заменяют этот тест.

## 6. Готовность плана R2 и статус реализации R3

В R1 не были определены освобождение failed-turn budget, exact HITL successor, parent-mediated child continuation, turn-scoped topology, выбор Judge output и crash windows. Это были реальные препятствия реализации, а не косметические уточнения. R2 задал порядок переходов, failure policy, места изменений и regression gates. P0 подтвердил совместимость установленного binary; это не заменяет оставшиеся gates и не разрешает обход новой Session при будущей несовместимости.

После R2 внесены изменения native Codex adapter, RUN/Work/MERGE/Judge owners, recovery ACK, quota adapters и EVAL-отчёта. Установленный Codex прошёл детерминированную localhost-пробу: terminal overload, затем успешный новый Turn в той же Session. Адресные dd-eval тесты и сборка dd-flow прошли. Общая regression, выпуск нового engine, qualification и четыре fresh scored E2E остаются обязательными gates; локальный широкий dd-flow прогон под высокой нагрузкой дал subprocess timeouts и пока не считается зелёным. Старые EVAL остаются frozen.
