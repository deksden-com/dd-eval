# 057 — Детерминированная verification matrix и исправление admission AGY и ZCode

Дата: 2026-09-29. Статус на 2026-09-30: P1–P6 реализованы, exact source beta.122 опубликован после успешного полного CI; installed/native qualification и новые E2E P7 выполняются. Историческая причина ZCode >15 s остаётся unknown; новый measured reliability envelope проверяется отдельно. Проверен по `$ponytail` (full) и `prompting`. Продолжает [056](056-cp185-three-harness-flow-repair-plan.md). P1–P4 закрывают evidence/матрицу; P5–P7 закрывают AGY shell/cwd, ZCode admission/диагностику и передачу причины отказа в controller/EVAL. Основание — [отчёт CP186](../runbooks/cp-186-three-harness-beta121.md), read-only исследование exact beta.121 и исходников. Timeout не является доказательством SQLite lock. Условия готовности — разделы 12 и 16; source tests не заменяют release/native gates.

## 1. Цель и установленная причина

Перенести механическое формирование технической матрицы проверки с агента на runtime. На входе этапа агент получает уже созданный файл, его точный путь, источники и границы использования. После проверки runtime добавляет реальные результаты. Агент отвечает за смысл требований, достаточность проверок и классификацию замечаний, не за ручное копирование IDs, hashes и статусов.

Основание — Luna `EVAL-20260929164326-5b90a479`, beta.121. RUN прошёл семь стадий до MERGE, Final Judge выполнен, `run_validity=valid`, cleanup `settled`. `task-priority@2` выдал единственный gap `priority_matrix_row_missing:PRT-007-task-priorities`. В том же frozen receipt все 11 AC связаны с успешными final MERGE checks `WRK-020-merge/RCP-037`–`RCP-040`. Это не доказанный функциональный дефект. Project verification index не обновлён; результат не содержит отдельного нового evidence passport в папке протокола. Поэтому нельзя представлять проблему исключительно как опечатку в таблице, но нельзя и отождествлять её с отсутствием runtime proof.

Два источника проблемы:

1. Техническая связь уже формализована в PLAN/receipts, но MBB closure-инструкции поручают агенту ещё раз отразить её в проектной таблице/паспорте. Отдельная запись может отставать от реального RUN.
2. Case-local checker требует конкретное Markdown-представление и curated `.md` reference как дополнительную authority, хотя уже проверяет цепочку финальных машинных доказательств. Сам runtime не создаёт техническую матрицу; в `src/services` нет генератора `verification-matrix`.

Новый контракт исправляет эти причины, а не добавляет ещё одну инструкцию «не забудь заполнить таблицу». Исторические EVAL/checker результаты остаются неизменными.

## 2. Решение и границы

- SSOT деклараций: accepted SPECIFY/PROTOCOLIZE, валидированный `plan.json`, его `checks`, `items[].verification`, `acceptance`, accepted PLAN revision и generated CODE batch.
- SSOT фактов: check receipts, input/profile/evidence hashes, stage/Work outcome, review decisions, frozen MERGE gate и gate acceptance с `accepted_tree`/final bindings.
- Матрица — **производное представление**, не новая authority приёмки. JSON содержит технические данные, Markdown — читаемую проекцию того же JSON.
- Ни `purpose`, ни `expected_evidence`, ни зелёная команда не дают автоматически verdict «требование корректно реализовано». Проверку смысла оставляем агенту/review/Judge. Отдельно показываем механическое выполнение и семантическую оценку; не вводим автоматический `accepted_local` только из exit 0.
- Не делаем матрицу обязательной для любых custom flows и маленьких проектов без принятого PLAN/check contract. Для текущего SDLC контракт действует с момента, когда есть структурированные принятые требования; пропущенный по конфигурации этап не требует искусственного исполнения.
- Не меняем продуктовый код, старые PLAN/EVAL, базы runtime или артефакты CP186. Новая логика действует только в новой поставке и новых RUN.
- В первой реализации runtime не переписывает `.memory-bank/plans/verification-matrix.md`. Основной результат — RUN-local, включённый в существующее frozen evidence. Project document остаётся optional index/summary; его наличие или точное оформление не заменяет proof.
- Контракт включать для новых vNext SDLC RUN явным retained маркером `verification_matrix_contract: "dd-flow/verification-matrix@1"` в существующем RUN index при создании. Отсутствующий маркер означает прежний контракт, а не повреждение матрицы. Это одно поле происхождения, не новая настройка для каждой упряжки и не registry capabilities. При штатном fork/import переносится фактический контракт источника; историческому RUN его не дописывают задним числом. Новый E2E/checkpoint должен быть создан уже под новым контрактом. Для marked RUN обязательный packet нельзя silently skip; для legacy/custom flows не создаём новое условие отказа.

## 4. P1 — одна техническая проекция

1. Добавить небольшой общий builder/renderer в `dd-flow/src/services/verification-matrix.ts`. Это чистая функция над валидированными структурированными входами; без чтения произвольной project Markdown, SQL внутри renderer, provider calls и запуска checks. Path/identity/receipt resolution остаются в существующих authority helpers. В CODE использовать `verificationProjection` и уже выбранные current receipts; в MERGE — existing gate acceptance bindings. Не вызывать CODE projection как универсальный renderer PLAN skeleton: сейчас отсутствие due receipt в ней означает `failed/unresolved`, а при PLAN это ещё не выполненная проверка. Общий helper выносить только для реально общей классификации, без зависимости PLAN от CODE stage orchestration и без переписывания старого gate ради отображения.
2. Ввести узкий контракт `dd-flow/verification-matrix@1` и соответствующую schema в canonical schemas. Не хранить новую сущность в SQLite: exact bytes публиковать уже имеющимся Stage packet mechanism.
3. Header: project/RUN identity, owning stage/attempt, role `input|output`, review cycle при наличии, source fingerprint, references/checksums принятых источников. В final MERGE — точный accepted tree и gate/profile identity. Не использовать текущий timestamp как идентичность; если время отображается, брать его из retained owning event.
4. Rows формировать по `(protocol_id, criterion_id)`, не только `AC-NNN`. Разные протоколы могут вносить вклад в один критерий; сохранять все check refs. У одного критерия несколько checks, receipts и контуров — это не конфликт и не основание first-wins.
5. Из PLAN переносить gate, Work ownership, path/environment/fixtures/cleanup, expected evidence и proof limits; refs на требования — из existing accepted ownership. Не выводить SCN/feature ID из prose или suffix протокола. Явно отсутствующая связь остаётся отсутствующей; optional scenario metadata не становится новым обязательным полем PLAN.
6. Check facts: declaration ID/canonical ref, command/definition, run_at/availability; retained result/receipt ID и input/profile/artifact hashes при наличии. Отсутствующий ещё не выполненный check — `not_run`. Native/receipt status не переименовывать ради зелёного UI. Повреждённое или неподходящее по binding доказательство — unavailable с причиной, не PASS и не обвинение продукту.
7. `passed` показывать только по подходящему exact receipt. Старый receipt можно использовать по existing доказанному reuse contract, не по последнему timestamp. Для ранней стадии отсутствующий поздний check показывается planned/not_run, а не текущим failure. Не менять runtime gate semantics из-за renderer.
8. Факты исполнения и model-authored semantic verdict держать раздельно, с provenance существующего `code-verification`/review decision. Project wording `accepted_local`, `closure_state`, CI/production readiness не выдумывать из наличия tests.
9. JSON/Markdown должны быть стабильными при одинаковых входах: явный порядок rows/refs, escaping `|`, переводов строк и Markdown; без случайных UUID. Реальные receipt IDs различаются между executions закономерно. Markdown не требуется повторно парсить для приёмки.

Уточнённый минимальный shape `@1`: header `project_id`, `run_id`, `stage`, `stage_attempt`, `role`, `completeness`, optional `review_cycle`, `source_fingerprint`; `sources[]` с `role/root/path/sha256`; `requirements[]` со всеми принятыми R и существующими PLAN item/Work/check связями; `criteria[]` с protocol/AC, declared gate/contour/proof limits и check facts; `policy_checks[]` для обязательных profile checks, не названных в semantic PLAN. Final header содержит MERGE request, gate/profile hashes, accepted tree; model verdict — отдельная optional секция с refs на уже принятый semantic result. Не создавать обязательную модельную связь R→AC, которой источники не дают: показывать реальные R→PLAN item→checks и AC→acceptance→checks. Work ещё не зарегистрирован — сохраняется scoped PLAN item ID, без придуманного WRK ID.

`completeness` имеет значения `skeleton|declared|execution|final`: PLAN input — именно skeleton. `final` означает финальный срез выбранного contour, а не все проверки мира; release check вне contour MERGE не становится ни PASS, ни failure. Для check отсутствующий результат имеет `result: null` и stage-relative disposition `not_run|not_due|unavailable`; retained результат сохраняет native receipt status. Planned provider и policy checks отображаются без фиктивного исполнения. Scoped source check key — `(protocol_id, check_id)` либо existing canonical policy ref; P1 разных protocols не склеиваются. Важно: `validatePsetCheckIdentity` уже запрещает одинаковый CHK ID внутри одного принятого PSET (`duplicate_pset_check_id`). Матрица сохраняет эту validation, не расширяет набор допустимых PLAN. Scoped source refs нужны для provenance и MERGE canonical bindings, не для обхода validator. Уникальность AC внутри одного protocol также уже проверяется; все вклады разных protocols сохраняются.

Fingerprint вычислять из канонического отсортированного source descriptor, не из готового JSON со своим fingerprint/path. Для сериализации — фиксированный порядок и сравнение строк без зависимости от locale машины. Metadata `semantic.verification_matrix` содержит contract, role, completeness, source fingerprint и **два** refs `{path, sha256}` для JSON/Markdown. Внутри generated файлов storage refs типизированы `run|workspace` и relative path (или существующий `run://`), не live absolute home. Команды/описания из PLAN сохранять как декларации, не переписывать shell command regex-ом ради переносимости; runtime path в command не использовать как адрес proof. Абсолютные разрешённые пути выдаются только в prompt/response. Это снимает двойную неоднозначность: какой из двух файлов хеширован и переживут ли refs перенос snapshot.

## 5. P2 — публикация и границы этапов

Runtime path: `<run-home>/<stage-dir>/verification/<source-fingerprint>/verification-matrix.json` и `.md`. Fingerprint включает role, stage/attempt, revision/cycle и exact набор authority/receipt hashes. Это разные файлы для разных срезов, не один mutable `latest.md`. Ссылки в persisted metadata — RUN-relative; фактический доступный путь в prompt разрешается runtime.

| Граница | Что уже известно и что формировать |
| --- | --- |
| Вход PLAN | Принятые R/AC и ownership из предыдущих стадий. Заготовка без придуманного каталога checks; prompt прямо сообщает неполноту. Агент пишет PLAN, не generated файл. |
| Успешная PLAN validation/finish | Полная declared matrix по принятому PLAN, status checks `not_run`. Сначала validation, затем публикация; malformed PLAN не получает вид «accepted». |
| Вход PLAN-REVIEW | Та же exact proposed matrix + checksums, до первого reviewer. При correction на finish создать отдельный output из validated final revision, не обновлять original reviewer input. |
| Вход CODE | Матрица из окончательного accepted PLAN/batch, включая изменения PLAN-REVIEW. Старый предложенный PLAN не использовать. |
| CODE checks / штатный successor | Новый срез из retained receipts перед следующей semantic оценкой. При `needs_checks` он передаётся уже в текущем CLI response, поскольку агент может продолжить тот же Turn. При failed check и repair сохранить реальные состояния; не создавать новую productive попытку ради проекции. |
| Вход CODE-REVIEW | Стабильный input snapshot из accepted CODE evidence, привязанный к review cycle. Один общий baseline для всех reviewer siblings. |
| Finish CODE-REVIEW после repair | Отдельный output по current final gate/semantic outcome. Не переписывать файл, который читали reviewers; repair не равен автоматической приёмке. |
| Вход MERGE | Исходный evidence snapshot и frozen target gate. Source PASS обозначен source evidence, не target PASS. |
| Finish MERGE | Final rows по accepted PLAN и exact final gate acceptance/bindings на accepted tree. Inputs удержать до cleanup source checkout; публикация вместе с accepted MERGE report до candidate boundary capture. Никаких post-gate изменений Git tree. |

Publication требования:

- Подготовка bytes вне длинной SQL transaction; commit exact packet bytes вместе с owning admission/transition через existing Stage settlement. После commit — обычный projection publisher. Никаких Git/process/filesystem обходов внутри writer transaction.
- Start не равен finish settlement: сейчас vNext start пишет prompt и лишь затем attaches Stage, а `acceptStagePacket` требует уже существующий owning attempt. Для marked start подготовить sources/bytes вне writer, затем коротко принять Stage attachment/binding и packets под одним owning attempt; перед return убедиться в публикации обоих файлов. Не оборачивать весь start/readiness/bootstrap в writer transaction. Предсказанный attempt в prepare перепроверяется против принятого attachment; stale generation/revision/Work/check identity отвергается bounded SQL checks. Новые matrix inputs берутся из retained accepted facts, не из произвольного чтения изменяемых файлов под writer lock.
- Ready prompt/response вправе говорить «файл сформирован» только после успешной публикации. При crash/disk error действует existing `publication_pending`/reconciliation; productive Stage/Work/check не повторяется ради файла.
- JSON и Markdown — два Stage packets, не атомарный filesystem bundle. Публикация только одного файла не даёт ready; reconcile достраивает второй из retained bytes. `reconcileRunStageReports` при attach исключает текущий stage, поэтому committed start/continuation должен адресно вызвать `publishStagePacket` для своих retained refs перед возвратом успешного packet. Проверить это и для resumed веток, которые сейчас читают существующий `stage-prompt.md`. Не считать no-op publisher подтверждением наличия файла: после publication нужен exact file/hash match. Не вводить новый recovery scheduler или replay stage start ради отсутствующего Markdown.
- Повтор admission/finish при тех же facts возвращает тот же путь и bytes. Другие facts получают новый fingerprint. Конфликт уже принятого файла нельзя «исправлять» overwrite: сохраняется обычная projection error.
- `semantic.verification_matrix` в accepted report хранит RUN-relative JSON/Markdown refs, checksum и role/source fingerprint. Матрица не включает hash собственного owning report, который в свою очередь включает hash матрицы: исключить циклическую зависимость. Ранее принятые predecessor report hashes допустимы.
- Start/continuation packets передают те же refs; после retry/recovery ссылки берутся из retained accepted packets, не из mutable last-on-disk файла. Новый stage attempt не публикует старый packet как текущий.
- Review input boundary включает exact JSON и, если он читается, Markdown; foreign RUN/parent/cycle или content drift — существующий blocker. Не добавлять исключение из `read_only_input_changed`. Пользовательская/модельная семантика заполняется в обычном stage result, не внутри generated artifact.
- Копирование/ребазирование для external reviewer подтверждает тот же checksum; абсолютный путь исходного host home не объявлять доступным без проверки. Не копировать entire runtime/provider home ради одного файла.
- Failed/cancelled gate не публикует матрицу как accepted stage completion. Промежуточный пакет может сохранять факты для следующего Turn/отчёта с явным роль/статусом.
- `needs_checks`, aggregate failed check, registered repair и MERGE source repair передают новую projection ref + общий instruction в существующем response/continuation. Ошибка остаётся исходной ошибкой с существующими effect/retry/repair данными; матрица не делает её retryable и не заменяет issued successor command. Для следующего worker/repair packet удерживается назначенный срез, а не глобальный latest файл. Незавершённые параллельные Works нельзя представить как полный aggregate result.
- MERGE сейчас выполняет `performConfiguredCleanup` до финального `mergeReport`. До cleanup сохранить в RUN-local packet валидированные source bytes/refs, которые могут исчезнуть; окончательные gate facts взять из retained acceptance/receipts. В `commitMergeStageReport` принять final matrix packets и report refs вместе. В `recoverCompletedMergeRun`/`completedMergeReport` публиковать exact retained matrix bytes, не обращаться к удалённому checkout и не повторять check/commit/delivery/cleanup ради представления. Сбой после cleanup до report acceptance требует rebuild из уже retained источников; при нехватке источника — infrastructure evidence blocker, не пустая зелёная матрица.

## 6. P3 — общие prompts и canonical инструкции

Добавить один `verificationMatrixInstruction` рядом с projection contract в `src/services/verification-matrix.ts`: он форматирует только уже разрешённые path/identity/completeness/task параметры, ничего не читает и не публикует. Его используют stage modules, `work-registry.ts:renderWorkerPrompt` и continuation responses. Не класть provider-independent artifact logic в delegation adapter и не создавать новый template engine. Shared блок включается в coordinator, relevant worker/repair и reviewer prompts только когда файл реально подготовлен; не включать misleading block в review-off или stage без матрицы. Одинаковый блок для всех harnesses; выдача prompt через `stage start`, Work start или response не меняет контракт.

Базовая формулировка (этапный task подставляет runtime):

> Runtime сформировал техническую матрицу проверки: `<absolute-markdown-path>`; структурированные данные: `<absolute-json-path>`. Это производное представление указанных PLAN/receipts, срез `<source-identity>`, полнота `<skeleton|declared|execution|final>`. Прочитай матрицу перед `<stage-task>`; используй связанные evidence refs в пределах выданного контекста. ## 13. P5 Причина AGY и общее распознавание lifecycle в shell-командах

### Подтверждённая причина

AGY `EVAL-20260929165726-d6ef470d` остановлен в PLAN. Native step 42 содержал `node fix-plan-refs.js && "$DD_FLOW_BIN" stage finish --stage plan --json`. Это нарушение тогдашнего правила standalone, но **не смена рабочего каталога**: retained `launch_cwd` соответствует назначенному feature checkout. В `handleControlledToolEvent` RUN короткой команды ищется через `observedLifecycleInvocation`; тот возвращает null для compound. `controlledLifecycleCwd` без RUN ошибочно выбирает stable root. Поэтому guard выдаёт `agy_directory_mismatch` до диагностики shell composition. Повторный вызов exact frozen beta.121 handler на read-only DB воспроизвёл тот же expected/actual mismatch без записи в EVAL. Отдельный read-only вызов `parseLifecycleCommand` уже правильно выделяет `stage_finish` и argv этого примера: первопричина не «parser не увидел команду», а blanket standalone policy и потеря scope на следующем шаге. По обсуждению 2026-09-29 blanket policy заменяется поддержкой однозначно распознанных составных вызовов; исторический результат не пересчитывается.

Есть ещё два самостоятельных дефекта: `observeLifecycleInvocation` считает managed AGY/Grok compound fatal (`recoverable=false`), а соседний путь сохраняет `lifecycle_shell_syntax_invalid/no_effect/recoverable=true`; `dd-agy.mjs` при передаче client failure принудительно заменяет любой `details.effect` на `unknown`, после чего `dd-agy-daemon.mjs:rejectHook` завершает active Turn при любой rejection. Shared `lifecycleRetryInstruction` разрешает исправление native pre-CLI shell refusal, но runtime не даёт воспользоваться этой инструкцией. Одна перестановка cwd guard исправит название ошибки, но не весь отказ.

### Изменения и границы

1. Цель shared слоя — **надёжно распознать настоящие lifecycle-вызовы**, их argv, source ranges и shell-контекст, затем связать их с existing issued assignments. Не исполнять shell для распознавания, не вычислять произвольные expansions и не писать свой shell interpreter. Разбор слов/операторов `shell-quote` уже существует, но собственные `commandSegments`, heredoc stripping и wrapper heuristics не должны разрастаться в самодельную грамматику. Использовать готовый структурный parser; основной кандидат — [Tree-sitter с Bash grammar](https://github.com/tree-sitter/tree-sitter-bash). Выбор и exact version закрепить после минимального qualification spike на corpus ниже: Node >=26, поддерживаемые платформы, native/WASM packaging, реальные sh/bash/zsh конструкции и cold hook budget. Bash grammar не объявлять полноценной zsh grammar. Если кандидат не проходит, выбрать другой поддерживаемый parser с доказанным coverage; не компенсировать провал набором provider-specific regex. [shell-quote](https://github.com/ljharb/shell-quote) можно оставить для уже подходящего quoting, не выдавать token array за полное AST. Новый parser не устанавливается в рамках этого документа.
2. Один общий recognition entrypoint в `lifecycle-command.ts`; существующие callers `lifecycle-invocations.ts`, `hooks.ts`, `hook-ingress.ts`, `codex-hook-delivery.ts` и ZCode dispatcher используют один результат. Он содержит все найденные executable command nodes, а не только первую команду; различает доказанное отсутствие lifecycle и неопределённость/ошибку разбора. Отмечает branches, pipelines, subshell/wrapper, redirects/stdin и unresolved dynamic words. Tree-sitter error recovery/ERROR/missing nodes не считать успешным разбором для admission. Строки в аргументах, комментариях и heredoc data не являются вызовами; executable command substitution — отдельный настоящий executable context. Отрицательный fast path разрешён лишь при доказанном отсутствии участия, иначе передать в полный shared handler. Не пропускать неизвестную форму как безопасное `none`.
3. Убрать blanket отказ по `compound`/`wrapped`. Первый обязательный productive scope — один однозначно распознанный lifecycle leaf в последовательности `&&`, `||`, `;`, newline, группировке/известном shell `-c`, а также с redirects/heredoc/stdin pipeline. Разбор wrapper учитывает реальные `-c` positional args; не безусловно unwrap и не терять shell dialect/argv. Для всех форм проверять trusted native Session/root/parent/daemon, exact issued assignment и current generation. Для managed public call отсутствие доказанного RUN — scope error, не fallback «наверное stable root»; bootstrap сохраняет отдельный контракт. Синтаксический AST только находит намерение, **не даёт lifecycle authority**.
4. Native tool выполняет **исходную shell-команду**: runtime не разбивает цепочку на независимые executions, не переписывает её через quote всего token array и не меняет stdin, redirects, условия или exit semantics. Если transport требует hook-event insertion, использовать проверенные source ranges конкретного lifecycle leaf и real-shell equivalence test; предпочтительно существующая привязка без rewrite, когда она квалифицирована. Prefix/suffix нельзя исполнять в hook. Наблюдение pre-tool — intent, не доказательство reached/executed leaf. Только фактический lifecycle CLI делает existing observed→executing CAS с проверкой actual argv, ownership, generation и реального process cwd; один tool receipt не является разрешением любых вложенных вызовов.
5. Cwd проверять для конкретной операции: bootstrap/SPECIFY/PROTOCOLIZE, PLAN/CODE feature checkout, read-only review copy, MERGE target и external Work сохраняют retained bindings. Разделить provider launch cwd и execution cwd leaf; `cd <feature> && dd-flow ...` не отвергать лишь потому, что shell начал в другом retained допустимом каталоге. Actual CLI cwd подтверждает достигнутый каталог; literal `cd` в AST — лишь ожидаемый маршрут, не native proof. AGY `workspace_paths[0]`, cwd предыдущего отдельного tool call и model text не становятся active cwd. Проверить одинаковую физическую route/alias policy с standalone CLI; реально чужой cwd остаётся denied. Prefix command execution не расширяет read-only scope reviewer.
6. Для условного/длинного prefix lifecycle leaf может не исполниться или дойти позже: observer не ждёт prefix синхронно, не объявляет CLI completed и не расходует ingress deadline на shell execution. Проверить lifetime issued/observed binding и cancellation/currentness при delayed leaf, branch skip, prefix failure и смене Stage/Work/generation между hook и CLI. Не продлевать authority бесконечно и не выбирать latest global; expiry возвращает точную диагностику/штатную допустимую continuation. Один lifecycle leaf внутри loop/function не равен одному execution: повторные executions требуют самостоятельной current assignment, CAS не переиспользуется. Несколько lifecycle leaves распознать все; в первой поставке admission разрешать только если существующий ledger уже даёт каждому отдельную однозначную привязку с проверкой текущего состояния на его CLI entry. Если это не обеспечено, bounded unsupported diagnostic, не общий допуск всей цепочки и не эвристика first-wins. Не вводить выдачу будущих assignments из AST ради поддержки `work start && work finish`.
7. Повтор никогда не воспроизводит автоматически весь compound command. Prefix мог изменить файлы, хотя lifecycle ещё no-effect; effects shell tool и lifecycle operation учитывать раздельно. Bounded correction только после доказанного native synchronous отказа всему tool call до shell либо отдельного подтверждённого no-effect lifecycle результата по existing contract. В первом случае агенту можно выдать точный разрешённый lifecycle command как fallback, но не требовать standalone для нормально поддерживаемого compound. ACP/post-tool после начала shell не доказывает отсутствие эффектов prefix. CLI prepare rejection со своим issued successor, repair/handoff и unknown-effect reconciliation остаются отдельными механизмами.
8. Не вводить retry registry. Сохранять diagnostic disposition в existing hook request/event/outcome с request/tool/Session/daemon/operation/generation и точной командой; использовать current-turn correlation/repeated-without-progress fence: одна разрешённая correction, повтор без прогресса — blocker. Durable запись предшествует correction. `dd-agy.mjs` сохраняет доказанный no-effect и полезную native deny reason вместо только code; timeout/socket/persistence остаются unknown. `rejectHook` не завершает Session/active prompt при первой доказанно корректируемой rejection. Произвольного `recoverable=true` недостаточно: нужны allowlisted disposition, bound request и current generation; stale/foreign receipt не меняет новую Turn.
9. Проверить на qualified AGY, что compound исполняется с правильным cwd и native deny позволяет correction в той же Session. Предпочтителен existing Turn; если native завершает Turn, разрешённая controller continuation только после доказанного terminal/idle, без concurrent prompt/новой Session/resume historical RUN. Этот semantic contract одинаков для Grok, Codex/Luna, ZCode, OpenCode/Droid; transport admission/effect proof различается. Shared `delegation-instructions.mjs` и canonical instructions больше не требуют standalone везде. Общий короткий пример остаётся удобным default, но composition сама по себе не ошибка. Проверить все активные producer/prompt/caller ограничения, не редактируя архивные traces. По `prompting` разрешённые действия объявляются только после runtime qualification соответствующего пути.

### Проверки P5

Обязательный **corpus реальных вызовов**, а не только новые придуманные примеры:

- В начале реализации перечислить доступные scored/qualification попытки Luna/AGY/ZCode/Grok в runbooks и retained evidence; собрать все доступные различные shell invocation forms из native tool events, hook payloads, adapter journal и retained lifecycle command/receipt. Включить successful и failed calls, bootstrap, Stage start/finish/pause/resume, Work start/finish/fail, repair/retry/recovery, coordinator/worker/reviewer. Обязательные anchors — AGY CP186 step 42 с `node fix-plan-refs.js && ...` и ZCode CP186 public PLAN finish без internal ID. Missing/unreadable источники перечислить как coverage gap; не утверждать «все исторические вызовы проверены», если evidence не сохранился. Historical runtime/DB открывать read-only, paid Session не запускать для сбора.
- Проверить **каждый извлечённый пример**; дедупликация только одинаковых syntax + dialect + payload/transport forms. Для fixture хранить provenance EVAL/RUN/tool/source ref, dialect/native argv/cwd metadata, исходную форму и вручную перепроверенный expected recognition: operation, argv, source ranges, executable contexts либо none/unresolved. Legacy `compound denied` не становится новым expected verdict только потому, что так ответил старый код. Не переносить auth/env dumps или секретные literals в repo; заменять значения placeholder-ами с сохранением quoting/операторов и явно отмечать sanitization. Крупные unrelated heredoc payloads можно сокращать только после проверки, что это не меняет разбираемую форму; точное тело проверить отдельно disposable equivalence assertion.
- В existing `test/hooks-shell.test.ts` добавить table-driven corpus; небольшую data fixture добавить лишь если inline случаи становятся нечитаемыми. Все extraction inputs сопоставить с fixture coverage, без нового corpus framework или хранилища. Native wrappers используют ту же fixture там, где путь применим; различие transport не меняет semantic recognition.

Два независимых уровня проверки:

1. **Recognition:** quoting/escaped spaces и executable path, DD_FLOW_BIN/env/node launcher, repeated options по actual CLI semantics, `&&`/`||`/`;`/newline, subshell/`-c` positional arguments, `cd`, export в условной branch (не переносить его безусловно в соседнюю), stdin pipes и fd redirects, quoted/unquoted heredoc, nested command substitution, multiple leaves/loops/functions, comments/help и malformed/error-recovered AST. Negative corpus: dd-flow в echo/grep/JSON/script text/heredoc, похожий executable, unrelated `node script.js`, dynamic `eval`. Не путать распознаваемый syntax с вычислимым argv/допустимым admission; known runtime-owned variable разрешается по retained binding, arbitrary expansion не угадывается.
2. **Admission/execution:** exact unique assignment/current native owner, expected feature cwd и `cd` route, prefix PASS/FAIL/side effect, skipped conditional branch, delayed prefix/expiry, shell syntax error (ничего не исполнилось), stdin consumption, lifecycle success с последующим suffix failure и exit masking, loop повтор/multiple leaves, stale generation, duplicate deliveries до/после executing и storage failure. В disposable shell исполнить настоящие bash/sh и используемые qualified zsh формы с harmless stand-in dd-flow: сравнить argv/stdin/cwd/порядок/exit status оригинала и допустимого rewrite. Затем existing ledger/CLI fixtures проверяют ровно один legitimate executing transition на assignment и отсутствие transition у skipped leaf. Parser assertion не заменяет эту проверку.

AGY CP186 форма в правильном checkout должна распознаваться и допускаться без ложного directory mismatch/standalone correction; hook не выполняет prefix, native shell сохраняет `&&`. Неправильный actual cwd, чужой RUN/Work/daemon/root/parent/generation, ambiguous binding и unknown-effect replay остаются denied. Отдельно пройти worker, external read-only reviewer, repair, HITL и MERGE target. Qualified packaged cold/concurrent parser probe входит в P6 deadline gate: новый AST parser не должен усугубить timeout ZCode. Offline parity Grok обязателен; live Grok пока не требуется.

## 14. P6 ZCode admission deadline и причинная диагностика

### Что подтверждено и чего трасса не доказывает

ZCode `EVAL-20260929164450-ec00147c` получил правильную короткую standalone PLAN finish команду. ACP tool pending поступил 17:30:40.696Z; observer `zcode event handle` не ответил в default 15 s, `native_hook_timeout` записан 17:30:55.963Z. Ledger завершил invocation `133af7ab-b4a0-4ffc-a41e-dae7ed4e94c1` с `invocation_receipt_timeout` в 17:31:30.376Z; event_key/identity_json остались null, receipt не записан. Native Bash duration 50191 ms включает загрузку CLI/ожидание admission; это не «hook работал 50 s». Deadline receipt начинается позже observer, поэтому 15/25/30 s нельзя суммировать или сравнивать как один таймер.

Почему конкретный observer subprocess не завершился за 15 s, исторические artifacts не показывают. SQLite busy_timeout 4 s, cold import около 520 ms и host load не доказывают ни lock, ни import, ни overload как первопричину. Hook-mode уже исключает migrations/VACUUM; их повторная «отмена» не исправит этот случай. До фазового воспроизведения latency cause остаётся открытой.

Подтверждены следующие системные проблемы:

- `runBoundedCommand` удерживает elapsed/effect/cleanup в error.details, но при timeout не прикладывает накопленную bounded диагностическую часть stderr; `AcpBridge.receive` в notification_failure теряет details полностью. Disposable assert воспроизвёл потерю. Timeout не входит в immediate `fatalLifecycleError`, однако остаётся `notificationError`, влияет на permissions и бросается в `flush`; эти пути должны иметь согласованную disposition. В CP186 controller увидел вторичный receipt timeout раньше settlement ошибки observer.
- ACP — в текущем qualified ZCode **рабочий admission transport**, а не просто secondary telemetry. Все семь successful CP186 hook rows имеют event_name PreToolUse и cwd=null; `handleZcodeEvent` public command допускает через lookup issued assignment. Tests также закрепляют этот путь. Комментарии «ACP only evidence»/«только explicit ID» устарели относительно кода. Удалить observer или ждать отсутствующий qualified native hook нельзя.
- `eventNameForReceipt` выбирается по наличию internal invocation ID, а не по происхождению события: public ACP регистрируется как PreToolUse. Disposable fixture подтвердил это; same-identity настоящий hook затем возвращает duplicate без обновления cwd. Предположение, что этот случай обязательно вызывает replay mismatch, **не подтвердилось**: ранний identity duplicate возвращает retained receipt. Нужен явный provenance и проверенная политика двух доставок, а не ослабление immutable replay guard.
- Observer запускает CLI для каждого Bash tool_call даже для unrelated shell; отбрасывание происходит лишь внутри CLI после import. При этом physical child/parent tracking необходим и не должен теряться. Это подтверждённая лишняя работа на critical path, но не доказанная причина CP186 15 s delay.
- Wrapper/ingress deadlines не передаются единым абсолютным deadline внутрь: wrapper ограничен 15 s, ingress читает stdin с новым default 25 s, CLI await receipt — отдельные 30 s. `hookBudget` комментирует общий native outer 30 s, тогда как просмотренный ZCode source default runner — 60 s с возможным hook-specific override. Host timeout нужно измерять из квалифицированного effective config, не из общего комментария. `hookBudget.run` Promise.race сам не отменяет underlying action: late commit возможен.

### Изменения P6

1. Первым шагом добавить red diagnostics/fault tests в существующие `zcode-invocation-observer`, `native-hook-ingress`, `hook-runtime-boundaries`, lifecycle suites. Сопоставить их с upstream bridge candidate по исследованию в разделе 16: native transport refactor не переносить без downstream recovery/identity regressions, vanilla upstream не подменяет qualified @2 bridge. После этого фазово измерить **exact packaged launch chain** `runtime shim → cli.js → import → prepared-store open → assignment lookup → receipt writer reservation/commit → reply`, включая tool event→CLI receipt wait. Замеры/import probe на уже warmed developer module не заменяют эту проверку. Никаких измерительных productive команд в historical EVAL.
2. В existing journal оставить bounded allowlist: phase, elapsed_ms, remaining/deadline, native/adapter Session, tool/request/operation, daemon/generation, store role, SQLite extended code, effect, receipt/commit identity и cleanup status. Диагностический stderr — только структурированные безопасные строки; не raw env, auth, result payload или полный transcript. Сохранять последнюю завершённую фазу до timeout в existing journal/transport. Generic debug dump и новый telemetry store не нужны.
3. Зафиксировать существующий qualified ZCode ACP admission contract. Handler явно различает ACP observation и native PreToolUse независимо от видимого invocation ID; совместно обновить все receipt consumers (`require*HookBinding`, `claimBootstrapHook`, hook Session identity, lookup, reconciliation), чтобы настоящее происхождение не ломало Stage/Work binding. Physical identity удерживается из native runtime metadata; callback не создаёт новый issued attempt. Если позже native PreToolUse квалифицирован как основной admission, это отдельная проверенная смена harness contract, не скрытое удаление текущего пути.
4. Dual delivery одного native tool: один authoritative receipt/claim, второй source — corroborating evidence с отдельной source identity. Arrival order и отсутствие cwd в ACP не дают ложный native-cwd claim. Проверить duplicate до/после observed/executing/settled, обе последовательности доставки, изменённую physical identity и late callback. Нельзя дописать доверенный cwd из model text или разрешить конфликт родителя/daemon. Не вводить новую authority DB: reuse existing ledger/hook evidence и native contract metadata.
5. Не выключать observer как secondary telemetry и не игнорировать его timeout. На стороне dispatcher убрать доказанно unrelated CLI spawn, **только** переиспользовав shared participation recognizer из P5; сохранить ancestry tracking для Agent/subagent events. Не использовать substring `dd-flow` как security classifier или второй облегчённый grammar parser. Изолировать recognition import от DB/controller bootstrap, если packaged measurements подтверждают пользу; выбранный готовый parser квалифицировать на cold/concurrent ingress path вместе с native/WASM artifacts. Неопределённый разбор передавать в общий handler, не skip как unrelated. Новый parser dependency разрешён по gate P5, второй parser/DSL не нужен. Если сокращение import graph/lookup не нужно по измерению, не делать speculative rewrite.
6. После measurements устранить найденную задержку в её владельце. Contention fixture удерживает writer в disposable runtime, конкурентно доставляет receipts и продвигает controller/CLI; проверить writer не удерживается через provider/file/process await, receipt waiting не происходит внутри writer, repeated SQL busy waits не расходуют весь бюджет незаметно. Existing synchronous writeTransaction/afterCommit и diagnostics_channel переиспользовать. Если задержку вызывает иной участок, фиксировать его, не объявлять SQLite guilty по одному timeout.
7. Propagate один ingress deadline через subprocess/daemon phases; inner waiting/SQLite reservation ограничены remaining budget и оставляют время response/cleanup. CLI lifecycle receipt deadline — отдельная граница authority, но обязан учитывать retained ingress outcome и не ждать до второго generic timeout после доказанного ingress failure. Значения budgets обосновать измеренным packaged cold path, contention и effective native limit. Нет произвольного `15→30`, provider wall-time retry или нового scheduler.
8. В ingress не выполнять provider calls, check/product execution, schema migration, VACUUM, весь home scan или unbounded evidence projection. SQL receipt transaction остаётся короткой; filesystem/native owner preparation — вне writer с existing generation/currentness recheck. Перед COMMIT повторно проверить deadline/current ownership. Timeout после возможного COMMIT остаётся unknown until reconciliation; ранний no-effect разрешён только по реально доказанной границе, не по timer exception.
9. Немедленно **сохранить и передать** first bound admission failure, но не выпускать retry и не ложно считать остановленный handler отсутствием любого эффекта. Timeout killed subprocess, cleanup confirmation, ledger transition no-effect и возможные earlier receipt side effects — отдельные факты. Late committed receipt reconciles existing invocation; не создаёт новый productive attempt и не оживляет отменённый Turn. Native wrapper deny также сохраняет structured cause вне model-facing reason.

### Проверки и критерий закрытия P6

Cold packaged startup; множество unrelated Bash без CLI spawn; native child ownership; параллельные участвующие события; writer contention; delayed stdin; deadline до/после commit; full stderr buffer; SIGKILL/descendant cleanup; event journal write failure; dual-source order; stale generation; exact public command без internal ID; late receipt после ledger expiry и cancellation. Каждая failure trace содержит phase/native tool/operation/effect и primary cause; clean admission содержит ровно один executing transition.

**P6 нельзя отметить выполненным только по диагностическому patch.** Нужны либо причинное воспроизведение задержки и адресный fix с regression, либо воспроизведение допустимой measured нагрузки, доказавшее недостаточную бюджетную границу, и обоснованное изменение этой границы с fault tests. Если CP186 slowdown не воспроизводится, причина честно остаётся unknown; проверяется новая измеримая reliability envelope, но исторический root cause не объявляется установленным. Для live E2E readiness нужны qualified cold/concurrent/late-commit probes нового engine, не успешный warmed import.

## 15. P7 Причинный отчёт и полная проверка общих путей

1. Source/transport/root cause ledger→adapter→daemon operation→controller→EVAL должны сохранять bounded identity и первичную причину. В CP186 ZCode observable first failure — observer native_hook_timeout, settled ledger failure — invocation_receipt_timeout; report показывает оба и причинную связь, не переписывает immutable старый outcome и не выбирает просто earliest timestamp среди чужих Turn. `run-controller-adapter.ts`, `run-controller.ts`, `continuation-outcome.ts`, daemon settlement и `dd-eval/lib/runner.mjs` используют existing error envelope. Secondary cancellation/cleanup/persistence не затирают primary.
2. Проверить report attribution. AGY historical report имеет `run_validity=valid`; `isInfrastructureFailure` не включает directory mismatch. Не добавлять глобальное правило «любой cwd error — infrastructure»: неправильный cwd модели и неверный runtime-derived expected route различаются. Новые structured admission/correction diagnostics должны позволять классификацию по доказанной component/disposition/provenance. Неправильная семантика/PLAN/result оцениваются flow/Judge; transport/authority defect не превращается в product failure. Старые reports не исправляются задним числом.
3. Аудит общих callers завершать адресными checks: `handleControlledToolEvent` (AGY/OpenCode/Droid), `handleCodexHook`, `handleGrokEvent`, ZCode event/hook, shared observe/await/settle; native wrappers AGY/Grok/ZCode, Droid controller, OpenCode plugin и Codex ingress. Особенно разделить before/after hooks: PostToolUse не может утверждать pre-CLI no-effect или безопасный shell retry. Не менять fail-closed guard для непросмотренного sibling только ради названия parity.
4.
