## Цель и границы

Interaction Judge отвечает на один операционный вопрос: достаточно ли выбранных
канонических ответов для продолжения существенных пользовательских решений?
Он не оценивает качество каждого уточнения и не требует от пользователя выбрать
техническую реализацию. Качество уточнений оценивается отдельно по существующим
flow-критериям финального Judge, если такая оценка доступна и применима.

Одинаковая семантика для всех упряжек, этапов с разрешённым HITL, classic Judge,
JEV и Luna Decisions. Никаких новых классификаторов, вторых судей, repair-циклов
или обязательных модельных проверок для обычной подготовки EVAL.

Работающие Luna/AGY, их исходный definition checkout, homes, pins, packets и
результаты не менять. Старые ZCode/OpenCode не возобновлять и не переписывать.
Продукт dd-tasks не исправлять. Выпуск и новые EVAL требуют отдельного запуска.

Исторические `recovery_observation_budget_exhausted` вторичны и не являются
объяснением несовпадения HITL. Процессы/cleanup и исходный семантический отказ
остаются отдельными осями.

## 2. Принятые решения

1. Сохраняем существующий компактный результат `hitl-coverage@1`:
   covered / uncovered / ambiguous, response_ids и remaining questions.
   Не добавляем новые enum, поля «качества» или required citations в компактный ответ.
2. Covered означает достаточность ответа для существенных пользовательских
   решений, включая явно делегированные детали реализации. Это не подтверждение
   качества всех формулировок Subject и не доказательство успешности продукта.
3. Техническая деталь считается делегированной только если не меняет принятое
   наблюдаемое поведение, права, совместимость, необратимые эффекты или риски.
   Нельзя автоматически объявить любой неизвестный вопрос implementation detail.
4. Иерархия: явные решения пользователя и авторитетные нормативные ограничения;
   далее текущее поведение; отдельно предположения/рекомендации Subject.
   Нормативность определяется содержанием и происхождением, не заголовком/role.
5. Явное каноническое решение новой функции может заменить старое поведение в
   своей границе. Настоящий конфликт с независимым принятым ограничением без
   разрешённого пересмотра остаётся unresolved. Не разрешаем конфликт молча.
6. Неизвестные существенные ссылки, противоречащие выбранные ответы, независимые
   новые решения и неполный существенный ответ остаются блокерами.
7. Выдаём только точные выбранные canonical bytes через имеющийся delivery path.
   Не переводим, не дописываем и не «лечим» ответ по ходу запуска.
8. Исторические v3 receipts читаем и показываем в исходном виде. Не меняем
   unmatched на covered постфактум и не используем новую политику для старой выдачи.

## 3. Работы по общим точкам

### P1 — Семантика одного решения, без наращивания исключений

В `lib/hitl-contract.mjs` выделить короткую общую политику достаточности и
авторитетности, переиспользуя существующую shared policy вместо новой подсистемы.
Использовать её в compact native prompt и `lib/hitl-coverage.mjs:jevInstructions`;
`lib/semantic-decisions.mjs:semanticQuestion` получает её через существующий импорт.
Убрать дублирующие/противоречащие формулировки. Не переписывать независимые правила
про material references, роли, archive/create/update и отказ от лишних механизмов.

Два кратких контрастных примера достаточны: default + делегированный backfill
против нерешённого поведения старых данных; ложное «English already settled»
против настоящего нормативного языкового ограничения. Не добавлять полный журнал
инцидентов в рабочий промпт. Менять и учитывать fingerprint фактических промптов.

Не разрешать все legacy out_of_scope автоматически. Legacy v3 остаётся отдельным
эксплицитным диагностическим/историческим режимом с прежней формой результата.

### P2 — Канонический пакет с определёнными границами

В task-priority `interactions/specify.json` и `plan.json` согласованно добавить:

- default `no_priority` обязателен как наблюдаемое поведение существующих задач;
  способ backfill/fallback выбирает исполнитель по правилам проекта, сохраняя
  целостность данных и согласованность UI/API;
- приведённые русские подписи — точные принятые тексты этой функции; существующий
  английский UI не требует их автоматического перевода. Локализация всего продукта,
  второй язык и переключатель языка этим не заказываются.

Не выбирать конкретную миграцию, не менять словарь/API/права/архивное исключение,
open/closed и optional display на форме создания. Не выдавать скрытые canonical
решения до реальной HITL-паузы. Использовать существующий builder там, где он уже
есть; для двух authored stage-файлов достаточно проверки равенства answer bytes,
а не нового формата ссылок или генератора фикстур. Обновить только производные
hashes/qualification expectations, реально зависящие от этих байтов.

### P3 — Общий SPECIFY и последующие handoff

В owning canon `.memory-bank/dd-flow/vnext/specify.md` и соответствующем spec
уточнить имеющиеся правила, не заводя harness-specific инструкции:

- current behavior, accepted decisions и open questions не смешиваются;
- «settled» требует ссылки на реальный user answer или нормативный источник;
- технические варианты не выносятся пользователю без существенного продуктового
  различия; делегирование сохраняется в handoff как свобода реализации;
- browser locale, язык исходников/документа и существующие UI strings не являются
  самостоятельной принятой политикой языка новой функции.

Проверить общие stage-context/source-precedence и renderer потребителей
PROTOCOLIZE/PLAN/review на те же предположения. В engine
`src/services/stage-context.ts` уже есть accepted_decisions и source precedence:
использовать их, не вводить второй реестр доверия. Не менять schema «на будущее».
Обновлять только найденные реально противоречащие тексты и синхронизировать curated
flow pack существующим способом. Нормативные product policy не отменять.

### P4 — Одинаковый operational contract профилей

Инвентаризация всех `cases/*/run-profiles` и загрузчиков профилей обязательна.
Для новых обычных full/focused/segment/SPECIFY запусков явно выбрать compact
`verdict_contract`; inline/server и разные упряжки не меняют семантическую задачу.
Изменение Subject harness не должно само выбирать другой Judge contract.

Исторические диагностические/qualification fixtures могут явно сохранять v3,
если проверяют именно его. Не менять глобально трактовку отсутствующего поля у
старых manifest. Добавить одну offline-проверку operational profile inventory,
исключения перечислить явно как diagnostic/legacy, а не по имени упряжки.
Согласовать schema examples/CLI docs, если они создают новые operational профили.
Обычные diagnose/reference/build профили тоже переводить на compact: само слово
diagnose не является исключением. V3 сохранять только в конкретных тестах и
профилях, чья заявленная цель — проверка atom-контракта, с явным verdict_contract.
Это не изменение default для внешних/исторических профилей без поля: они по-прежнему
читаются старым путём; новые проектные шаблоны всегда задают контракт явно.

### P5 — Связанные пути: issuance, статус и финальный аудит

Проследить оба caller `resolveHitlJudgment` (обычный запуск и восстановление),
retained verification, focused entry и live runner: одинаковое правило выдачи,
никакой выдачи по unverifiable/uncovered verdict и повторной выдачи принятого ответа.
Сохранить pause/scope/round/EVAL bindings, точные bytes и идентичность native turn.

Сводку interactions/status собирать из фактических grounded exchanges, а не только
из compact manifest; legacy status показывать как legacy, без выдуманных confidence
или преобразования в новый verdict. Историческое read-only отображение не разрешает
новую выдачу. Недоступный receipt — unknown/unavailable, не молчаливый PASS.

В существующем finalJudgePrompt убрать зависимость применимого семантического
аудита от наличия coverage_filter. Пакет/выданные решения доступны в том же final
Judge вызове: в `executionEvidence` добавить разрешённый packet_file для любого
grounded обмена с проверенными receipt/packet anchors, используя существующий
retained proof, а не произвольный путь из непроверенного result. Filter —
необязательные metadata источника. Аудит оценивает только
существенные последствия по существующей rubric, не повторяет mechanical matching
и не требует отдельного Judge перед EVAL. Невыданный пакет не становится scope.
Если финальный Judge не запускался, не приписывать ему проведённую проверку.

### P6 — Минимальные целевые регрессии

Перенести реальные вопросы и существенные frozen context bytes из двух EVAL в
санитизированные фикстуры, сохранив provenance и различие raw observation / authored
ожидание. Не сохранять весь home, секреты, auth/config и приватные native журналы.
Исходные отрицательные verdicts остаются отрицательными историческими фактами.

Проверить в существующих suites, без нового framework:

| Сценарий | Ожидание |
|---|---|
| Полный вопрос ZCode + default и явное делегирование backfill/fallback | covered |
| Отличается видимое поведение старых задач, ответа нет | uncovered |
| Технический вариант в options, без отдельного продуктового выбора | не новый блокер |
| «English already settled» только в тексте Subject, пакет задаёт русские подписи | covered |
| Реально принято обязательное English + нет разрешённого пересмотра | uncovered |
| Запрошены дополнительный язык/переключатель, ответа нет | uncovered |
| Archive baseline + явное узкое canonical исключение | covered только в границе исключения |
| Вопросы о новом независимом поведении или неидентифицированном решении | uncovered / ambiguous |
| Противоречащие canonical ответы / mixed covered+uncovered | не covered |
| Выдача, reattach и повторное наблюдение одного accepted pause | точные bytes, без нового model call |
| Старый v3, compact Judge и Decision/fallback | сравнимая отчётность, исходные verdicts сохранены |

Детерминированный тест не доказывает, что LLM семантически выберет правильный
вердикт: он проверяет сборку контекста/политики, routing, сохранность границ,
oracle expectations и delivery. Повторная оценка старого неверного ответа не
должна превратить его в PASS. Будущую живую проверку исправленного prompt отдельно
помечать как regression evidence, не как сертификат безошибочности.

## 5. Проверка ponytail и готовности

- Исправляем назначение Judge и общие точки, не пишем классификатор по словам
  «миграция», «English» или названиям упряжек.
- Переиспользуем compact schema, shared policy, source precedence, plugins,
  issuance и suites. Без новых зависимостей и required prelaunch model checks.
- Не расширяем фикстуру техническим дизайном; явно задаём достаточное поведение
  и свободу реализации. Не добавляем глобальную подсистему localization.
- Не ослабляем trust boundaries, существенные неизвестные, conflict handling,
  точность answer bytes и binding принятой паузы.
- Все решения для реализации перечислены; semantic success LLM остаётся предметом
  честной последующей регрессии. План готов к реализации, не означает, что исправления
  уже выполнены или новые EVAL гарантированно пройдут.

## 6. Дополнения повторного ревью готовности

### Миграция контракта и корпуса без ложной эквивалентности

`hitlQualificationInputs` выбирает `case.hitl_qualification.coverage` для compact,
а не автоматически конвертирует старый корпус. Сейчас в atom-корпусе 24 кейса,
в compact — 50; они не взаимозаменяемы. При P4 проверить наличие coverage declaration,
его digest, контекстов и expectations до любого вызова модели. Пользоваться уже
существующим compact-корпусом; не переносить механически старые fault-классы в
новые статусы и не считать прежний v3 PASS квалификацией compact.

Кейс с повторным/лишним уточнением уже принятого решения больше не должен
автоматически делать operational coverage отрицательным: если имеющийся пакет
однозначно отвечает, статус covered, а не оценка качества вопроса. Неизвестная
существенная ссылка или новый independent choice остаются блокерами. Применить
это правило и к ожиданиям корпуса; unrelated negative cases не смягчать.

### Fingerprints, политика и совместимость сохранённых доказательств

- `semanticFingerprint` уже включает hitl-contract/coverage и transport files;
  `jevPromptHash` входит в legacy coverage policy. После общей правки обновить
  authored policy references/hashes только там, где они реально используются.
  Не подменять qualification_sha256 у старого JEV cascade receipt: для изменённой
  policy прежняя калибровка не доказывает новую. Новые credential/model/provider,
  confidence threshold, retry/backoff и fallback правила этот план не меняет.
- `verifySemanticReceipt`/`verifyJevReceipt` и status должны различать проверку
  исторических frozen bytes и разрешение новой выдачи. Если текущий fingerprint
  не позволяет семантически перепроверить старый HTTP receipt, показать evidence
  incompatible/unavailable с причиной, не объявлять порчу, PASS или новый результат.
  Не строить универсальную миграцию старых observations; не вызывать модель ради status.
- Shared policy может менять legacy prompt через существующий импорт. Новые
  diagnostic задачи получают новый fingerprint; старый сохранённый prompt не
  перезаписывается и не «проверяется» как будто был создан новой версией.

### Доставка и сводка: точные граничные решения

- Covered без хотя бы одного существующего response_id остаётся невалидным;
  «вопрос технический» не разрешает выдать пустой ответ или произвольную реплику.
- Несколько canonical responses допускаются только если вместе непротиворечивы;
  один отвеченный подпункт не скрывает новый независимый вопрос. Условия archive,
  actor, create/update, open/closed сохраняются. Опциональность не равна запрету.
- Недоступный материал, необходимый для конкретного решения, не заменять догадкой.
  Отсутствие явно optional нерелевантного источника само по себе не делает ответ
  непокрытым; для Decisions сохраняется существующий консервативный fallback.
- В status/report выводить исходные contract/status, source и remaining questions;
  не смешивать matched/unmatched и covered/uncovered в хранимом verdict. Отсутствие
  HITL — not_requested; отсутствие доказательств запрошенного HITL — unavailable,
  не not_requested. Дедупликация — существующая receipt/pause/scope/round identity,
  а не одинаковый текст вопроса: одинаковые вопросы разных пауз не один обмен.
- Отклонённый/невыданный пакет допустим как evidence evaluator-ошибки, но никогда
  не как принятый продуктовый scope. Final Judge не должен обвинять Subject в
  несоблюдении ответа, который runner ему не выдал.

### Артефакты, изоляция и проверяемое завершение

После P2 проследить существующие зависимости case/corpus/context/assessment и
reference-entry builders: обновлять authored source и производные digests штатным
способом, не blind hash replacement и не редактированием исторических entry packs.
Существующие цитаты в oracle остаются точными; expectations проверяются по смыслу.
Синхронизация canon касается flow pack; неизменный product baseline остаётся
прикреплённым к своему commit, менять продуктовый main для импорта промпта нельзя.

Минимальные suites по фактическому diff: `hitl-contract`, `hitl-corpus`,
`hitl-coverage`, `semantic-routing`/`semantic-decisions`, `hitl-issuance`,
`hitl-retained`, `hitl-reattach-review`, `hitl-coverage-report-review` и профильные
проверки. Не запускать каждую группу автоматически: выбирать тесты затронутых
функций; если изменён shared контракт, его реальные consumers входят в scope.
Добавить проверки retained HTTP mismatch и отсутствующего coverage declaration,
не привязанные к реальным homes/БД/сети. Все offline tests используют временные
изолированные каталоги; ни один не обращается к живому EVAL или credentials.

Готовность реализации и подтверждение поведения моделей — разные результаты.
Реализацию можно завершить с прошедшими scoped offline checks и честно указанной
непроведённой live regression. Нельзя назвать исправленный prompt модельно
проверенным по подставленному expected verdict. Новые модели/EVAL сейчас не нужны.
