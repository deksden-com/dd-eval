## Уточнение контракта hook → CLI после проверки документации

Обязательная передача контекста не должна зависеть от updatedInput. Предпочтительный путь — существующая БД: hook синхронно записывает минимальный контекст вызова, делает COMMIT и только затем успешно возвращается. CLI в новой транзакции читает контекст, атомарно связывает его с операцией и изменяет состояние Work. Hook не начинает Work и не выполняет миграции на каждом вызове. Фоновая запись недопустима на этом обязательном пути.

После COMMIT не требуется ждать WAL checkpoint или добавлять sleep: новая read transaction видит committed запись. Старый открытый snapshot может не видеть её — нельзя опрашивать БД в прежней транзакции. Timeout/crash до commit означает отсутствие допуска и наблюдаемый инфраструктурный отказ CLI; timeout после commit требует отдельной проверки поведения и не должен приводить к повторному исполнению уже совершённой операции.

Корреляция — отдельное нерешённое условие, а не свойство SQLite. Нужен подтверждённый adapter execution scope и однозначная связь команды с native tool invocation. updatedInput может доставлять точный ID там, где это проверено, но не является единственным каналом. Нельзя автоматически считать единственную свежую запись правильной: она может остаться от прерванного предыдущего вызова. Нельзя выводить session ID из общего parent env. Для транспорта без точного ID адаптер должен обеспечить однозначность активного вызова существующим механизмом либо отказать, а не выбирать последнюю запись. Не вводить новые токены для модели и второй реестр поверх существующих invocations.

В текущем hooks.ts findRecentMatchingHookEvent уже обходит невозможность rewrite вложенного Bash для Codex/Antigravity, но использует окно 60 секунд и ожидание 250 мс. Этот путь требует проверки stale receipt, повторов, одинаковых конкурентных команд и generation scope, а не расширения окна ожидания. Дополнительные обязательные сценарии: ignored updatedInput, rollback до commit, commit перед timeout, duplicate delivery и старый read snapshot. На финальном native транспорте отдельно проверить root/child и прямой/вложенный tool call. Живого эксперимента в рамках данного уточнения не проводилось; окончательный способ точной корреляции пока не квалифицирован.

## Первопричины и границы доказанности

### 1. Обязательный hook имеет слишком тесный бюджет для тяжёлого пути

`dd-flow-cli/src/services/hooks.ts`: commandHook задаёт 5 секунд; hookCommand запускает полный CLI. `src/storage/database.ts`: writable getDatabase выполняет schema initialization/migrations, busy_timeout равен 4000 мс; schema path использует write transaction. `src/cli/run-cli.ts` дополнительно строит контекст и проводит preflight.

Доказан timeout при конкурентном запуске, а не конкретная доля CPU/SQLite contention. Одной лишь задержкой SQLite объяснять всё нельзя без измерения. Даже один допустимый DB wait почти исчерпывает внешний бюджет.

### 2. Сбой доставки не входит в управляющий контур

`src/harness-runtime/lib/dd-codex.mjs` сохраняет hook notifications, но не превращает отказ собственного обязательного hook в отказ операции. `src/services/lifecycle-invocations.ts` при отсутствии anchor возвращается без outcome. Получается замкнутая зависимость: чтобы сообщить об отсутствии receipt, нужен receipt. Общее место затрагивает lifecycle-команды разных адаптеров, а не только Codex work start.

### 3. Восстановление оставлено модели

`src/harness-runtime/lib/delegation-instructions.mjs` задаёт первый start, но не явное прекращение работы при его отказе; отдельные инструкции `dd-droid.mjs` требуют той же сверки. Hook handler принимает model-generated payload. Успешный ручной вызов handler не является доказательством доставки исходного native hook. Это операционная граница доверия, не обещание криптографической защиты от агента с полным доступом к ОС.

### 4. Противоречивые инструкции результата

`src/services/work-registry.ts` в PLAN-REVIEW и CODE-REVIEW требует remove findings when none exist. Оба schema требуют соответствующие findings: массив должен быть пустым, а не отсутствовать. Это самостоятельный исправимый дефект, не причина терминального отказа.

### 5. Классификация и мониторинг

Проверка владельца в work-registry отклоняет finish до изменения состояния, однако общий outcome по умолчанию маркирует неретраебельную ошибку как unknown effect. Известный отказ без эффекта и неизвестный эффект — разные вещи. В dd-eval/lib/runner.mjs fatal lifecycle outcome уже признаётся инфраструктурным отказом; надо сохранить это и для нового раннего пути, не приписывать поломку hook качеству модели. Сохранение raw hook events без использования их мониторингом недостаточно для заявления «всё штатно».

## Минимальный системный пакет

1. Измерить cold/warm hook и шесть параллельных start на изолированной тестовой БД. Убрать повторную подготовку неизменённой схемы из hot path, сохранив проверку версии и безопасную миграцию при реальном изменении. Согласовать внутренний бюджет с внешним timeout с запасом; не добавлять ещё один watchdog и не лечить только увеличением числа.
2. В Codex adapter преобразовать отказ именно принадлежащего dd-flow обязательного hook в существующий канал runtime/lifecycle failure с native session, tool-call ID и исходной причиной. Не останавливать запуск из-за постороннего пользовательского hook. Общий controller получает нормализованное событие; специфика native notification остаётся в адаптере.
3. Сделать отказ managed lifecycle-команды наблюдаемым и без receipt: scope брать из уже подтверждённого managed execution, но не выдавать диагностическому scope права на мутацию. Не ослаблять ownership/receipt guard. При отсутствии доказанного scope — диагностика, не выдуманная привязка.
4. По умолчанию при обязательном hook failure останавливать принадлежащее выполнение и сохранять первичную причину. Не вводить автоматический повтор вслепую: он допустим только при доказанном отсутствии эффекта. Для текущего исправления достаточно корректного быстрого отказа, надёжного hot path и последующего контролируемого восстановления.
5. Общий worker contract: продолжение только после успешного start и полученного Work packet; status не заменяет start; запрещены ручная генерация receipts и вызов handler для починки. Managed admission должен сверять receipt с реальным native tool call/доставкой, используя существующий журнал, а не создавать второй реестр. Уточнить поведение при задержанной записи native event; неизвестное не считать успешным.
6. Для доказанных pre-mutation rejection сохранять effect=no_effect отдельно от disposition. Инфраструктурный no_effect остаётся ошибкой, не поводом просить модель обойти guard.
7. Исправить оба result template: findings: []; дать валидные примеры. Не ослаблять schema.
8. Мониторинг и итог eval используют тот же нормализованный failure; показывают первичный hook timeout отдельно от последующего finish rejection и исправленных schema ошибок.

## Проверки без повторения полного E2E на каждой правке

- Изолированный concurrent lifecycle test с шестью детьми: все receipts относятся к своим native sessions, start успешно завершается в бюджете; нет model-generated receipts.
- Adapter transcript test: собственный hook timeout немедленно достигает controller; посторонний hook не становится ложным blocker.
- Missing receipt: отказ start наблюдаем без права мутации; work остаётся незапущенным; finish не принимается; ошибка не теряется из-за отсутствия anchor.
- Синтетический handler payload не считается успешной native delivery; delayed/duplicate native events не создают вторую операцию.
- Pre-mutation rejection имеет no_effect; действительно неопределённый исход не становится retryable.
- PLAN/CODE review examples с пустыми и непустыми findings проходят реальные schemas.
- Один тест eval attribution/stop: первичная инфраструктурная причина сохранена, собственное дерево завершено, нет ложного успешного EVAL.
- Затем один живой прогон с сохранённой границы PLAN → PLAN-REVIEW. Старый RUN не изменять; новый fork должен использовать новый engine. Это проверит наиболее проблемную конкурентную волну без повтора первых стадий.

## Трассировка ожидаемого поведения

Controller создаёт wave → адаптер создаёт native children → каждый hook быстро регистрирует native invocation → CLI start проверяет receipt и атомарно создаёт WorkSession → ребёнок получает packet → создаёт результат → finish проверяет владельца и schema → controller принимает результаты wave. Если hook падает, adapter немедленно сообщает failure; CLI не создаёт WorkSession без receipt; controller останавливает дерево с исходной причиной. Ни status, ни самостоятельный вызов handler моделью не превращают неудачный start в успешный. Schema rejection после успешного start остаётся локально исправимым и не смешивается с отказом инфраструктуры.

Ограничение аудита: установлены конкретные общие места распространения класса ошибок; это не утверждение, что все native адаптеры воспроизвели Codex timeout. Для них требуется проверка контракта, а не механическое копирование Codex-specific обработчика.
