# Beta contour for flow and engine work

Use this runbook when changing the project-local `dd-flow` pack or
`dd-flow-cli` before promoting proven behaviour to the Memory Bank canon. It
is deliberately short: the current evaluation procedure is
[create-eval-case.md](create-eval-case.md) and
[execute-eval.md](execute-eval.md), both driven exclusively by `dd-eval
runner`.

## What a beta pair is

A beta pair is one explicit combination of:

- a committed `dd-tasks` beta branch containing the flow pack;
- a committed `dd-flow-cli` beta branch and a uniquely versioned local engine
  snapshot;
- a committed `dd-eval` case/run profile that records the exact pair.

The flow pack pins the selected beta engine exactly. Build and install the
engine through its normal installer, then verify `dd-flow engine resolve` and
`dd-flow engine doctor` against the clean project root. Do not call a source
`dist/cli.js` as eval evidence and do not copy engine directories between
isolated `DD_FLOW_HOME` roots.

## Smallest useful beta loop

1. Start with a concrete observation and classify it as `engine`, `flow`,
   `harness`, or `model` behaviour.
2. Write or amend the small beta specification that states the observed cause,
   intended contract and acceptance evidence. Beta specifications are design
   records, not Memory Bank protocols.
3. Change only the owning component. Add the smallest regression test for an
   engine or harness defect; validate a prompt/semantic change through the
   smallest affected eval.
4. Commit the flow and engine changes, give a changed engine a new prerelease
   version, install it, and commit the matching run-profile/checkpoint input.
5. For a changed stage contract, first run a disposable diagnostic over the
   affected boundary. When that is sound, build a fresh canonical entry-pack
   revision and run the declared focused or E2E comparison.
6. Preserve every failed attempt as evidence. A new beta version is needed for
   a behaviour or contract change, not for a repeat of the same pair.

## Eval boundary rules

- All mutable runtime files live below an absolute `DD_EVAL_HOME`.
- A routine focused run starts with a new empty provider Session and the
  accepted portable stage-entry fixture. It never uses a canonical or
  “starter” provider Session, and it never uses a provider fork as a fallback.
- An E2E run restores only the E2E entry, then lets the Subject create each
  successor artifact itself.
- The Subject's first technical action is the exact standalone lifecycle
  command generated by the runner. Keep `DD_FLOW_HOME=... dd-flow ...` as one
  Bash action so the hook can bind the real Session.
- The runner alone dispatches successor stages, creates mechanical worker
  Sessions, handles permitted HITL through an Interaction Judge and records
  events. It never chooses product work or repairs Subject artifacts.
- Do not manually send a Subject a recovery/continuation prompt after a
  provider turn ended with a running Stage. Preserve the trace as
  `incomplete_subject_turn`; a canonical build is restarted from a clean
  revision. This avoids accepting an artifact influenced by operator coaching.

## Promotion

Promote only the cumulative, accepted beta delta: reconcile its flow semantics
into `dd-memorybank`, transfer functional engine commits to the release branch,
release the engine and canon, update `dd-tasks`, then run one small control
eval on released artifacts. Do not carry beta pins, local paths, old runtime
snapshots, manual controller notes or provider Session IDs into the canon.

## Retired procedure

The former `prepare`, `sync`, `checkpoint`, starter-session and manual-fork
workflow is retired. Those low-level commands may exist for diagnostics, but
they are not a routine launch procedure and their output is not current scored
evidence.
